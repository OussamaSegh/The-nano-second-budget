## Threads and Data Races {#f05}

This chapter starts the concurrency half of Part 0. It explains what a thread adds to a program, writes a first correct parallel computation, and then defines the bug that the rest of the book is organised around: the data race.

### What a thread adds

A *process* has an address space and operating-system resources such as open files. A *thread* is a path of execution inside a process, with its own stack and registers but the same memory as every other thread in that process. Two threads can therefore work on different halves of one buffer with no copying at all. They can also corrupt each other's state if they touch the same mutable data without coordination.

*Concurrency* means tasks overlap in time; *parallelism* means they run at the same instant on different cores. A program can be concurrent on a single core, with the scheduler alternating between threads. Extra cores do not guarantee a speed-up: work may depend on other work, threads may fight over the same cache lines (Chapter 2), or the memory bus may already be saturated.

Starting a thread costs tens of microseconds. Starting one per record is almost always wrong. Systems in this book use a few long-lived threads, each with a clear job, that pass batches of work between them.

### A first correct parallel computation

Summing an array in parallel needs no shared state at all, if each thread owns its partial result:

```cpp
inline std::uint64_t parallel_sum(std::span<const std::uint32_t> in, unsigned threads) {
    std::vector<std::uint64_t> partial(threads, 0);   // one result per worker
    std::vector<std::thread> workers;
    const std::size_t chunk = in.size() / threads, extra = in.size() % threads;
    std::size_t begin = 0;
    for (unsigned t = 0; t < threads; ++t) {
        const std::size_t len = chunk + (t < extra ? 1 : 0);
        const auto part = in.subspan(begin, len);
        begin += len;
        workers.emplace_back([&partial, part, t] {
            partial[t] = std::accumulate(part.begin(), part.end(), std::uint64_t{0});
        });
    }
    for (auto& w : workers) w.join();
    return std::accumulate(partial.begin(), partial.end(), std::uint64_t{0});
}
```

Why is this correct without a mutex or an atomic? Every thread *reads* the input, which nobody writes while they run, and reading shared immutable data is always safe. Each thread *writes* only its own element of `partial`. The main thread reads `partial` only after `join()`, and join guarantees that each worker's writes are visible. Waiting "long enough" with a sleep would not: elapsed time creates no guarantee at all in C++.

A detail that has nothing to do with threads: `std::accumulate` uses the type of its initial value as the accumulator. With `0` it would accumulate in `int` and overflow long before the 64-bit result is assigned. `std::uint64_t{0}` selects the right type from the start.

The partial sums sit next to each other in one vector, so two workers write to the same cache line. That is correct, but it can be slow; Chapter 2 calls it *false sharing* and shows how to measure and avoid it. Here each thread writes its slot once, so it does not matter.

### The data race

Now share a counter:

```cpp
std::uint64_t count = 0;                       // plain integer
auto work = [&] { for (int i = 0; i < 100000; ++i) ++count; };
std::thread a(work), b(work);
a.join(); b.join();
// count is probably less than 200000, and the program has undefined behaviour
```

`++count` is three steps: load, add, store. Two threads can both load 10, both compute 11, both store 11, and one increment is lost. That much is intuitive. What is less intuitive is that C++ does not promise you even that: this program contains a **data race**, and a program with a data race has undefined behaviour. The compiler is allowed to assume races do not happen, so it may keep `count` in a register for the whole loop and store it once at the end, or do anything else that would be correct in a single-threaded program.

The definition is precise. Two accesses *conflict* if they touch the same memory location and at least one is a write. A data race is two conflicting accesses, from different threads, at least one of them not atomic, with neither ordered before the other by synchronisation. Three common misunderstandings follow from it:

- "My CPU writes 64-bit integers in one instruction, so it is atomic." The hardware is not the language. The race is in the C++ program, and the optimiser works on the C++ program.
- "`volatile` fixes it." It does not. `volatile` is for memory-mapped hardware registers; it makes neither the increment atomic nor any other data visible.
- "I read the value and then threw it away, so the race does not matter." The race is the access, not what you do with the result. Chapter 7 meets this one in the sequence lock, and fixes it properly.

There are exactly two ways to share mutable data without a race: protect every access with the same lock (Chapter F6), or use atomic operations whose ordering you can justify (Chapter F7). A third option is the best when it is available: do not share mutable data at all, as `parallel_sum` does.

### Finding races

ThreadSanitizer (TSan) instruments every memory access and reports conflicting accesses that are not ordered by synchronisation. Build the project with `-DLLDS_SANITIZE=thread` (see the preface) and run the tests: the counter above produces a report naming both lines. TSan finds races in executions it observes, so it needs tests that actually run the concurrent code paths. Chapter 16 covers it, and its limits, in depth.

### Summary

- Threads share memory. Prefer designs where each thread owns what it writes and shared data is read-only.
- `join()` makes a thread's writes visible; sleeping does not.
- A data race (conflicting accesses, one non-atomic, not ordered by synchronisation) is undefined behaviour, not merely a lost update.
- `volatile` is not for threads. Word-sized hardware stores do not make C++ code race-free.
- Run every concurrency test under ThreadSanitizer.
