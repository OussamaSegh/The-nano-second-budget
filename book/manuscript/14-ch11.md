## Memory Without malloc {#ch11}

Every data structure in Part III so far has avoided the allocator on its hot path, except the Michael-Scott queue, which allocates a node per item and was correspondingly slower. This chapter explains why the general-purpose allocator is a latency hazard, measures it, and builds the alternatives used throughout low-latency systems: fixed-size pools, lock-free pools, bump arenas and, best of all for pipelines, designs in which memory flows back to its owner instead of being freed.

### Why malloc is a hazard

Modern allocators (glibc's ptmalloc, jemalloc, tcmalloc, mimalloc) are fast on average. A small allocation from a thread-local cache costs 10 to 30 ns, which is acceptable on most hot paths. The problem is the *distribution*:

- **Cache refills.** When a thread's cache for a size class runs dry, the allocator refills it from a central structure, which may involve a lock shared by all threads.
- **Cross-thread frees.** Memory freed by a thread other than the one that allocated it must eventually find its way back. Each allocator handles this differently (remote free lists, per-thread arenas, periodic flushes), but all of them make the cross-thread pattern slower and less predictable than the same-thread one.
- **Growing the heap.** When the allocator needs more memory from the kernel (`brk` or `mmap`), the call itself takes microseconds, and the first touch of each new page takes a page fault (Chapter 1's table: 0.5 to 2 µs).
- **Returning memory.** Allocators periodically give memory back to the kernel (`madvise`, `munmap`) and must fault it in again later.
- **Fragmentation and locality.** Consecutive allocations land wherever the allocator finds space, so objects that are used together may be scattered across pages, costing cache and TLB misses (Chapter 2).

None of these happens often. All of them happen eventually, and each one lands in your tail.

### Measurements

`examples/ch11_allocators.cpp` measures two patterns. The first is same-thread: allocate a 64-byte message, touch it, free it, five million times, timing each allocate-and-free individually. The second is cross-thread: the producer allocates, sends the pointer through an SPSC ring, and the consumer frees it, which is the shape of every message pipeline. On the reference machine:

```text
same-thread alloc+free of 64 B (per-operation latency):

  LockFreePool   p50=31 p90=32 p99=41 p99.9= 65 p99.99=2943 max= 464467 (ns)
  Arena (bump)   p50=11 p90=14 p99=21 p99.9=109 p99.99= 407 max= 831396 (ns)
  pmr pool       p50=41 p90=55 p99=67 p99.9=129 p99.99=4287 max=1854863 (ns)

cross-thread (producer allocates, consumer frees):
  new/delete         alloc p50=106 p90=1087 p99=1663 p99.9=3615 p99.99=20735 (ns)
  LockFreePool       alloc p50=299 p90= 503 p99= 807 p99.9=3647 p99.99=20991 (ns)
  private list +ring alloc p50= 27 p90= 116 p99= 201 p99.9= 251 p99.99= 7423 (ns)
```

![Allocation when the consumer frees what the producer allocated. Sending memory back to its owner through a return ring keeps even p99.9 near 250 ns.](figures/chart-alloc.svg)

In the same-thread pattern, glibc's `new`/`delete` is excellent: 25 ns at the median, comparable to the pools. The bump arena is fastest, as it should be, since allocation is a pointer increment. The interesting row is the cross-thread one. When the consumer frees what the producer allocated, `new`'s median quadruples to 106 ns and its p90 jumps to over a microsecond: one allocation in ten pays for the allocator moving memory between threads.

The lock-free pool, perhaps surprisingly, is *worse* at the median in the cross-thread case (299 ns). Its free list is a single Treiber stack (Chapter 6), and in this pattern the producer pops from it and the consumer pushes to it on every message, so the stack's head is a cache line written by two threads on every operation. We have rebuilt exactly the contended line that Chapter 2 warned about.

The last row is the design this chapter recommends, and it is the only one with a short tail: a median of 27 ns, and a p99.9 of 251 ns against 3.6 µs for both of the others. We will build up to it.

### Fixed-size pools

Most hot-path allocations in a low-latency system are of a few fixed sizes: messages, orders, nodes, events. A **pool** pre-allocates a fixed number of fixed-size slots and hands them out and takes them back in O(1) without ever calling the allocator.

The simplest pool is single-threaded, with an **intrusive free list**: each free slot's storage holds a pointer to the next free slot, so the free list costs no memory of its own. Exercise 11.1 asks you to build exactly this:

```cpp
template <class T>
class FixedPool {
    union Slot {
        Slot* next;
        alignas(T) unsigned char storage[sizeof(T)];
    };
public:
    explicit FixedPool(std::size_t capacity);
    void* allocate() noexcept;        // pop the free list, or nullptr
    void deallocate(void* p) noexcept; // push onto the free list
    template <class... Args> T* create(Args&&... args);
    void destroy(T* p) noexcept;
};
```

Allocation pops the head of the list, deallocation pushes onto it. Both are a few instructions. Because the list is LIFO, the slot handed out is usually the one most recently freed, which is still hot in cache: a property general-purpose allocators also aim for.

A pool turns "out of memory" into an ordinary, testable condition: `allocate()` returns `nullptr` when the pool is exhausted. Deciding what to do then (drop, apply back-pressure, raise an alarm) is a design decision you make once, rather than an `std::bad_alloc` you discover in production.

### A lock-free pool

When several threads allocate and free from the same pool, the free list must be a concurrent stack. `include/llds/mem/object_pool.hpp` uses the tagged Treiber stack from Chapter 6:

```cpp
template <class T>
class LockFreePool {
    // The free-list hook is kept *beside* the object, not overlaid on it.
    struct Slot {
        TaggedStackHook hook;
        alignas(T) unsigned char storage[sizeof(T)];
    };
public:
    explicit LockFreePool(std::size_t capacity, bool prefault = true)
        : capacity_(capacity), slots_(new Slot[capacity]) {
        if (prefault) std::memset(static_cast<void*>(slots_.get()), 0, capacity * sizeof(Slot));
        for (std::size_t i = capacity; i-- > 0;) free_.push(&slots_[i].hook);
    }

    void* allocate() noexcept {
        TaggedStackHook* h = free_.pop();
        return h ? static_cast<void*>(reinterpret_cast<Slot*>(h)->storage) : nullptr;
    }
    void deallocate(void* p) noexcept {
        auto* base = reinterpret_cast<unsigned char*>(slots_.get());
        const auto idx = static_cast<std::size_t>(static_cast<unsigned char*>(p) - base) / sizeof(Slot);
        free_.push(&slots_[idx].hook);
    }
    // create(), destroy(), owns() ...
private:
    std::size_t capacity_;
    std::unique_ptr<Slot[]> slots_;
    TaggedStack free_;
};
```

Two details matter.

**The hook is beside the object, not inside it.** The single-threaded pool overlays the free-list pointer on the object's storage, which saves memory. In a concurrent pool that is a data race: a thread inside `pop()` may read the `next` field of a slot that another thread has just allocated and is now constructing an object in (the stale read the tagged pointer makes harmless in Chapter 6, but which is still a read of memory being concurrently written as a different type). Keeping the hook separate costs eight bytes per slot and keeps the program well-defined. This was a real bug in an early version of the companion library, found by reasoning about exactly this interleaving.

**Pre-faulting.** `new Slot[capacity]` reserves virtual memory, but the kernel only maps a physical page when it is first touched. Without pre-faulting, the first use of each page on the hot path takes a page fault. The `memset` in the constructor touches every page at start-up instead. (In this particular pool, the loop that builds the free list also writes every slot, so the `memset` is belt and braces; Exercise 7 explores when it is not.) For very large pools, `mlock` (or `mlockall(MCL_CURRENT | MCL_FUTURE)` for the whole process) additionally prevents the kernel from ever swapping the pages out.

The lock-free pool is the right tool when many threads allocate and free at random. As the measurements show, it is the wrong tool for a two-thread pipeline, because its single free-list head becomes a hot, shared, written line.

### Bump arenas

When many objects are allocated together and can all be freed together, a **bump arena** (also called a monotonic or linear allocator) is the fastest possible allocator: allocation is rounding a pointer up to the required alignment and adding the size; freeing is resetting the pointer to the start.

```cpp
class Arena {
public:
    explicit Arena(std::size_t bytes);  // allocates once and pre-faults
    void* allocate(std::size_t n, std::size_t align = alignof(std::max_align_t)) noexcept {
        std::size_t p = (used_ + align - 1) & ~(align - 1);
        if (p + n > size_) return nullptr;
        used_ = p + n;
        return buf_ + p;
    }
    template <class T, class... Args> T* make(Args&&... args);
    void reset() noexcept { used_ = 0; }
private:
    std::byte* buf_;
    std::size_t size_;
    std::size_t used_ = 0;
};
```

Arenas fit naturally wherever work has a clear lifetime: per message (parse a message into an arena, process it, reset), per frame in a game, per request in a server, per tick in a simulation. They are single-threaded by design; give each thread its own. Note that `reset()` does not run destructors: arenas are for trivially destructible objects, or objects whose destructors you call yourself.

C++17's `std::pmr` (polymorphic memory resources) gives standard containers the same abilities: `std::pmr::monotonic_buffer_resource` is a bump arena, `std::pmr::unsynchronized_pool_resource` a set of single-threaded pools, and `std::pmr::vector<T>`, `std::pmr::string` and friends allocate from whichever resource you pass them. The measurements show the `pmr` pool resource at about 41 ns, slower than the hand-written pool because of its virtual dispatch and size-class lookup, but still far more predictable than the global heap. It is the easiest way to keep existing container-based code off `malloc`.

### Memory that flows back

Now the design behind the last row of the measurements. In a pipeline, memory naturally flows in one direction: the producer fills buffers and the consumer uses them. The consumer must eventually give each buffer back. Instead of freeing it into a shared structure, it can **send it back** through a second SPSC ring, to the thread that owns it:

```text
             full buffers
   producer ─────────────────> consumer
   (owns a private free list)      │
       ^                           │
       └───────────────────────────┘
             empty buffers (return ring)
```

The producer keeps a private, single-threaded free list (a plain `std::vector<Msg*>` used as a stack). When it needs a buffer, it pops its private list. Only when the list is empty does it drain the return ring, refilling the list in one batch. The consumer, when it has finished with a buffer, pushes it onto the return ring. From `ch11_allocators.cpp`:

```cpp
for (std::uint64_t i = 0; i < n; ++i) {
    if (free_list.empty()) {
        Msg* back;
        while (to_producer.try_pop(back)) free_list.push_back(back);
    }
    if (free_list.empty()) { --i; continue; }  // everything is in flight: retry
    Msg* m = free_list.back();
    free_list.pop_back();
    m->words[0] = i;
    while (!to_consumer.try_push(m)) {}
}
```

Every shared write in this design is one of the two rings' indices, each with a single writer; the free list is private to the producer; and the producer touches the return ring only once per batch. The result is the 27 ns median and 251 ns p99.9 in the table: an order of magnitude better in the tail than both the global allocator and the lock-free pool.

The pattern generalises. Network stacks recycle packet buffers this way (DPDK's mempools have per-core caches that work similarly), audio engines recycle sample buffers, and the Disruptor (Chapter 10) is the extreme case, in which the "buffers" never leave the ring at all.

### Other sources of page faults

Avoiding `malloc` is not enough to avoid page faults on the hot path. Other common sources are:

- **Thread stacks.** A new thread's stack is mapped lazily; deep recursion or large stack arrays fault on first use. Touch the stack at thread start (or use `mlockall`).
- **Static and global data.** Large zero-initialised arrays live in the BSS segment and are faulted in on first touch.
- **Copy-on-write after `fork`.** Avoid forking latency-critical processes.
- **Transparent huge pages.** The kernel's background compaction (`khugepaged`) can stall a process. Either use explicit huge pages (`MAP_HUGETLB`, `hugetlbfs`) or disable THP for latency-critical processes (Appendix B).
- **Memory-mapped files.** Every first access to a page of an `mmap`ed file is a fault, possibly with disk I/O.

`perf stat -e page-faults,major-faults` on a running process shows how many faults it takes. On a well-prepared hot path, the number after start-up should be zero.

### Summary

- `malloc` is fast on average and unpredictable in the tail: cache refills, cross-thread frees, heap growth and page faults all land eventually.
- Measured on the reference machine: `new`/`delete` 25 ns same-thread, but a 106 ns median and over 1 µs at p90 when the consumer frees what the producer allocated.
- Fixed-size pools make allocation O(1), predictable and testable; pre-fault their memory. Lock-free pools allow any thread to allocate and free, at the cost of a contended free-list head.
- Bump arenas are the fastest allocator for objects with a shared lifetime; `std::pmr` brings the same ideas to standard containers.
- In pipelines, send memory back to its owner through a return ring. Measured: 27 ns median and 251 ns p99.9, against 3.6 µs for both `new` and the lock-free pool.
