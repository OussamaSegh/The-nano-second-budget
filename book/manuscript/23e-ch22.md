## Engineering for a Regulated Environment {#ch22}

A medical device's software is developed under a defined process. IEC 62304 sets out the software life cycle; ISO 14971 covers risk management; a quality management system such as ISO 13485 wraps both. This book does not interpret those standards, and nothing in it establishes compliance with any of them. What it can do is teach the engineering habits that make such a process work instead of fighting it: stating claims precisely, connecting each one to a design decision, a test and a result, and keeping that chain intact when the code changes. This chapter applies those habits to the pipeline of Chapters 19 to 21, then sets out a capstone project in five reviewable stages.

### Claims need boundaries

"The pipeline loses no data" is not a claim anyone can verify. Which data? Every hit the simulator generated, every record the transport delivered, or every photon that reached a crystal? The software cannot count events it was never told about, unless the protocol gives it a way, such as sequence numbers. A verifiable version of the claim names its boundary and its mechanism:

> Every hit record delivered to the host is either decoded and passed to coincidence sorting, or rejected by the decoder and counted; every record lost between the front end and the decoder is detected through per-module sequence numbers and counted.

That is a claim the example checks at the end of every run.

### From requirement to evidence

A small traceability table for the example looks like this. The identifiers are invented for this book; a real project's come from its own requirements process.

| ID | Requirement | Design | Verification |
|---|---|---|---|
| DAQ-001 | A record whose length is not 16 bytes, or whose module is out of range, is rejected and counted, and never produces a hit | `decode_hit` returns a status; writes `out` only on success | `test_pet`: decode boundaries; example `--corrupt`: rejected = injected |
| DAQ-002 | Every lost record is detected and counted | per-module sequence numbers; end-of-stream final counts | example: gaps = dropped + rejected, in normal and overload runs |
| DAQ-003 | Coincidences are exactly the pairs defined by the pairing specification (Ch. 20) | `StreamingSorter`, checked against `pairs_oracle` via `window_pairs` | `test_pet`: oracle equality, every chunk split; example `--smoke`: oracle check |
| DAQ-004 | Merged hits are in non-decreasing time order across sources | `WatermarkMerger` with source promises | `test_pet`: merge equals stable sort; sorter's out-of-order count is 0 |
| DAQ-005 | No batch is processed with a mix of calibration versions; every count names its version | immutable `CalibrationTable`, one snapshot per batch | `test_pet`: snapshot consistency under concurrent publish; example output by version |
| DAQ-006 | Data may be dropped only at the sources, and every drop is counted | backpressure downstream of the sources | example `--rate=0` and `--slow-analysis`: books balance |
| DAQ-007 | No data race in the pipeline's components | ownership table (Ch. 19), release/acquire hand-offs | all tests and the example's smoke run under ThreadSanitizer |

Two features of the table matter more than its contents. Each row's evidence is *executable*: a test that fails if the property breaks, not a sentence in a document. And the table lives with the code, so a change to the design shows up as a change to the table that a reviewer can see.

Tests are evidence, not proof. The randomised tests cover many inputs but not all; ThreadSanitizer sees the interleavings that happened, not all possible ones (Chapter 16); the close tests of Chapter F6 do not force every waiter state. State those limits next to the evidence, as Chapter 16's hierarchy of evidence does. A reviewer who finds the limits stated trusts the rest more.

### Fault reports that can be acted on

When something goes wrong in the field, the report is all anyone has. Record a fault code, the stage, a run identifier, the configuration and calibration versions, and enough detail to reproduce it, and keep the *first* causal fault: a source going silent may cause a watermark stall, then full buffers, then drops, and a log that shows only the drops points at the wrong component. Distinguish faults that look alike: a length error from an invalid module number, a full queue from a transport failure, a slow consumer from a stalled source.

Observability must not perturb the data plane. A log line per hit allocates, locks, formats and writes; a pipeline with one becomes a benchmark of the logger. Use per-thread counters (Chapter 13's sharded counter), published as a periodic immutable snapshot or read after join, and buffered event records with explicit overflow handling (Chapter 18's audit log). Measure the cost: run with one log line per record, one per thousand, and a sampled counter, and compare throughput and tail latency with the same processing in all three.

### Two kinds of stop

*Draining* and *aborting* are different promises, and a pipeline that only has one of them will eventually be asked for the other.

- **Graceful stop** (drain): stop accepting new acquisition, process everything already accepted, then shut down. The example's end of run is a drain: each source sends a final batch marked `last`, the merger closes that source, and the pipeline finishes once every source is closed and every buffer is empty.
- **Abort**: stop as soon as possible, and report how much accepted data was discarded. Every blocking wait must be interruptible (a closeable queue, a stop token, a flag checked in every spin loop), and the report must count what was in each buffer when the abort happened.

In both, the owner joins every thread before destroying anything those threads use (Chapter F2), and the tests must check the *accounting*, not just that the program exits. A test that aborts and passes because nothing hung has not tested the abort contract.

### Reviewing a concurrency change

Ask for these with every change to the data path, and give them with your own:

- **For a queue or hand-off change:** the ownership table, the publication and reuse edges with the operations that provide them, and shutdown tests (drain and abort).
- **For a data-layout change:** a differential test against the previous layout's output, and measurements on a quiet machine (Appendix B), with the run-to-run range.
- **For a configuration change:** validation, versioning, and a test that a batch never mixes versions.
- **For a memory-order relaxation:** the edge that is no longer needed and why, sanitizer results, and the note that x86 hides many ordering bugs (Appendix A), with a run on ARM if one is available.

A good review technique for lock-free code is to explain the change aloud while a colleague interrupts at every publication or reclamation step to ask "what guarantees the reader sees this?" and "what guarantees nobody still reads that?". It is particularly effective for hazard pointers and epochs (Chapter 12), where a pointer can be perfectly valid while the object it points to has already been reclaimed.

### Capstone: evolve the pipeline in five stages

The project below turns the example into something closer to a real acquisition system, one reviewable change at a time. Each stage ends with a short note: what changed, which rows of the traceability table it affects, the tests and results, and what is still unverified.

**Stage 1: reproduce and specify.** Build the project, run all tests and the example, and record the compiler, flags and machine. Write a one-page specification of the record format, time ordering, module domain, pairing rule and failure behaviour, and check it against the code. Change the simulated energy distribution and confirm that the coincidence count does not change, since energy is not part of the pairing rule, and the energy-qualified count does.

**Stage 2: a second pairing policy.** Add single-window sorting with kill-multiples (Exercise 20.1) as a selectable policy in the sorter, behind the same interface. Add a streaming version, test it against the batch version for every chunking, and report trues, randoms (Exercise 20.2) and multiples for both policies at three count rates. Do not change the default policy without the people who own it.

**Stage 3: faults and abort.** Add heartbeats to the sources and a timeout that excludes a silent source and records the fault. Add an abort path that interrupts every wait and reports what was discarded at each stage. Inject a source that stops, a source that sends a broken promise, and a decoder flood of bad records, and test that each run ends within a time limit with the right status and balanced books.

**Stage 4: a measured design change.** Replace one hand-off, for example the analysis ring with a Disruptor (Chapter 10) feeding both the analysis and a list-mode writer. Keep the workload, endpoints and output checks identical, measure at several offered rates with paced arrivals (Chapter 4's coordinated-omission rules apply), and report rejected and late data, not only latency. It is a legitimate outcome that the simpler design wins.

**Stage 5: the review package.** Assemble the design note, the traceability table, the test and sanitizer logs, the benchmark protocol and raw results, the known limitations, the list of unverified assumptions, and the exact source revision. Explain why each concurrent structure you chose was necessary. If a vector and a mutex would meet a requirement, saying so is the stronger engineering decision.

A possible scoring rubric, for self-assessment or for a study group: correctness and boundary cases 30 points; ownership and shutdown reasoning 25; tests and differential checks 20; measurement validity 15; clarity of documentation and limitations 10. A fast pipeline with a data race or silent loss fails regardless of its score.

### A rehearsal for a technical discussion

Whether in an interview or a first design review in a new team, the ability to explain a design briefly and honestly is worth more than a fast queue. Practise this in three minutes:

1. **The pipeline:** two simulated sources with per-module sequence numbers, SPSC rings of wire batches, decode and validation, watermark merge, streaming coincidence sorting against an oracle, versioned calibration, private histograms.
2. **The rules:** loss in one place and counted; sequence numbers as independent proof; backpressure everywhere else; one calibration version per batch; join before destroy.
3. **One limitation, stated plainly:** for example, a silent source stalls the merge until a timeout excludes it, and the example has no timeout yet.
4. **The next experiment:** for example, compare multiple-window and single-window sorting at three count rates, with randoms estimated by a delayed window, and report what changes for reconstruction.

Then expect the questions this book has prepared you for: why not a mutex here, what happens when that buffer is full, how do you know nothing was lost, and what does that number mean on a different machine.

### Summary

- Standards define the process; engineering habits make it work. This book teaches the habits, not compliance.
- Give every claim a boundary and a mechanism. Connect requirement, design, test and result, and keep the table with the code.
- Tests and sanitizers are evidence with limits; state the limits.
- Keep the first causal fault. Observe without perturbing the data plane.
- Draining and aborting are different contracts; test the accounting of both.
- Evolve the system in small, reviewable stages, each with its evidence.
