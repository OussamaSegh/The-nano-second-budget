## Ordered Structures: Skip Lists and Order Books {#ch14}

A hash map answers "what is the value for this key?". Many systems also need to answer "what is the *smallest* key?", "what comes after this one?" and "what lies between these two?". The order book of an exchange, a scheduler's queue of timers, a time-ordered event log and a database index all need order. This chapter builds the concurrent ordered structure that has become the standard answer, the skip list, then turns to the order book, the ordered structure whose performance is most scrutinised, and finds that the best concurrent order book is usually not concurrent at all.

### Why not a concurrent tree?

The sequential answer to "ordered map" is a balanced binary search tree; `std::map` is a red-black tree. Trees are hard to make concurrent for one reason: **rebalancing**. An insert in a red-black tree may recolour and rotate nodes all the way up to the root, so a single update can touch nodes that every other operation needs. A lock per node does not help when an update must hold locks on a whole path; a global lock serialises everything.

Lock-free and fine-grained trees do exist. Ellen, Fatourou, Ruppert and van Breugel's non-blocking binary search tree (2010), Natarajan and Mittal's lock-free BST (2014) and Bronson's optimistic AVL tree (2010) are all practical. They are also among the more intricate algorithms in the literature, and most give up on strict balance. The skip list reaches the same goal with only local changes, and with an implementation that can be checked in an afternoon.

### Skip lists

A **skip list** (William Pugh, 1990) is a sorted linked list with express lanes. Every node is in the bottom list, level 0. Each node is also, with probability 1/2, in level 1; with probability 1/4, in level 2; and so on. Each level is itself a sorted linked list, and higher levels skip over more nodes:

![A skip list. Every node is on level 0, and each level above holds about half the nodes of the level below. A search starts at the top of the head and drops one level each time the next node would overshoot.](figures/skiplist.svg)

To search for a key, start at the head's top level, move right while the next key is smaller than the target, and drop down a level when it is not. At level 0, the next node is the first one whose key is at least the target. Each level skips about half the remaining nodes, so the expected search cost is O(log n), with the same constant as a balanced tree and no rebalancing at all: a node's level is chosen randomly when it is inserted and never changes.

Every operation is built on one helper, which Exercise 14.1 asks you to write: walk from the top level down and record, at each level, the last node before the target position. Those are the **predecessors**. Insert links a new node in after each predecessor up to the node's level. Erase unlinks the node from each predecessor. Both touch only the nodes adjacent to the change.

That locality is what makes skip lists the standard concurrent ordered map. Java's `ConcurrentSkipListMap` (Doug Lea's lock-free design, after Fraser and Harris) is the best known; LevelDB and RocksDB use skip lists as their in-memory tables; Redis uses them for sorted sets.

### The lazy skip list

`include/llds/ordered/lazy_skiplist.hpp` implements the **lazy skip list** of Herlihy, Lev, Luchangco and Shavit ("A Simple Optimistic Skiplist Algorithm", 2007). It is not lock-free, since updates take locks, but its lookups take no locks at all and never retry, and its updates lock only the few nodes they change. It is much simpler than the lock-free variants and performs about as well.

Each node carries, besides its key, value and `next` array, two flags and a lock:

```cpp
struct Node {
    Kind kind;                              // Head, Data or Tail
    K key{};
    V value{};
    int top_level;
    std::atomic<bool> marked{false};        // logically deleted
    std::atomic<bool> fully_linked{false};  // linked at every level
    TtasLock lock;
    std::array<std::atomic<Node*>, MaxLevel> next{};
};
```

A key is **in the set** exactly when its node is `fully_linked` and not `marked`. Those two flags carry the whole algorithm.

**Lookup** is an ordinary skip-list search over atomic `next` pointers, followed by a check of the flags:

```cpp
bool contains(const K& k) const {
    EpochDomain::Guard g;
    Node* preds[MaxLevel];
    Node* succs[MaxLevel];
    const int lf = find_node(k, preds, succs);
    return lf != -1 && succs[lf]->fully_linked.load(std::memory_order_acquire) &&
           !succs[lf]->marked.load(std::memory_order_acquire);
}
```

It takes no locks, writes nothing shared, and visits each node at most once, so it is wait-free. The epoch guard is what makes it safe to follow `next` pointers while a concurrent erase unlinks and retires nodes (Chapter 12). Here the epoch scheme is clearly better than hazard pointers: a search visits about `2 log₂ n` nodes, around 34 for 100,000 keys, and protecting each with a hazard pointer would cost 34 fences.

**Insert** has three phases. First, an optimistic search without locks, which finds the predecessors and successors at every level. Second, it locks each distinct predecessor from the bottom up and **validates**: each predecessor is unmarked, each successor is unmarked, and each predecessor still points to its successor. If validation fails, some concurrent update got there first; release the locks and start again. Third, link:

```cpp
Node* n = new Node(k, std::move(v), top);
for (int l = 0; l <= top; ++l) n->next[l].store(succs[l], std::memory_order_relaxed);
for (int l = 0; l <= top; ++l) preds[l]->next[l].store(n, std::memory_order_release);
n->fully_linked.store(true, std::memory_order_release);   // linearization point
```

The new node's own pointers are set before it becomes reachable; then it is linked bottom-up, so it appears in level 0 first; then it is marked fully linked. A lookup that finds it before that last store sees `fully_linked == false` and reports it absent, which is correct, because the insert has not yet taken effect.

If the search finds the key already present and unmarked, the insert waits until that node is fully linked and returns false. The wait is a subtle linearizability point: without it, our `false` ("already present") could be observed before the other thread's `true` takes effect.

**Erase** is two-step, which gives the algorithm its name. It locks the victim and sets `marked`, the **logical deletion** and the linearization point; from then on, lookups report the key absent. Then it locks the predecessors, validates that each still points to the victim, and unlinks it from the top level down: the **physical deletion**. Finally, it retires the node through the epoch domain. A lookup that was already standing on the victim when it was unlinked can still follow its `next` pointers, which are untouched, so it is not lost.

Range scans walk level 0 from the first node at or above the lower bound, reporting each node that is fully linked and unmarked:

```cpp
template <class F>
void for_range(const K& lo, const K& hi, F&& f) const {
    EpochDomain::Guard g;
    Node* preds[MaxLevel];
    Node* succs[MaxLevel];
    find_node(lo, preds, succs);
    for (Node* n = succs[0]; n->kind == Kind::Data && n->key < hi;
         n = n->next[0].load(std::memory_order_acquire))
        if (n->fully_linked.load(std::memory_order_acquire) && !n->marked.load(std::memory_order_acquire))
            f(n->key, n->value);
}
```

A scan is **not a snapshot**: a key inserted or erased during the scan may or may not be reported. What it guarantees is that every reported key was in the set at some moment during the scan, and that every key present for the whole scan is reported. For most uses (risk checks, monitoring, display), that is enough. When it is not, take a snapshot with an RCU structure (Chapter 13) instead.

### Measurements

`examples/ch14_skiplist.cpp` runs a mixed workload, 80% lookups, 10% inserts and 10% erases, over keys drawn uniformly from 0 to 100,000, half of which are present at the start. It compares `std::map` under a mutex, `std::map` under a `std::shared_mutex`, and the lazy skip list. Throughput, all threads together, on the reference machine:

```text
                 T=1           T=4
mutex map        4.29 M ops/s  1.32 M ops/s
rw map           3.83 M ops/s  0.39 M ops/s
lazy skiplist    2.12 M ops/s  7.03 M ops/s
```

![Three ordered maps on one and four threads. The skip list is the slowest on one thread and the only one that gets faster with more.](figures/chart-maps.svg)

On one thread, the skip list is *half* as fast as `std::map`. That is the usual result and worth stating plainly. The skip list's nodes are bigger (a 16-entry `next` array, flags and a lock), so fewer fit in the cache; each search visits about twice as many nodes as a balanced tree's; every operation takes an epoch guard, with its fence; and every update takes locks. A concurrent structure pays for its concurrency even when there is none.

On four threads, the picture inverts. The mutex-protected map loses two-thirds of its throughput, the reader-writer lock loses 90%, and the skip list more than triples, to five times the mutex map's throughput. The rule from Chapter 13 applies again: readers that write shared lines do not scale, and the skip list's readers write nothing shared.

The second part of the example measures the operation that makes an ordered structure worth having: a range scan over 50 price levels, out of 2,000, while another thread continuously inserts and erases levels in the same range.

```text
50-level range scan under churn:
  p50=112 p90=181 p99=351 p99.9=615 p99.99=13439 max=100390 (ns)
```

A median of 112 ns for 50 levels, a little over 2 ns per level, and a p99.9 of 615 ns, with a writer modifying the structure underneath. The scan never waits for the writer, and the writer never waits for the scan. The p99.99 and maximum, 13 µs and 100 µs, are not the data structure: on a four-vCPU virtual machine running two busy threads plus the system, they are the scheduler and the hypervisor taking the core away (Chapter 17 is about removing them).

### Order books

An **order book** is the list of outstanding buy orders (**bids**) and sell orders (**asks**) for one instrument on one exchange. Bids are ordered by price, highest first; asks by price, lowest first. The highest bid and lowest ask are the **top of book**, or the "inside market", and the difference between them is the **spread**. Every trading system maintains order books, built from the exchange's market-data feed, and the speed at which it can update them and read the top of book is a direct component of its reaction time.

There are two common granularities. A **market-by-price** (MBP, or "level 2") book aggregates all orders at the same price into one level with a total quantity; the feed reports changes to levels. A **market-by-order** (MBO, or "level 3") book tracks every individual order, with its ID, price, quantity and position in the queue at its price; the feed reports adds, modifies, cancels and executions of orders.

The operations, for an MBP book, are:

- **Apply an update**: add or remove quantity at a price level; create the level if it does not exist; delete it if its quantity falls to zero.
- **Read the top of book**: best bid and best ask, with their quantities. This is by far the most frequent read.
- **Read depth**: the best N levels on each side, for models that look past the top.

The natural first implementation is an ordered map per side, from price to quantity, which is what `llds::MapBook` does (`include/llds/ordered/order_book.hpp`):

```cpp
class MapBook {
public:
    void apply(Side side, std::int64_t px, std::int64_t qty) {
        if (side == Side::Bid) adjust(bids_, px, qty);
        else adjust(asks_, px, qty);
        publish();
    }
    TopOfBook top() const { return top_.load(); }
    // ...
private:
    std::map<std::int64_t, std::int64_t, std::greater<>> bids_;  // best (highest) first
    std::map<std::int64_t, std::int64_t> asks_;                  // best (lowest) first
    SeqLock<TopOfBook> top_;
    std::uint64_t seq_ = 0;
};
```

Prices are integers, in **ticks**, the instrument's minimum price increment. Floating-point prices in an order book are a classic bug: 0.1 + 0.2 is not 0.3, and two levels that should be one appear side by side.

### The single-writer order book

Notice what `MapBook` is *not*: it is not a concurrent map. That is deliberate, and it is the most important design point in this chapter.

An order book for one instrument is updated by a stream of messages from one feed, which must be applied **in sequence-number order**. Two threads applying updates to the same book concurrently would have to be ordered anyway, so there is nothing to gain from a concurrent structure on the write side. Real systems therefore give each book exactly one writer: the feed-handler thread that decodes the feed (or one of several, each owning a partition of the instruments).

The readers, strategy threads that want the top of book, need a consistent snapshot of a few numbers, not access to the whole book. So the writer **publishes** a small `TopOfBook` struct after every update, through a seqlock (Chapter 7):

```cpp
struct TopOfBook {
    std::int64_t bid_px, bid_qty, ask_px, ask_qty;
    std::uint64_t seq;   // update counter
};
```

Readers on any number of cores read the seqlock without writing anything; the writer never waits for them. This combination, a single-threaded structure owned by one thread, with a small summary published through a seqlock or a ring, is the standard architecture of a market-data system, and it outperforms any concurrent order book. The `seq` field lets a reader detect that it has missed updates, or that the top of book has not changed since it last looked.

When strategies need more than the top, the writer can publish the top N levels through the same mechanism, or it can send every update downstream through an SPSC ring or a Disruptor (Chapter 10) so that each consumer maintains its own copy of the book.

The remaining question is how fast the single-threaded book itself can be made, and the answer has nothing to do with concurrency. `std::map` allocates a node per level, rebalances on insert and erase, and follows a chain of pointers on every lookup. Chapter 15 replaces it with a flat array indexed by price, the **ladder**, and measures the result: 45 ns per update for `MapBook` against 12 ns for `LadderBook`, on the same stream of updates, with both books producing the same top of book.

### Market-by-order books

An MBO book adds an index from order ID to order, because cancels and modifies identify the order only by ID. A typical layout has three parts:

- A **pool** of fixed-size order records, allocated once (Chapter 11). Each record holds the order's ID, side, price, quantity and two intrusive links.
- Each price level holds an **intrusive doubly linked list** of its orders, in time priority, so that a cancel unlinks an order in O(1) and the queue position of an order can be computed by walking from the front.
- A **hash map from order ID to record**, typically an open-addressing table such as `ConcurrentIntMap` or a single-threaded Swiss table, since only the writer uses it. Order IDs are an unbounded key space, so the table must be rebuilt or cleared periodically (exchanges typically reset IDs daily).

The ladder or tree of levels sits on top, holding each level's total quantity and its list head. With all of this pre-allocated, an MBO update is a hash lookup, a list operation and an array update: a few tens of nanoseconds, with no allocation.

### Other ordered structures

Two more structures solve problems that look as if they need a sorted map but do not.

**Priority queues.** If you only need the minimum (the next timer to fire, the next event to process), a binary heap in an array is far faster than any map. For timers specifically, a **hierarchical timing wheel** (Varghese and Lauck, 1987), used by the Linux kernel, Kafka and Netty, makes insert and cancel O(1): timers are hashed into slots by expiry time, and the wheel advances one slot per tick.

**Sorted arrays.** For data that is read far more often than it changes, a sorted `std::vector` with binary search beats every node-based structure for lookups and range scans, because it is contiguous and prefetchable. Combined with RCU (copy, insert, publish), it gives lock-free, snapshot-consistent ordered reads, at the cost of O(n) writes.

### Summary

- Ordered structures support minimum, successor and range queries, which hash maps cannot. Trees are hard to make concurrent because rebalancing touches nodes far from the change.
- A skip list is a sorted linked list with randomly chosen express lanes: expected O(log n) operations with only local updates.
- The lazy skip list has wait-free lookups (an unlocked search plus two flags), and updates that lock only their predecessors, after an optimistic search and validation. Erase marks first, then unlinks, then retires through epochs.
- Measured: on one thread, the skip list ran at half the speed of `std::map` under a mutex (2.1 against 4.3 M ops/s). On four threads, it ran 3.3 times faster than its own single-thread figure and five times faster than the mutex map. A 50-level range scan under churn took a median of 112 ns.
- Order books are ordered by price in integer ticks, and are best built as single-writer structures that publish a top-of-book summary through a seqlock. Concurrency is solved by ownership, not by a concurrent map.
- MBO books combine a pool of orders, intrusive lists per level and a hash map by order ID.
