## Data-Oriented Design and SIMD {#ch15}

The previous fourteen chapters were mostly about synchronisation: how threads share data without waiting for each other. This chapter is about something that often matters more, and that applies just as much to code running on one thread: how data is laid out in memory. The memory hierarchy of Chapter 2 rewards programs that touch memory sequentially and densely, and punishes those that chase pointers and drag unused bytes through the cache. **Data-oriented design** is the discipline of choosing layouts for the access patterns a program actually has, rather than for the objects a programmer happens to think in. Its natural partner is **SIMD**, the instructions that process 4, 8 or 16 values at once, which can only be used when data is laid out to suit them.

### The cost of a byte you did not need

Recall the numbers from Chapter 2. A load that hits L1 costs about 1 ns; one that misses every cache and goes to DRAM costs around 100 ns, the time to execute several hundred instructions. The unit of transfer is always a 64-byte cache line. If a program needs 4 bytes from each line it fetches, 94% of the memory bandwidth it consumes, and of the cache capacity it fills, is waste.

Object-oriented code produces exactly that pattern. A natural C++ record for a bedside monitor might be:

```cpp
struct PatientAoS {             // one 64-byte record per bed
    std::uint32_t bed_id;
    std::int32_t heart_rate;
    std::int32_t spo2;
    std::int32_t resp_rate;
    std::int32_t systolic;
    std::int32_t diastolic;
    std::int32_t temperature_mc;
    std::int32_t flags;
    std::uint64_t last_update_ns;
    char name[24];
};
std::vector<PatientAoS> beds;   // "array of structs"
```

This is an **array of structs** (AoS): each object's fields are together, and the objects are in sequence. It is the right layout when code typically uses many fields of one record at once, such as when rendering one patient's tile on a display. It is the wrong layout for a query that looks at one field across many records: "how many patients have a heart rate above 120?". That query loads a full cache line per patient and uses 4 bytes of it.

The alternative is a **struct of arrays** (SoA): one array per field.

```cpp
struct PatientsSoA {
    std::vector<std::uint32_t> bed_id;
    std::vector<std::int32_t> heart_rate, spo2, resp_rate, systolic, diastolic,
                              temperature_mc, flags;
    std::vector<std::uint64_t> last_update_ns;
};
```

Now the heart-rate query reads one dense array of `int32_t`, sixteen values per cache line, all of them useful.

### Measurements

`examples/ch15_data_oriented.cpp` runs three comparisons on four million records. The first is the heart-rate count in each layout:

```text
scan one field of 4000000 records: AoS 5.67 ns/rec, SoA 0.27 ns/rec
```

The SoA scan is **21 times faster**. Two effects multiply. The AoS loop is bound by memory bandwidth: each record costs one cache line, and 64 bytes per 5.67 ns is about 11 GB/s, roughly what one core of this virtual machine can pull from DRAM. The SoA loop reads 16 times less data, *and* the compiler can now vectorise it: with AVX2, one instruction compares eight heart rates against 120 and another adds the eight results to a vector of counts. GCC 12 and later vectorise simple loops like this even at `-O2`, which the examples use.

The second comparison sums the heart rates of patients whose SpO₂ is below 90%, first with an `if`, then without a branch:

```cpp
// branchy
if (soa.spo2[i] < 900) s1 += soa.heart_rate[i];

// branchless
const long mask = -static_cast<long>(soa.spo2[i] < 900);   // all ones or all zeros
s2 += soa.heart_rate[i] & mask;
```

```text
filtered sum: branchy 5.58 ns/rec, branchless 0.35 ns/rec (same result)
```

The SpO₂ values are random between 85.0% and 99.9%, so the condition is true for a third of the records with no pattern, and the branch predictor guesses wrong about a third of the time. Each misprediction throws away the work the core did speculatively, about 15 to 20 cycles. The branchless version does the same arithmetic for every record and selects the result with a mask, so there is nothing to mispredict, and as a bonus it vectorises. To keep the comparison honest, the branchy loop contains a compiler barrier that stops GCC from converting it to branchless code by itself; without the barrier, GCC would produce almost the same code for both. Exercise 6 asks you to separate the two effects.

The third comparison applies the same five million order-book updates to the two books of Chapter 14:

```text
order book updates: MapBook 45.3 ns/update, LadderBook 12.2 ns/update (tops agree)
```

The flat ladder is almost four times faster than the tree, for reasons we will look at below.

### Hot and cold data

Full SoA is not always the right answer. If a query needs heart rate, SpO₂ and respiratory rate together, three separate arrays mean three streams and three cache misses per record when the data is not cached. Two intermediate layouts are common.

**Hot/cold splitting** puts the fields used on the hot path together in a small struct, and moves everything else (names, descriptions, configuration, statistics) into a parallel array or behind an index:

```cpp
struct VitalsHot {               // 16 bytes: four beds per cache line
    std::int16_t heart_rate, spo2, resp_rate, systolic;
    std::int16_t diastolic, temperature_dc;
    std::uint16_t flags, bed;
};
struct PatientCold {             // touched by the UI, rarely
    std::string name, mrn, ward;
    AlarmLimits limits;
};
std::vector<VitalsHot> hot;
std::vector<PatientCold> cold;   // same index
```

Note also the narrower types. Heart rate fits in 16 bits; so does SpO₂ in tenths of a percent. Halving the size of hot data halves the cache lines it needs, and on a hot path, that is usually worth more than any instruction-level optimisation.

**Array of structs of arrays** (AoSoA) groups records into blocks of, say, 8 or 16, with SoA layout inside each block. A block is one or a few cache lines, so related fields of the same record are close, and each field's values for the block are contiguous and SIMD-friendly. Game engines and particle systems use it heavily.

The general principle is to ask, for each piece of data, **which code reads it, and how often**, and group data by access pattern rather than by the noun it describes. In a market-data system, the top of book is read millions of times per second and the instrument's name a few times a day; they do not belong in the same cache line.

### Layout within a struct

Even inside one struct, layout matters:

- **Order fields by size**, largest first, to minimise padding. A struct of `char, double, char, double` is 32 bytes; reordered as `double, double, char, char`, it is 24.
- **Check sizes** with `static_assert(sizeof(T) == 64)`, as the example does, so that a careless edit cannot silently push a hot struct over a cache-line boundary.
- **Use indices instead of pointers** for links between pooled objects. A 32-bit index into a pool is half the size of a pointer, which can halve the size of a small node, and it survives serialisation and relocation.
- **Keep data written by different threads apart** (Chapter 2), but keep data written by the *same* thread together. SoA arrays updated by several threads must be partitioned so that no cache line is written by two of them.

### The ladder order book

Chapter 14's `MapBook` stores each side of the book in a `std::map`: one heap-allocated node per price level, with a lookup that follows about log₂ n pointers through scattered memory. `LadderBook` replaces it with the data-oriented alternative, a flat array of quantities indexed by price:

```cpp
class LadderBook {
public:
    LadderBook(std::int64_t base, std::size_t levels)
        : base_(base), bids_(levels, 0), asks_(levels, 0) {}

    void apply(Side side, std::int64_t px, std::int64_t qty) {
        const auto i = static_cast<std::size_t>(px - base_);
        if (side == Side::Bid) {
            auto& q = bids_[i];
            q += qty;
            if (q < 0) q = 0;
            if (q > 0 && (best_bid_ < 0 || static_cast<std::int64_t>(i) > best_bid_))
                best_bid_ = static_cast<std::int64_t>(i);
            else if (q == 0 && static_cast<std::int64_t>(i) == best_bid_)
                rescan_bid(i);
        } else { /* the mirror image for asks */ }
        publish();
    }
private:
    void rescan_bid(std::size_t from) {
        for (std::size_t j = from; j-- > 0;)
            if (bids_[j] > 0) { best_bid_ = static_cast<std::int64_t>(j); return; }
        best_bid_ = -1;
    }
    std::int64_t base_;
    std::vector<std::int64_t> bids_, asks_;
    std::int64_t best_bid_ = -1, best_ask_ = -1;   // indices; -1 = empty
    SeqLock<TopOfBook> top_;
    std::uint64_t seq_ = 0;
};
```

An update is an array index and an add. The best price is tracked incrementally: an update that creates quantity above the current best moves the best up; an update that empties the best level triggers a **rescan** for the next non-empty level. A rescan sounds expensive, but real books are dense near the inside, so it rarely goes far, and when it does it streams sequentially through memory that the hardware prefetcher has already fetched. Two sides of 8,192 levels of 8 bytes are 128 KiB, which fits in L2.

The ladder's limitation is that it covers a fixed band of prices. Real implementations either size the band to the instrument's daily price limits, or **recentre** the ladder (copy it to a new base) when the price drifts near an edge, a rare and predictable event that can be done off the critical path; levels far from the inside can be kept in a small `std::map` as an overflow. In exchange, the common case costs 12 ns instead of 45.

### SIMD

**SIMD** (single instruction, multiple data) instructions operate on vector registers holding several values: 128 bits (SSE, NEON), 256 bits (AVX2) or 512 bits (AVX-512, SVE). An AVX2 register holds eight `int32_t` or eight `float`s, and one instruction adds, compares or multiplies all eight. There are four ways to use them, in increasing order of effort.

**Let the compiler do it.** Auto-vectorisation works well on simple loops over contiguous arrays with no aliasing doubts and no early exits. Help it by using SoA layouts; by marking pointers that do not alias with `__restrict` (as the Exercise 15.1 solution does); by replacing data-dependent branches with selects; and by checking the result, with `-fopt-info-vec-missed` in GCC, `-Rpass-missed=loop-vectorize` in Clang, or by reading the assembly. Build with `-march=` set to your deployment target (for example `-march=x86-64-v3` for AVX2), or the compiler can only use SSE2.

**Use a portable SIMD library.** `std::experimental::simd` (in libstdc++ since GCC 11) and its standardised successor `std::simd` in C++26, Google's Highway, and xsimd let you write explicit vector code once and compile it for SSE, AVX and NEON:

```cpp
#include <experimental/simd>
namespace stdx = std::experimental;

long count_above(const std::int32_t* hr, std::size_t n, std::int32_t limit) {
    using V = stdx::native_simd<std::int32_t>;
    long count = 0;
    std::size_t i = 0;
    for (; i + V::size() <= n; i += V::size()) {
        V v(hr + i, stdx::element_aligned);
        count += stdx::popcount(v > limit);
    }
    for (; i < n; ++i) count += hr[i] > limit;      // tail
    return count;
}
```

**Use intrinsics** when you need a specific instruction the library does not expose. The canonical low-latency example is the group probe of a Swiss-table hash map: compare a one-byte tag against sixteen control bytes in one instruction, and turn the result into a bitmask of candidate slots:

```cpp
#include <immintrin.h>

// Return a bitmask of positions in ctrl[0..15] equal to tag.
inline unsigned match16(const std::int8_t* ctrl, std::int8_t tag) {
    const __m128i group = _mm_loadu_si128(reinterpret_cast<const __m128i*>(ctrl));
    const __m128i eq = _mm_cmpeq_epi8(group, _mm_set1_epi8(tag));
    return static_cast<unsigned>(_mm_movemask_epi8(eq));
}
```

The same pattern searches a small sorted array of price levels, or a bucket of order IDs, in a handful of instructions with no branches.

**Write assembly**, rarely, and only after the other three have failed.

Two cautions apply to SIMD in latency-sensitive code. On some Intel processors, heavy use of 512-bit instructions lowers the core's clock frequency for a while afterwards, which slows *everything* on that core, including the scalar code that follows; measure before adopting AVX-512 on a hot path. And wide vectors need wide data: if a loop processes ten elements, the setup and tail handling can cost more than the vector instructions save.

### Branches and predictability

The branchless filter above was 16 times faster, but branchless code is not a universal rule. When a branch is *predictable*, almost always taken or almost never, the predictor gets it right, the branch costs about nothing, and the branchy version is often faster because it skips work. The branchless version always does the work of both paths.

There is, however, an argument for branchless code specific to low-latency systems: **it takes the same time regardless of the data**. A branchy hot path is fast on the inputs the predictor has learned and slow on the rare input it has not, and the rare input is often the one that matters: the price move, the alarm, the unusual message. Code that does not branch on data has no such tail. The same reasoning motivates keeping hot paths free of rarely taken branches altogether: move error handling and logging out of line (`[[unlikely]]`, or a separate cold function marked `[[gnu::cold]]`), so that the common path is short, straight and compact in the instruction cache.

### Prefetching

Hardware prefetchers detect sequential and strided access and fetch lines before they are needed, which is a large part of why the SoA scan and the ladder rescan are fast. They cannot predict pointer chasing or hash lookups. When code knows an address in advance, it can issue a **software prefetch**:

```cpp
// While processing message i, start fetching the order record message i+1 needs.
__builtin_prefetch(&orders[next.order_index], /*rw=*/1, /*locality=*/3);
```

Prefetches are hints, cost an instruction, and help only if issued early enough (several hundred cycles before the use) and not so early that the line is evicted again. Batch processing creates the opportunity: when a consumer drains a batch from a ring (Chapter 8), it can prefetch the state every message in the batch will touch, then process them. Always measure: an unhelpful prefetch is a pure cost.

### Summary

- Memory moves in 64-byte lines, and a cache miss costs hundreds of instructions. Choose layouts for the access pattern, not for the noun.
- Measured: counting one field across four million records took 5.67 ns per record in an array of structs and 0.27 ns in a struct of arrays, 21 times faster, because the SoA scan reads 16 times less data and vectorises.
- Hot/cold splitting, narrower types and AoSoA blocks are the practical middle ground. Check struct sizes with `static_assert`; use indices instead of pointers in pools.
- A branchless filter over unpredictable data ran 16 times faster than a branchy one. Branchless code also takes data-independent time, which removes a source of tail latency.
- A flat price ladder updated an order book in 12 ns, against 45 ns for `std::map`.
- Use SIMD through auto-vectorisation first, then `std::simd` or a portable library, then intrinsics. Check what the compiler did.
- Software prefetching helps when the next address is known early, such as across a batch.
