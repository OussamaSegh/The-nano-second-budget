## A Detector Acquisition Pipeline {#ch19}

A PET scanner images the distribution of a radioactive tracer in the body. Each decay emits a positron, which annihilates with an electron within a millimetre or so, producing two 511 keV photons that fly off in almost exactly opposite directions. A ring of detectors surrounds the patient. When two detectors on opposite sides register a photon within a few nanoseconds of each other, the scanner records a *coincidence*: the annihilation happened somewhere on the line between them. Millions of such lines, combined by a reconstruction algorithm, become an image.

The software in the middle of this, between the detector electronics and reconstruction, is a data-acquisition (DAQ) pipeline of exactly the kind this book is about. This chapter describes what it has to do, builds a simulated version from the library, and sets out the ownership and loss rules that keep it correct. The next two chapters cover the algorithms in its two busiest stages.

### What the pipeline does

The detector is made of scintillation crystals, which turn a 511 keV photon into a flash of visible light, read by photodetectors such as silicon photomultipliers. Front-end electronics, typically ASICs and FPGAs, measure each flash's time and energy and send a digital record per detected photon. In PET terminology a detected photon is a *single*; this book calls the record a *hit*.

![A PET detector ring seen end on. The two 511 keV photons of one annihilation hit two detector blocks within the coincidence window, and the line between the blocks is the line of response.](figures/pet-ring.svg)

From there, the software does five things:

1. **Read out and decode** hit records from each detector module or readout board, checking each one.
2. **Merge** the per-source streams into one stream ordered by time (Chapter 20).
3. **Sort coincidences**: pair hits from different modules whose times are within a coincidence window (Chapter 20).
4. **Qualify and calibrate**: convert raw energies to keV with per-module calibration, and keep only pairs in which both photons are inside an energy window around 511 keV (Chapter 21).
5. **Hand off** the result for storage and reconstruction, as a list of events (*list mode*) or as histograms of counts per detector pair (*sinograms*) (Chapter 21).

A scanner's total singles rate is typically in the millions per second and can reach tens of millions in a large system, and the coincidence window is a few nanoseconds wide. Those two numbers already decide a lot: the pipeline must sustain several million hits a second with headroom for bursts, and the time order of hits matters at nanosecond resolution even though no individual stage needs nanosecond *latency*.

### Four planes

It helps to separate four kinds of traffic that share the process but should not share locks or mutable objects:

- **Data**: the hits and coincidences themselves. High rate; must never block on anything slower than itself.
- **Control**: start, stop, abort, change mode. Low rate, but must take effect predictably.
- **Configuration**: calibration tables, module maps, windows. Low rate, but must change *consistently*: no batch may be processed half with old and half with new values (Chapter 21).
- **Observability**: counters, delays, faults. Must be cheap to produce and must not perturb the data plane (Chapter 22).

### The simulated pipeline

`examples/ch19_pet_daq.cpp` simulates an 8-module ring read out by two independent sources, each serving four modules:

![The simulated acquisition pipeline in ch19_pet_daq.cpp. Each stage has one owner thread, and data moves only through bounded SPSC rings.](figures/pet-pipeline.svg)

Each simulated decay produces two photons heading for opposite modules (module *m* and *m* + 4, sometimes a neighbour of that), each detected with some probability, with a time jitter of up to a nanosecond and an energy that is either near 511 keV or lower because the photon scattered. Undetected partners leave singles behind; singles from different decays that happen to fall within the window form *random* coincidences. So the output contains trues, scatters and randoms, as a real scanner's does, and because every true pair crosses the two sources, the merge must be right for the pairs to be found at all.

The sources stand in for the hardware. Each packs 64 hits into a `WireBatch` of encoded 16-byte records and pushes it into its own SPSC ring (Chapter 8); with the batch it sends a *promise*, the earliest time any of its future hits can have, which the merger needs (Chapter 20). The sorter thread owns everything in the middle; the analysis thread owns the results.

### The wire format and the decoder

The records use the synthetic format of `include/llds/pet/hit.hpp`: a 64-bit timestamp in picoseconds, a 32-bit per-module sequence number, a 16-bit module number and a 16-bit raw energy, little-endian. The decoder follows Chapter F4's rules: check the length, build each field from bytes, validate the module number, and report *why* a record was rejected:

```cpp
enum class DecodeStatus : std::uint8_t { ok, bad_length, bad_module };

inline DecodeStatus decode_hit(std::span<const std::byte> in, std::uint16_t n_modules, Hit& out) noexcept {
    if (in.size() != kHitWireSize) return DecodeStatus::bad_length;
    Hit h;
    h.tick = detail::load_le<std::uint64_t>(in, 0);
    h.seq = detail::load_le<std::uint32_t>(in, 8);
    h.module = detail::load_le<std::uint16_t>(in, 12);
    h.energy = detail::load_le<std::uint16_t>(in, 14);
    if (h.module >= n_modules) return DecodeStatus::bad_module;
    out = h;   // written only on success
    return DecodeStatus::ok;
}
```

`out` is written only on success, so a rejected record can never be mistaken for a valid hit on module 0. The sorter adds one more check the decoder cannot make: a hit from source 0 must be on one of source 0's modules. A real format would also carry a type and version field, flags, and a checksum or CRC per packet; the hardware specification defines them.

### Ownership at each hand-off

Chapter F2 asked, at every hand-off, *who may reuse this storage, and after which observable event?* For this pipeline the answers fit in a table, and writing the table is the first design step, before any code:

| Data | Owner | Transferred by | Released by |
|---|---|---|---|
| Hits in a source's reorder buffer | the source | encoding into its current batch | – |
| A `WireBatch` in a ring slot | the ring | the source's release of `tail_` (`try_push`) | the sorter's release of `head_` (`pop_front`) |
| Decoded hits in the merger | the sorter | – | emitted in time order once below the watermark |
| Retained hits in the coincidence window | the sorter | – | retired when too old to pair (Chapter 20) |
| A `Coincidence` in the analysis ring | the ring | the sorter's `try_push` | the analysis thread's `try_pop` |
| Calibration table | shared, immutable | `CalibrationHolder::publish` | last `shared_ptr` dropped |
| Counters and histograms | the thread that updates them | – | read by `main` after `join()` |

The batch is read in place: the sorter decodes straight out of the ring slot (`front()`), and only then hands the slot back with `pop_front()`. That is the zero-copy consumer API of Chapter 8, and its correctness is exactly the reuse edge of Chapter F8: the producer cannot overwrite the slot until the release in `pop_front()`.

The last row is the one most often got wrong. The statistics are plain variables owned by one thread each, read by `main` only after joining that thread. No atomics are needed, and none are used, because `join()` provides the ordering (Chapter F5).

### Where loss may happen

The most important design decision in a DAQ pipeline is *where it is allowed to lose data*, and the answer should be "in one place, and counted". Detector hardware cannot wait: if the host does not take a batch, the front end overwrites or discards it. The simulated sources behave the same way. A full ring makes the source drop the batch and count it:

```cpp
} else if (!rings[s]->try_push(b)) {
    ++st.batches_dropped;   // hardware cannot wait: drop and count
    st.hits_dropped += b.n;
    st.hits_sent -= b.n;
}
```

Everything downstream of the sources applies backpressure instead of dropping: the sorter does not take a batch from a ring if the merger has no room for it, and it spins on a full analysis ring rather than discard a coincidence. Backpressure therefore propagates upstream until it reaches the one stage that is allowed to drop, and the loss is concentrated where it is accounted for.

Counting at the source is not enough on its own, because it trusts the source. Real front ends lose data in ways their own counters do not see. The independent check is the *sequence number*: each module numbers its hits, and a gap in the numbers seen downstream is proof of loss, wherever it happened. The sorter keeps the next expected number per module and adds up the gaps, using unsigned 32-bit arithmetic so that the count is right across the wrap from 0xffffffff to 0. Hits lost at the very end of a stream leave no gap behind them, so at shutdown the sources' final counts are compared too. Exercise 19.1 turns this into a reusable `SequenceTracker` that also recognises late and duplicate records.

### Do the books balance?

At the end of a run, the example checks a set of identities that must hold if no data was lost silently:

```text
generated = sent + dropped at source
sent      = decoded + rejected by the decoder
gaps seen downstream = dropped at source + rejected by the decoder
coincidences sorted  = coincidences analysed
```

Here is a run at the default rate of one million decays per second, with `--corrupt`, which makes the sources damage about one record in 100,000 so that the decoder has something to reject:

```text
simulated 10000000 decays in 10.00 s: 14999655 hits (1.5 M hits/s through the pipeline)
accounting: generated 14999655 = sent 14999655 + dropped at source 0 (0 batches)
            sent 14999655 = decoded 14999542 + rejected by decoder 113 (injected 113)
            sequence gaps seen downstream: 113 (dropped + rejected = 113)
sorter: 14999542 hits in, 8771288 coincidences, out-of-order 0, forced evictions 0, peak retained 11
queue delay (source push -> sorter pop): n=234371 min=237 p50=551 p90=1163263 p99=3932159 ... max=7988816 (ns)
books balance: yes
```

Every damaged record was rejected, and the sequence numbers independently accounted for each one. The queue delay, from a source's push to the sorter's pop, has a median of about half a microsecond, but its 90th percentile is above a millisecond and its maximum is 8 ms (the full output is in `sample-output/ch19_pet_daq.txt`; an earlier run on the same machine had a 90th percentile of 1.4 µs, so the tail is not stable). That tail is not the ring: it is the sorter thread being descheduled on a 4-vCPU virtual machine that is running four busy threads, exactly the effect Chapter 1 described and Chapter 17 removes with isolated cores. A pipeline that must absorb such pauses needs buffers sized for them, which is Chapter 21's subject.

In smoke mode (`--smoke`, used by `ctest`), the example also records every hit the sources sent and checks that the streaming coincidence output equals the batch oracle of Chapter 20 run over the merged input. Running it as a test means that a change that breaks the merge, the sorter or the hand-offs fails the build.

### The hardware boundary

The rings in this pipeline move data between *threads*. Between the hardware and the first thread there is a different boundary, and the techniques of this book do not carry over to it unchanged. A front end typically writes into host memory by DMA (direct memory access), into buffers the driver has set up, and signals completion with an interrupt or a status word. C++ atomics order memory accesses between threads of one program; they do not, by themselves, establish ordering, cache coherency or ownership between a device and the CPU. The rules for that are in the platform and driver documentation (on Linux, the kernel's DMA API documentation distinguishes CPU virtual addresses, physical addresses and device bus addresses, and says when cache maintenance is required).

In practice, the user-space program receives a filled buffer from the driver's API and must give it back. The questions to ask about that API are the same ownership questions as above, applied to the hardware: when has the device finished writing a buffer? Who owns it then? Does the CPU need to do anything before reading it? When may it be resubmitted, and what happens if the program holds on to it too long? A simulator cannot answer those; the driver's specification must.

### Questions for the hardware team

Before designing this pipeline for real, get answers to these, in writing:

- Record format: fields, units, byte order, versioning, integrity checks, and how a reader resynchronises after a corrupt record.
- Rates: average and peak hits per second per source, and burst durations.
- Time: counter width, unit, how it is extended, whether all sources share a clock, and the maximum disorder within and between sources.
- Loss: what the hardware does when the host is slow, whether it counts what it drops, and whether sequence numbers exist.
- Faults: how a source reports an error, and what the pipeline must do when one goes silent.
- Boundaries: which stages run in the front end, the driver, the host CPU or an accelerator, and what latency each has to meet.

### Summary

- A PET DAQ pipeline decodes hits, merges sources in time, sorts coincidences, calibrates and qualifies them, and hands them to reconstruction.
- Separate the data, control, configuration and observability planes.
- Write the ownership table before the code. Read batches in place and release them after use.
- Allow loss in exactly one place, the stage that cannot wait, and count it there. Downstream, apply backpressure.
- Detect loss independently with sequence numbers, including at the end of the stream. Make the books balance.
- C++ atomics do not cover the device boundary; the driver's DMA contract does.
