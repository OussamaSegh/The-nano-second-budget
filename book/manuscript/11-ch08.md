## The SPSC Ring Buffer {#ch08}

If you learn one data structure from this book, make it this one. A bounded single-producer single-consumer (SPSC) ring buffer is the fastest way to move data from one thread to another, it is wait-free on both sides, it needs no read-modify-write instructions at all, and it is the building block of almost every low-latency pipeline. It is also small enough that every design decision in it can be isolated and measured, which makes it the perfect place to see the principles of Chapters 2 to 4 at work.

This chapter builds the ring in five steps, from a mutex-protected `std::deque` to the version in the companion library, and measures each step's throughput and round-trip latency. Along the way we meet a result that contradicted the author's expectations, and the lesson that comes with it.

### The interface

The ring holds up to `capacity` elements. The producer calls `try_push`, which fails if the ring is full; the consumer calls `try_pop`, which fails if it is empty. Neither ever blocks. Blocking, if needed, is a policy layered on top (Chapter 9 shows how).

```cpp
template <class T>
class SpscRing {
public:
    explicit SpscRing(std::size_t capacity);
    bool try_push(const T& v);   // producer only
    bool try_pop(T& out);        // consumer only
    T* front();                  // consumer only: peek at the oldest element
    void pop_front();            // consumer only: release it
};
```

"Producer only" and "consumer only" are the whole contract. Exactly one thread may call the producer functions and exactly one (other) thread the consumer functions. That restriction is what lets the ring avoid every expensive operation, and violating it is a bug the ring cannot detect.

### The benchmark

`examples/ch08_spsc_steps.cpp` contains all five versions and measures each two ways:

- **Throughput:** the producer pushes 20 million 8-byte items as fast as it can; the consumer pops them and checks they arrive in order. Because SPSC throughput turns out to be *bimodal* (more on that later), the program runs this seven times and reports the median and the range.
- **Round-trip latency:** two rings, `ping` and `pong`. The main thread pushes an item into `ping` and waits for it to come back on `pong`; an echo thread pops from `ping` and pushes into `pong`. Each round trip is two hand-offs between cores, timed individually, two million times.

Both threads are pinned to separate cores (0 and 1 by default). Here are the final results on the reference machine, which we will build up to step by step:

```text
v1 mutex + deque              2.5 M/s (range    2.4-   2.6)  RTT p50= 2367 p99= 16255 p99.9=  38911 ns
v2 atomic, modulo, seq_cst    7.5 M/s (range    6.5-   8.3)  RTT p50=  519 p99=   743 p99.9=   7935 ns
v3 mask, acquire/release     53.1 M/s (range   45.7-  69.8)  RTT p50=  467 p99=   623 p99.9=   5503 ns
v4 + padding                 86.0 M/s (range   65.5-  99.8)  RTT p50=  491 p99=   671 p99.9=   6079 ns
v5 + cached indices         138.8 M/s (range  112.2- 160.5)  RTT p50=  475 p99=   623 p99.9=  11519 ns
```

From the first version to the last, throughput improves by a factor of 55 and median round-trip latency by a factor of 5. Let us see where each factor comes from.

### v1: a mutex and a deque

The baseline is what most people write first:

```cpp
class V1MutexDeque {
public:
    explicit V1MutexDeque(std::size_t cap) : cap_(cap) {}
    bool try_push(Item v) {
        std::lock_guard g(m_);
        if (q_.size() == cap_) return false;
        q_.push_back(v);
        return true;
    }
    bool try_pop(Item& v) {
        std::lock_guard g(m_);
        if (q_.empty()) return false;
        v = q_.front();
        q_.pop_front();
        return true;
    }
private:
    std::mutex m_;
    std::deque<Item> q_;
    std::size_t cap_;
};
```

It is correct, simple and general, and it delivers 2.5 million items a second with a 2.4 µs median round trip and a 39 µs p99.9. Every operation takes the mutex, so the mutex's cache line bounces between the two cores on every push and every pop. When the two threads collide, one of them sleeps in the kernel. And `std::deque` allocates a new block every 512 bytes of elements, which puts the allocator on the hot path.

### v2: atomic indices

The key insight of the SPSC ring is that the producer and the consumer never need to modify the same variable. The producer owns the *tail* (where the next element will be written); the consumer owns the *head* (where the next element will be read). Each reads the other's index to check for full or empty, but only one thread ever writes each index. So no lock and no RMW are needed: plain atomic loads and stores suffice.

```cpp
class V2NaiveAtomic {
public:
    explicit V2NaiveAtomic(std::size_t cap) : cap_(cap + 1), buf_(cap_) {}
    bool try_push(Item v) {
        const auto t = tail_.load();
        const auto next = (t + 1) % cap_;
        if (next == head_.load()) return false;   // full
        buf_[t] = v;
        tail_.store(next);
        return true;
    }
    bool try_pop(Item& v) {
        const auto h = head_.load();
        if (h == tail_.load()) return false;      // empty
        v = buf_[h];
        head_.store((h + 1) % cap_);
        return true;
    }
private:
    std::size_t cap_;
    std::vector<Item> buf_;
    std::atomic<std::size_t> head_{0};
    std::atomic<std::size_t> tail_{0};
};
```

The indices wrap around modulo the buffer size. One slot is always left empty so that "full" (`next == head`) can be distinguished from "empty" (`head == tail`). All operations use the default `seq_cst` order.

Is it correct? The producer writes `buf_[t]` and then stores `tail_`; the consumer loads `tail_` and then reads `buf_[h]`. That is the release-acquire publication pattern from Chapter 3 (and `seq_cst` is stronger than release-acquire), so the consumer sees the element. In the other direction, the consumer reads `buf_[h]` and then stores `head_`; the producer loads `head_` before overwriting the slot. That hands the slot back. Yes, it is correct.

It is three times faster than v1 in throughput and four times faster in median round trip. But it still leaves a lot on the table.

### v3: power-of-two masks and acquire/release

Two changes. First, every `seq_cst` store on x86 is an `xchg` instruction, a full barrier costing about 7 ns (Chapter 6). The analysis above only needs release on the stores and acquire on the loads of the *other* side's index; the thread's own index can be read relaxed. Second, `%` with a runtime divisor is an integer division, which costs 20 to 40 cycles. Restricting the capacity to a power of two turns it into a bitwise AND.

v3 also changes the index representation: the indices become free-running 64-bit counters that are never wrapped. The slot is `index & mask`, the number of elements is `tail - head`, the ring is full when `tail - head == capacity` and empty when `tail == head`. No slot is wasted, and there is no ambiguity. A 64-bit counter incremented a billion times a second wraps after 584 years.

![Free-running indices in a ring of capacity 8. The size is always write − read, the slot is the index masked by capacity − 1, and empty and full are no longer ambiguous.](figures/spsc-ring.svg)

```cpp
bool try_push(Item v) {
    const auto t = tail_.load(std::memory_order_relaxed);         // own index
    if (t - head_.load(std::memory_order_acquire) == mask_ + 1) return false;
    buf_[t & mask_] = v;
    tail_.store(t + 1, std::memory_order_release);                // publish
    return true;
}
bool try_pop(Item& v) {
    const auto h = head_.load(std::memory_order_relaxed);         // own index
    if (h == tail_.load(std::memory_order_acquire)) return false;
    v = buf_[h & mask_];
    head_.store(h + 1, std::memory_order_release);                // hand back
    return true;
}
```

Throughput jumps sevenfold, to 53 million items a second. On x86 every operation in both functions is now a plain `mov`, plus an AND.

### v4: padding

In v3, `head_` and `tail_` are declared next to each other, so they share a cache line. The producer writes `tail_` on every push and the consumer writes `head_` on every pop: classic false sharing (Chapter 2). Every push invalidates the consumer's copy of the line that holds `head_`, and every pop invalidates the producer's.

```cpp
alignas(llds::kFalseSharingRange) std::atomic<std::size_t> head_{0};
alignas(llds::kFalseSharingRange) std::atomic<std::size_t> tail_{0};
```

Throughput rises again by about 60%, to 86 million items a second. The median round trip does not change, because a round trip is dominated by the two unavoidable hand-offs of the data itself.

### v5: caching the other side's index

Look at v4's `try_push` again. On *every* push, the producer loads `head_`, a line that the consumer writes on every pop. So almost every push incurs a cache miss to fetch the consumer's latest `head_`, even though the producer only needs it when the ring might be full. The same is true of the consumer and `tail_`.

The fix is to keep a private copy of the other side's index and only re-read the shared one when the private copy says there is no room (for the producer) or no data (for the consumer). If the ring has 1,024 slots and the consumer is keeping up, the producer re-reads `head_` about once per 1,024 pushes instead of every time.

This is the version in the companion library, `include/llds/queue/spsc_ring.hpp`:

```cpp
template <class... Args>
bool try_emplace(Args&&... args) {
    const auto t = tail_.load(std::memory_order_relaxed);  // we are the only writer
    if (t - prod_.head_cache == cap_) {
        prod_.head_cache = head_.load(std::memory_order_acquire);
        if (t - prod_.head_cache == cap_) return false;  // really full
    }
    new (&slots_[t & mask_].storage) T(std::forward<Args>(args)...);
    tail_.store(t + 1, std::memory_order_release);  // publish the element
    return true;
}

T* front() noexcept {
    const auto h = head_.load(std::memory_order_relaxed);  // we are the only writer
    if (h == cons_.tail_cache) {
        cons_.tail_cache = tail_.load(std::memory_order_acquire);
        if (h == cons_.tail_cache) return nullptr;  // really empty
    }
    return std::launder(reinterpret_cast<T*>(&slots_[h & mask_].storage));
}

void pop_front() noexcept {
    const auto h = head_.load(std::memory_order_relaxed);
    std::launder(reinterpret_cast<T*>(&slots_[h & mask_].storage))->~T();
    head_.store(h + 1, std::memory_order_release);  // hand the slot back
}
```

The cached copies live on their own cache lines, next to nothing that the other thread writes:

```cpp
// Shared, written by the consumer.
alignas(kFalseSharingRange) std::atomic<std::uint64_t> head_{0};
// Shared, written by the producer.
alignas(kFalseSharingRange) std::atomic<std::uint64_t> tail_{0};

// Producer-private cache of head_ (own cache line).
struct alignas(kFalseSharingRange) ProducerState {
    std::uint64_t head_cache = 0;
} prod_;

// Consumer-private cache of tail_ (own cache line).
struct alignas(kFalseSharingRange) ConsumerState {
    std::uint64_t tail_cache = 0;
} cons_;

// Read-only after construction; may share a line with each other.
alignas(kFalseSharingRange) const std::size_t cap_;
const std::size_t mask_;
Slot* const slots_;
```

Is the cached value safe to use? The producer's cached `head_cache` is always *less than or equal to* the real `head_`, because `head_` only grows. So using the stale value can only make the producer think the ring is *fuller* than it really is, never emptier. When that happens, it re-reads the real value. The same argument holds for the consumer: a stale `tail_cache` makes the ring look emptier than it is, which is safe. Stale information that errs on the safe side is the essence of many lock-free designs.

The result: 139 million items a second, 55 times the mutex version, with the same sub-microsecond round trip.

### A result that surprised the author

The first version of v5 written for this book kept a private copy of the thread's *own* index as well (`prod_.tail` alongside `prod_.head_cache`), on the theory that reading a plain member would be cheaper than a relaxed atomic load. It measured *slower* than v4, about 55 million items a second, consistently across runs. Removing the extra copy, so that each side reads its own index with a relaxed load of the atomic, produced the 139 million above.

The exact microarchitectural cause is not obvious. A plausible explanation is that the extra private store on every operation adds a store-to-load dependency through memory on the hot path, and that maintaining two copies of the same value forces the compiler to emit more memory traffic than the single atomic does. What matters more is the lesson: **a change that "obviously" saves work can cost more than it saves.** The only defence is to measure every change in isolation, which is exactly why this chapter builds the ring one step at a time.

### Throughput is bimodal

The ranges in the results table are wide: v5 varies from 112 to 161 million items a second between runs, and on some machines the spread is much larger. That is not just measurement noise. SPSC throughput has two stable regimes:

- **Near empty.** The consumer is slightly faster than the producer, so it drains the ring and keeps finding it empty. Every element is then handed over individually: the consumer reloads `tail_` for each one and pulls the slot's cache line across from the producer while the producer is still writing neighbouring slots in the same line. Throughput is limited by cross-core latency.
- **Near full.** The producer gets ahead and the ring fills. Now the consumer finds many elements available each time it reloads `tail_`, reads whole cache lines of slots that the producer has finished with, and the producer rarely needs to reload `head_`. Hand-offs are amortised over many elements. Throughput is limited by memory bandwidth and instruction count.

Which regime a run settles into depends on small timing differences at start-up, and a run can flip between them. That is why the benchmark reports a median and a range rather than a single number, and why you should be suspicious of any SPSC benchmark that reports one number from one run.

Batching makes the near-empty regime less painful: if the consumer pops several elements per reload of `tail_` and the producer publishes `tail_` once per batch, each cross-core transfer carries more data. Exercise 8.1 asks you to implement exactly this.

### Round-trip latency and what limits it

The round-trip median barely changed from v2 to v5: about 470 to 520 ns for two hand-offs, so roughly 240 ns per one-way hand-off on this virtual machine (on bare-metal desktop and server parts, 60 to 150 ns is typical). The throughput optimisations did not help, because latency is limited by something the ring cannot avoid: the element itself must travel from the producer's core to the consumer's core. The producer writes the slot (taking its cache line in Modified state), then writes `tail_`. The consumer, spinning on `tail_`, sees the change only once the line holding `tail_` has been transferred, and then must transfer the slot's line too. That is two cache-line transfers per hand-off, and no software change can remove them.

What software *can* do is avoid adding to them. Every extra shared line touched per operation adds a transfer; every `seq_cst` store adds a fence; every allocation adds the allocator's latency. v5 touches the minimum: one slot line and one index line per hand-off.

The p99.9 values (5 to 12 µs) are, as in Chapter 1, the virtual machine's interference, not the ring's. On a machine with isolated cores (Chapter 17) the p99.9 of the same round trip is typically within a few hundred nanoseconds of the median.

### Details that matter in production

**Element construction.** The library ring stores elements in raw, suitably aligned storage and constructs them with placement `new`, so `T` need not be default-constructible, and destroys them when popped. `std::launder` is required by the standard when accessing an object created by placement `new` in storage obtained through a pointer to a different type. The destructor drains any remaining elements so that non-trivial types do not leak.

**Zero-copy consumption.** `front()` and `pop_front()` let the consumer process an element in place and release the slot afterwards, which avoids a copy for large elements. The producer can do the same with `try_emplace`, constructing the element directly in the slot.

**Element size.** For small elements (8 to 16 bytes) several share a cache line, which helps throughput in the near-full regime and hurts slightly in the near-empty one. For latency-critical rings carrying small messages, some designs pad each slot to a full cache line so that the producer and consumer never touch the same slot line at the same time. Measure both for your workload.

**Capacity.** A larger ring absorbs bursts, but a full large ring is a long wait (Little's law, Chapter 1) and a large working set (Chapter 2). Choose the smallest capacity that absorbs your expected bursts; for many pipelines that is a few hundred to a few thousand elements.

**Full and empty policies.** `try_push` failing is information. In a market-data feed, a full ring usually means the consumer is overloaded, and the right response may be to drop and count, not to spin. In the patient-monitoring pipeline of Chapter 18, dropping a sample is unacceptable, so the ring is sized so that it can never fill under the specified load, and filling it is treated as a fault.

**Waiting.** Both `try_` functions return immediately. A consumer with nothing to do can spin (lowest latency, burns a core), spin with `cpu_relax()` (same latency, less power, kinder to a hyper-thread sibling), yield, or sleep. Chapter 9 builds a spin-then-sleep wait strategy and Chapter 17 measures what each choice does to the tail.

### Correctness argument, in full

It is worth writing out why the final ring is correct, because the same structure of argument applies to every lock-free structure in this book.

1. *Single writer per variable.* `tail_` is written only by the producer, `head_` only by the consumer, `prod_` only by the producer, `cons_` only by the consumer. No variable has two writers, so no RMW is needed.
2. *Publication.* The producer constructs the element in slot `t & mask` and then stores `tail_ = t + 1` with release. The consumer loads `tail_` with acquire and only accesses slots below the value it read. By release-acquire, the element's construction happens before the consumer's access.
3. *Reclamation of slots.* The consumer destroys the element in slot `h & mask` and then stores `head_ = h + 1` with release. The producer loads `head_` with acquire before deciding a slot is free. So the destruction happens before the producer's reuse of the slot.
4. *Stale caches err safely.* `head_cache <= head_` and `tail_cache <= tail_` at all times, so cached values can only cause a spurious "full" or "empty", which triggers a re-read.
5. *No ABA.* Indices are 64-bit and monotonic; they never repeat.

ThreadSanitizer agrees: the test suite, run under `-DLLDS_SANITIZE=thread`, reports no races for the ring, and does report a race for the deliberately broken ring in Chapter 16.

### Summary

- The SPSC ring is wait-free on both sides and uses no RMW instructions: each index has exactly one writer.
- Five steps, each measured on the reference machine: mutex + deque 2.5 M items/s; atomic indices 7.5 M/s; power-of-two masks and acquire/release 53 M/s; padding 86 M/s; cached remote indices 139 M/s.
- Round-trip latency (two hand-offs) is about 475 ns on the reference VM and is limited by cache-line transfers that no software change can remove.
- A plausible "optimisation" (a private copy of the thread's own index) made the ring slower. Measure each change in isolation.
- SPSC throughput is bimodal (near-empty versus near-full). Report medians and ranges over several runs.
- Stale cached indices are safe because they can only make the ring look fuller or emptier than it is.
