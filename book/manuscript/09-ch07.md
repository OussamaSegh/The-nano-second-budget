## Readers, Writers and Sequence Locks {#ch07}

A large class of shared data is read far more often than it is written. A configuration record, a routing table, the latest market price, the fused state of a patient's vital signs, the current pose of a robot arm: one thread updates it occasionally, many threads read it constantly. Locks handle this badly, because a lock makes readers *write* (the lock word), and Chapter 2 showed that writes to a shared line serialise. This chapter looks at the two classic answers, reader-writer locks and sequence locks, measures them, and builds a sequence lock that is correct under the C++ memory model, which turns out to be harder than it looks.

### The problem with reader-writer locks

A reader-writer lock (`std::shared_mutex`, `pthread_rwlock_t`) allows many readers at once or one writer. It sounds like exactly the right tool. But to know when a writer may enter, the lock must count its readers, so every `lock_shared` and `unlock_shared` is an atomic RMW on the lock's counter. With many readers on many cores, that counter's cache line bounces between them as violently as any contended counter in Chapter 6. Readers do not block each other logically, but they block each other physically.

On top of that, `std::shared_mutex` on Linux is a `pthread_rwlock_t`, a fairly heavyweight object with a sleeping slow path, and its writers can be starved or can starve readers depending on the policy.

### Measuring the alternatives

`examples/ch07_seqlock.cpp` sets up the scenario this chapter is about. One writer updates a 48-byte vital-signs record 100,000 times a second (paced, one update every 10 µs):

```cpp
struct Vitals {
    std::uint64_t timestamp_ns;
    std::int32_t heart_rate_bpm;
    std::int32_t spo2_permille;
    std::int32_t resp_rate_bpm;
    std::int32_t systolic_mmhg;
    std::int32_t diastolic_mmhg;
    std::int32_t temperature_mc;  // milli-degrees Celsius
    std::uint64_t sequence;       // == timestamp_ns in this test: lets us detect tearing
    std::uint64_t checksum;
};
```

R reader threads read the record in a tight loop and check that each copy they get is internally consistent. The record is shared three ways: behind a `std::mutex`, behind a `std::shared_mutex`, and in a `SeqLock`. The program reports total reads per second, how many torn (inconsistent) reads were seen, and the writer's own latency per update. Results on the reference machine:

```text
std::mutex     R=1  reads    46.60 M/s  torn=0  write p50=  591 p99=  1759 ns
shared_mutex   R=1  reads     1.12 M/s  torn=0  write p50=21503 p99= 45055 ns
SeqLock        R=1  reads   105.93 M/s  torn=0  write p50=   92 p99=   137 ns

std::mutex     R=3  reads    21.02 M/s  torn=0  write p50=  687 p99= 20223 ns
shared_mutex   R=3  reads    11.59 M/s  torn=0  write p50=38911 p99= 87039 ns
SeqLock        R=3  reads   212.90 M/s  torn=0  write p50=   64 p99=   195 ns
```

![Readers and the writer of a 48-byte record. The seqlock reads ten to twenty times faster than a mutex, and its writer's p99 is a hundred times lower.](figures/chart-seqlock.svg)

Three observations:

- **Readers.** With three readers, the mutex delivers 21 million reads a second in total, the reader-writer lock 12 million, and the sequence lock 213 million: ten to twenty times more. And while mutex throughput *fell* as readers were added, seqlock throughput *doubled*.
- **The writer.** This is the more important number for a low-latency system. Under the mutex, the writer's p99 is 20 µs, because it has to wait for readers to get out of the way. Under `shared_mutex` it is worse still: a median of 39 µs and a p99 of 87 µs, because the lock gives readers precedence and the writer has to wait for a gap in a continuous stream of them. Under the seqlock, the writer's p99 is 195 ns, the cost of writing 48 bytes and two counter updates. Readers cannot slow the writer down at all.
- **`shared_mutex` is the worst of the three.** That surprises many people. It is the right tool when critical sections are long (milliseconds) and readers are few. For short critical sections, its bookkeeping costs more than the exclusion it buys.

The seqlock's advantages come from a single property: **readers never write shared memory.** The rest of this chapter explains how that is possible.

### How a sequence lock works

A sequence lock (seqlock) pairs the protected data with a sequence counter. The rules are:

- The **writer** increments the counter (making it odd), writes the data, and increments the counter again (making it even).
- A **reader** reads the counter. If it is odd, a write is in progress; try again. Otherwise read the data, then read the counter again. If the two counter values are equal, no write overlapped the read and the copy is consistent. If not, discard the copy and try again.

The writer never waits for readers. Readers never block the writer or each other. A reader may have to retry if it overlaps a write, but writes are short and, in this scenario, infrequent, so retries are rare. The Linux kernel uses seqlocks for exactly this kind of data: the current time in the vDSO (which is why `clock_gettime` is so cheap) is protected by one.

There is one hard constraint: **a seqlock supports one writer** (or several writers serialised by a separate lock), and **the data must be safe to copy while it is being modified.** You cannot put a `std::string` in a seqlock, because a reader copying it mid-update might follow a half-written pointer. Plain data only: integers, floats, fixed-size arrays, trivially copyable structs.

![The sequence counter over time. Reader 1 sees the same even value before and after its reads and succeeds. Reader 2 overlaps a write, sees the counter change and retries.](figures/seqlock.svg)

### The obvious implementation is wrong

Here is how seqlocks are usually written, and how they are written in C:

```cpp
// WRONG in C++: has a data race
struct NaiveSeqLock {
    std::atomic<unsigned> seq{0};
    Vitals data;  // plain

    void store(const Vitals& v) {
        seq.store(seq.load() + 1);
        data = v;
        seq.store(seq.load() + 1);
    }
    Vitals load() {
        for (;;) {
            unsigned s1 = seq.load();
            if (s1 & 1) continue;
            Vitals copy = data;          // races with the writer
            if (seq.load() == s1) return copy;
        }
    }
};
```

The reader's `copy = data` can execute while the writer is writing `data`. That is a data race on a non-atomic object, which (Chapter 3) is undefined behaviour, even though the program throws the torn copy away afterwards. In practice compilers usually generate the code you expect, and the bug is latent. But a compiler is allowed to assume no data race occurs and, for example, to move the read of `data` after the second `seq.load()`, or to read `data` twice. And ThreadSanitizer will (correctly) report it.

Hans Boehm's 2012 paper *Can Seqlocks Get Along With Programming Language Memory Models?* works through this problem in detail. The resolution is to make the data accesses themselves atomic, but relaxed, and to use fences to order them against the sequence counter. Relaxed atomic loads and stores of a machine word compile to plain `mov` instructions on x86 and plain `ldr`/`str` on ARM, so this costs nothing at run time; it just tells the compiler the truth.

### A correct seqlock in C++

`include/llds/sync/seqlock.hpp` stores the payload as an array of relaxed atomic 64-bit words and copies the payload in and out with `memcpy`:

```cpp
template <class T>
class SeqLock {
    static_assert(std::is_trivially_copyable_v<T>, "SeqLock payload must be trivially copyable");
    static constexpr std::size_t kWords = (sizeof(T) + 7) / 8;

public:
    // Single writer only. Use a mutex around store() if you have several.
    void store(const T& value) noexcept {
        std::array<std::uint64_t, kWords> buf{};
        std::memcpy(buf.data(), &value, sizeof(T));
        const auto s = seq_.load(std::memory_order_relaxed);
        seq_.store(s + 1, std::memory_order_relaxed);         // odd: write in progress
        std::atomic_thread_fence(std::memory_order_release);  // keep data stores after it
        for (std::size_t i = 0; i < kWords; ++i)
            data_[i].store(buf[i], std::memory_order_relaxed);
        seq_.store(s + 2, std::memory_order_release);         // even: done
    }

    T load() const noexcept {
        std::array<std::uint64_t, kWords> buf;
        for (;;) {
            const auto s1 = seq_.load(std::memory_order_acquire);
            if (s1 & 1) {  // writer active
                cpu_relax();
                continue;
            }
            for (std::size_t i = 0; i < kWords; ++i)
                buf[i] = data_[i].load(std::memory_order_relaxed);
            std::atomic_thread_fence(std::memory_order_acquire);  // keep data loads before s2
            const auto s2 = seq_.load(std::memory_order_relaxed);
            if (s1 == s2) break;
        }
        T out;
        std::memcpy(&out, buf.data(), sizeof(T));
        return out;
    }

private:
    alignas(kCacheLine) std::atomic<std::uint64_t> seq_{0};
    std::array<std::atomic<std::uint64_t>, kWords> data_{};
};
```

Every memory order here is load-bearing. Let us go through them.

**Writer, first counter store (relaxed) plus release fence.** The data stores must not become visible *before* the counter turns odd; otherwise a reader could read half-new data and see an even counter on both sides. A release *store* would not help, because release only orders earlier operations before the store, and the data stores come *after* it. A release *fence* followed by stores is what we need: the C++ rules say that if a reader's acquire operation observes any of the data stores, it also observes everything before the fence, including the odd counter value. (On x86 this fence compiles to nothing, since stores are never reordered with each other; it only restrains the compiler.)

**Writer, second counter store (release).** The data stores must be visible before the counter turns even again. A release store orders every earlier write before it. This is the ordinary publication pattern.

**Reader, first counter load (acquire).** Pairs with the writer's final release store: if the reader sees even value *s*, it sees all the data written before the counter reached *s*. It also stops the data loads from moving above it.

**Reader, acquire fence before the second counter load.** The data loads must complete before the second counter load; otherwise the reader could check the counter, find it unchanged, and only then read data that a new write has since modified. An acquire *load* of the counter would not express this (acquire orders *later* operations), so we use an acquire fence after the data loads. Combined with the writer's release fence, it guarantees: if any data load saw a value written by a write that started after `s1`, then the second counter load sees at least that write's odd value, so `s1 != s2` and the copy is discarded.

**Reader, second counter load (relaxed).** The fence before it does the ordering work.

The final `memcpy` from the local buffer into a `T` happens only after a consistent copy has been obtained, on purely local data, so it is safe.

This version is correct, race-free, and (on x86) compiles to exactly the same instructions as the naive one, apart from `mov` instructions the compiler can no longer merge or reorder. The tests in `tests/test_locks.cpp` run three readers against a writer storing 100,000 updates and verify that no reader ever sees a torn value.

### Variations

**`try_load`.** A reader with a deadline may prefer to fail rather than retry. `SeqLock::try_load(T&)` makes a single attempt and returns false if a write overlapped it.

**Version numbers.** The counter divided by two is the number of completed writes. Readers can use it to detect whether anything changed since their last read without copying the data (`version()` in the library).

**Readers depend on the writer finishing.** Readers never block each other, but they are not lock-free with respect to the writer. If the writer is preempted, page-faults or is stopped in a debugger between its two counter increments, the counter stays odd and every reader spins until the writer runs again; `try_load` with a retry budget is how a reader with a deadline protects itself. On a real-time system, give the writer at least the priority of its most urgent reader, or keep the write so short that it cannot be preempted in practice (on Linux, a `SCHED_FIFO` writer on an isolated core). And if the writer updates continuously, a reader can keep overlapping writes and retry forever even though the writer never stalls. In practice writers are rate-limited (our test writes every 10 µs and each write takes under 100 ns), so the probability of a retry is under 1%. If writes are very frequent, use double buffering instead: keep two copies, write the inactive one, then flip an index.

**Large payloads.** The seqlock copies the whole payload on every read. For a few cache lines this is the fastest possible design. For kilobytes of data it is wasteful, and RCU (Chapter 12), which hands readers a pointer to an immutable snapshot, is better.

**Several writers.** Put a mutex (or a spinlock) around `store()`. The writers then serialise among themselves, and readers are still unaffected.

### Where seqlocks fit

Seqlocks are ideal when:

- one thread produces snapshots of a small, plain-data state;
- many threads want the *latest* snapshot, not every snapshot (a reader that misses intermediate updates is fine);
- the writer must never be delayed by readers.

That describes a market-data top of book (Chapter 14 publishes one), a robot's current joint angles, a game's latest input state, a sensor-fusion output, or the vital-signs display in Chapter 18. It does not describe a queue of messages that must all be processed; that is what Part III is for.

### Summary

- Read-mostly data is common; locks handle it badly because readers write the lock word.
- `std::shared_mutex` was the slowest option measured, for both readers and the writer.
- A seqlock lets readers proceed without writing shared memory and lets the writer proceed without waiting. Measured: ten to twenty times the read throughput of a mutex, and a writer p99 of 195 ns against 20 µs.
- The textbook seqlock has a data race in C++. Store the payload in relaxed atomics, and use a release fence in the writer and an acquire fence in the reader.
- Seqlocks need trivially copyable data and a single (or serialised) writer, and deliver the latest snapshot, not every snapshot.
