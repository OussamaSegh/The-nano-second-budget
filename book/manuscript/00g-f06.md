## Mutexes, Condition Variables and a Queue That Can Stop {#f06}

A mutex is the simplest correct way to share mutable state, and in a surprising number of low-latency systems it is also fast enough. This chapter covers what a mutex protects, how to wait for a condition without spinning, and how to design a queue with a clear *close* contract, so that a pipeline can shut down without losing data or hanging. Chapter 5 continues the story with how locks are built and what they cost.

### What a mutex protects

A mutex lets at most one thread at a time run the code between `lock()` and `unlock()`, the *critical section*. Always lock with an RAII guard:

```cpp
std::mutex m;
std::uint64_t total = 0;      // protected by m

void add(std::uint64_t x) {
    std::lock_guard lock(m);
    total += x;
}
```

The rule that makes this correct is that **every** access to `total`, reads included, happens with `m` held. Locking the writes and letting reads skip the lock is still a data race.

A mutex protects *relationships*, not just variables. Suppose three counters must always satisfy `accepted + rejected == received`. Making each counter atomic removes the races on the individual counters, but a reader can still see `received` already incremented and `accepted` not yet, a state that violates the relationship. If the relationship must hold in every observation, all three must be updated and read under one lock, or published together as one immutable snapshot (Chapter 12), or read only when the system is quiet (at shutdown, for example). Write the protected invariant down next to the mutex. If you cannot state it in a sentence or two, the design probably needs clearer ownership before it needs faster synchronisation.

Two more rules. **Check and act under the same lock.** Testing "the queue is not empty" without the lock and then popping with it fails when another thread takes the last item in between. **Avoid deadlock** by acquiring multiple locks in one documented order, or with `std::scoped_lock lock(a, b);`, which acquires both without deadlocking. Never call unknown code (a user callback, a logger) while holding a lock: it may try to take another lock, or yours.

Is a mutex too slow for low-latency code? An uncontended lock and unlock costs a few tens of nanoseconds (about 15 to 25 ns; Chapter 5 measures about 30 ns per acquisition on the reference machine, of which about 18 ns is the cost of the timer itself). Under contention, and especially when the holder is descheduled, waiting times grow by orders of magnitude, and that, not the average cost, is why later chapters avoid locks on critical paths. Start with a mutex, measure, and replace it only where the measurements say so.

### Waiting for a condition

A consumer that has nothing to do should sleep, not spin. A `std::condition_variable` lets a thread sleep until another thread says that something *may* have changed:

```cpp
std::unique_lock lock(m);
not_empty.wait(lock, [&] { return closed || !queue.empty(); });
// here: m is held and the predicate is true
```

`wait` atomically releases the mutex and sleeps; before it returns it re-acquires the mutex and re-checks the predicate. That re-check matters for two reasons. Condition variables can wake up *spuriously*, without any notification. And another thread may have been woken too and taken the item first. Always wait with a predicate. `std::unique_lock` rather than `lock_guard` is needed because `wait` must unlock and relock.

**A notification is not stored work.** `notify_one()` wakes a waiting thread if there is one; if there is none, the notification is lost. The durable facts, the queue contents and the closed flag, live in ordinary variables protected by the mutex, and the predicate reads them. That is why a consumer that starts waiting after the producer has already notified still sees the item.

### A queue with a close contract

Here is the specification before the code, because the specification is where shutdown bugs are prevented:

- `push(v)` blocks while the queue is full. It returns `false`, without enqueuing, if the queue is closed, including when it was closed while the producer was blocked.
- `pop()` blocks while the queue is empty and open. It returns the oldest item, or "nothing" **only when the queue is closed and empty**. This separates a temporary "nothing yet" from a permanent "no more, ever".
- `close()` is idempotent and wakes **all** waiters on **both** sides. Items pushed before the close are still delivered: closing drains, it does not discard.

```cpp
template <class T>
class ClosableQueue {
public:
    bool push(T v) {
        std::unique_lock lock(m_);
        not_full_.wait(lock, [&] { return closed_ || q_.size() < cap_; });
        if (closed_) return false;
        q_.push_back(std::move(v));
        lock.unlock();
        not_empty_.notify_one();
        return true;
    }
    std::optional<T> pop() {
        std::unique_lock lock(m_);
        not_empty_.wait(lock, [&] { return closed_ || !q_.empty(); });
        if (q_.empty()) return std::nullopt;   // closed and drained
        std::optional<T> v(std::move(q_.front()));
        q_.pop_front();
        lock.unlock();
        not_full_.notify_one();
        return v;
    }
    void close() {
        { std::lock_guard lock(m_); closed_ = true; }
        not_empty_.notify_all();
        not_full_.notify_all();
    }
    // members: m_, not_empty_, not_full_, q_ (std::deque<T>), cap_, closed_ = false
};
```

Each detail of `close` is there because leaving it out causes a hang. Notifying only consumers leaves a producer blocked on a full queue forever. `notify_one` instead of `notify_all` wakes one waiter and leaves the others asleep, even though closure makes all their predicates true. Setting `closed_` without holding the mutex would race with the waiters' predicate checks. The notifications are made after releasing the lock, which avoids waking a thread only for it to block immediately on the mutex; correctness comes from changing the state under the lock, not from where the notification happens.

Two limits are worth saying out loud. The queue bounds the *number* of items, but `std::deque` may still allocate as it grows, so it is a correctness baseline, not an allocation-free component; the SPSC ring of Chapter F8 and Chapter 8 is. And `close()` does not stop or join anyone. The owner must close the queue, then join every thread that uses it, then destroy it, and that order should be visible in the code.

### Shutting down a pipeline

With this queue, a producer-consumer pipeline has a clean lifecycle:

```cpp
ClosableQueue<Hit> q(32);
std::vector<Hit> received;
std::thread consumer([&] { while (auto h = q.pop()) received.push_back(*h); });
std::thread producer([&] {
    for (const Hit& h : source) if (!q.push(h)) break;
    q.close();          // always, even if nothing was pushed
});
producer.join();
consumer.join();        // returns once the queue is closed *and* drained
// received is complete; reading it here is safe after the join
```

The producer must close the queue even when it produced nothing; otherwise the consumer waits forever on an empty, open queue. If the producer can throw, catch the exception inside the thread, store it in a `std::exception_ptr`, close the queue, and rethrow it after the join: an exception that escapes a thread function terminates the whole program. *Draining* (stop accepting, finish what was accepted) and *aborting* (stop now, report what was discarded) are different promises; Chapter 22 adds the second.

### Summary

- Every access to protected state, reads included, must hold the same mutex. Protect relationships, not just variables.
- Check and act under one lock. Take multiple locks in one order; never call unknown code while holding one.
- Always wait on a condition variable with a predicate. Notifications are not stored; state is.
- A closeable queue returns "nothing" only when closed and empty, and `close()` wakes everyone on both sides.
- Shutdown order: close, join, destroy.
