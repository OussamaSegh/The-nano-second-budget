## Locks Done Right {#ch05}

A book about lock-free data structures starts its building blocks with locks for a simple reason: locks are the baseline every other design must beat, and they beat lock-free designs more often than their reputation suggests. A well-chosen lock, held briefly, with no contention, costs about as much as a single atomic operation. The trouble starts under contention and under preemption, and understanding exactly how it starts is the best way to understand why the lock-free structures in later chapters are shaped the way they are.

This chapter looks inside `std::mutex`, builds five spinlocks of increasing sophistication, measures all of them under contention, and covers the failure modes that matter for latency: convoys, unfairness, priority inversion and lock-holder preemption.

### What a mutex costs

On Linux, `std::mutex` is a thin wrapper around a `pthread_mutex_t`, which in glibc is built on a **futex** (fast user-space mutex). The design is clever. The lock is an integer in user memory. Locking an uncontended mutex is a single atomic compare-and-swap from 0 to 1, done entirely in user space. Unlocking it is a single atomic exchange back to 0. Only when a thread finds the lock already held does it make a `futex(FUTEX_WAIT)` system call to sleep in the kernel, and only when the unlocking thread sees that someone is waiting does it make a `futex(FUTEX_WAKE)` call to wake them.

So an uncontended `std::mutex` lock-unlock pair costs two atomic RMW operations, about 15 to 25 ns. Contended, it costs a system call to sleep (several hundred nanoseconds), a context switch away and back (microseconds), and a wake-up by the unlocker (another system call). On a busy machine, the woken thread may also wait for the scheduler to give it a core. That is the gap between the two halves of the table in Chapter 1, and it is the reason latency-critical code avoids *blocking* on contended locks, even when it uses locks.

glibc's mutex does a small amount of adaptive spinning before sleeping only if you ask for `PTHREAD_MUTEX_ADAPTIVE_NP`; `std::mutex` uses the default type, which goes to the kernel almost immediately.

### Spinlocks

A **spinlock** never sleeps: a thread that finds it held keeps retrying until it is free. Spinning wastes CPU time, but it reacts within nanoseconds when the lock is released, and it never involves the scheduler. It is the right tool when critical sections are short (tens to hundreds of nanoseconds), when each contending thread has its own core, and when wake-up latency is unacceptable. It is the wrong tool when the lock holder can be preempted, because then the spinners burn their whole time slice waiting for a thread that is not running.

All five spinlocks below are in `include/llds/sync/spinlock.hpp`. They all satisfy the `BasicLockable` requirements (`lock()` and `unlock()`), so they work with `std::lock_guard` and `std::scoped_lock`.

#### 1. Test-and-set

The simplest possible spinlock is one atomic flag and an exchange:

```cpp
class TasLock {
public:
    void lock() noexcept {
        while (flag_.exchange(true, std::memory_order_acquire)) cpu_relax();
    }
    bool try_lock() noexcept { return !flag_.exchange(true, std::memory_order_acquire); }
    void unlock() noexcept { flag_.store(false, std::memory_order_release); }
private:
    std::atomic<bool> flag_{false};
};
```

`exchange(true)` atomically sets the flag and returns the old value: if it was false, we now own the lock. The acquire order on the exchange and the release order on the store make the critical section behave as you expect: everything the previous holder wrote before unlocking is visible to the next holder after locking (Chapter 3, rule 2).

`cpu_relax()` is the x86 `pause` instruction (or `yield` on ARM). It tells the core that this is a spin-wait loop. On x86 it prevents the core from speculatively issuing a flood of loads to the contended line, which would cause a costly pipeline flush (a "memory order machine clear") when the line changes, and it saves power. On Intel cores since Skylake, `pause` takes about 140 cycles; on earlier cores, about 10. That difference changes the tuning of every spin loop, which is one reason to measure on the hardware you deploy to.

The problem with test-and-set is that *every* spin iteration is an atomic read-modify-write, and an RMW requires the cache line in exclusive state. With several waiters, the line bounces between their caches continuously, even though none of them can possibly acquire the lock while it is held. The lock holder, when it tries to release the lock, has to win the line back from the spinners.

#### 2. Test-and-test-and-set

The fix is to spin on a plain load, which only needs the line in Shared state and therefore causes no traffic while the lock is held, and only attempt the exchange when the lock looks free:

```cpp
void lock() noexcept {
    for (;;) {
        if (!flag_.exchange(true, std::memory_order_acquire)) return;
        while (flag_.load(std::memory_order_relaxed)) cpu_relax();
    }
}
```

Now waiters sit quietly with a shared copy of the line. When the holder releases, it invalidates their copies; they all see the flag false and all try the exchange at once. One wins; the others go back to spinning on loads. The thundering herd at release time is the remaining weakness.

#### 3. Backoff

Exponential backoff spreads the herd out: after a failed attempt, wait a little; after another, wait twice as long; up to a limit.

```cpp
class Backoff {
public:
    void pause() noexcept {
        for (unsigned i = 0; i < spins_; ++i) cpu_relax();
        if (spins_ < max_) spins_ <<= 1;
        else std::this_thread::yield();
    }
    // ...
};

void BackoffLock::lock() noexcept {
    Backoff backoff;
    for (;;) {
        if (!flag_.load(std::memory_order_relaxed) &&
            !flag_.exchange(true, std::memory_order_acquire))
            return;
        backoff.pause();
    }
}
```

Backoff dramatically improves throughput under contention. It also makes the lock *unfair*: a thread that just released the lock and immediately asks for it again usually wins, because its competitors are all in the middle of a backoff pause. Unfairness is good for throughput (the lock and its data stay in one core's cache) and bad for tail latency (an unlucky waiter can lose many times in a row).

#### 4. Ticket lock

A ticket lock is fair: threads acquire it in the order they asked for it, like customers taking a numbered ticket at a counter.

```cpp
class TicketLock {
public:
    void lock() noexcept {
        const auto my = next_.fetch_add(1, std::memory_order_relaxed);
        for (;;) {
            const auto cur = serving_.load(std::memory_order_acquire);
            if (cur == my) return;
            for (std::uint32_t i = 0; i < (my - cur) * 32; ++i) cpu_relax();
        }
    }
    void unlock() noexcept {
        serving_.store(serving_.load(std::memory_order_relaxed) + 1, std::memory_order_release);
    }
private:
    alignas(kCacheLine) std::atomic<std::uint32_t> next_{0};
    alignas(kCacheLine) std::atomic<std::uint32_t> serving_{0};
};
```

Each thread takes a ticket with one `fetch_add` and then waits until `serving_` reaches it. Because a waiter knows its position in the queue (`my - cur`), it can back off proportionally. `unlock` needs no RMW: only the holder writes `serving_`, so a load and a release store suffice. The two counters are on separate cache lines so that ticket-takers do not disturb the line waiters are spinning on.

Fairness has a price that will show up clearly in the measurements: every hand-off must go to the *next* thread in line, which is usually on another core, and if that thread happens to be descheduled, everyone behind it waits too.

#### 5. MCS lock

All of the locks so far have one thing in common: every waiter spins on the same cache line. When the lock is released, that line must be invalidated in every waiter's cache. On a machine with dozens of cores, especially across sockets, that broadcast is expensive. The **MCS lock** (after its inventors, Mellor-Crummey and Scott) solves this by giving each waiter its own line to spin on. Waiters form a linked queue; each spins on a flag in its own queue node; the holder hands the lock to its successor by writing the successor's flag, which touches exactly one remote cache line.

```cpp
class McsLock {
public:
    struct alignas(kCacheLine) Node {
        std::atomic<Node*> next{nullptr};
        std::atomic<bool> locked{false};
    };

    void lock(Node& me) noexcept {
        me.next.store(nullptr, std::memory_order_relaxed);
        me.locked.store(true, std::memory_order_relaxed);
        Node* prev = tail_.exchange(&me, std::memory_order_acq_rel);
        if (prev) {
            prev->next.store(&me, std::memory_order_release);
            while (me.locked.load(std::memory_order_acquire)) cpu_relax();
        }
    }

    void unlock(Node& me) noexcept {
        Node* succ = me.next.load(std::memory_order_acquire);
        if (!succ) {
            Node* expected = &me;
            if (tail_.compare_exchange_strong(expected, nullptr, std::memory_order_acq_rel,
                                              std::memory_order_relaxed))
                return;  // no one was waiting
            // A successor swapped itself into tail_ but has not linked yet.
            while (!(succ = me.next.load(std::memory_order_acquire))) cpu_relax();
        }
        succ->locked.store(false, std::memory_order_release);
    }
private:
    alignas(kCacheLine) std::atomic<Node*> tail_{nullptr};
};
```

To lock, a thread swaps its own node into `tail_`. If there was a previous tail, the lock is held: link ourselves behind the previous node and spin on our own `locked` flag. To unlock, if we have a successor, clear its flag. If not, try to swing `tail_` back to null; if that fails, a new waiter is in the middle of enqueuing itself, so wait for it to link in and then hand over.

The subtle part is the window in `unlock` between a new waiter's `exchange` on `tail_` and its store to `prev->next`. During that window the unlocker sees no successor, but `tail_` is no longer its own node. The CAS detects exactly this case. Reasoning about such windows, where a multi-step operation by one thread is observed half-done by another, is the core skill of lock-free programming, and you will see it again in every structure in Part III.

The MCS lock needs a queue node per acquisition, which must outlive the critical section, so its interface takes a `Node&`. `McsLock::Guard` puts the node on the stack. The Linux kernel's `qspinlock` is a compact MCS variant that packs the queue into a 32-bit word.

(The acquisition latencies include about 18 ns of `rdtsc` overhead, which is why the uncontended figures are around 30 ns rather than 10.)

Several lessons are visible in these numbers.

**Uncontended, they are all the same.** With one thread, every lock costs about one atomic RMW per acquire, and the differences are noise. `std::mutex` is a perfectly good lock when nobody contends for it.

**Contention collapses throughput, and fairness collapses it further.** With two threads, throughput drops by a factor of two to ten for every lock except backoff. The ticket lock is the slowest of all: 1.9 million acquisitions per second, against 17 million for backoff. A fair lock must hand over to the other thread on every release, so the lock and the shared counter cross between cores on every single acquisition. The unfair backoff lock lets one thread re-acquire many times in a row while the other is backing off, so the line stays put.

**Throughput and latency disagree.** The backoff lock wins on throughput, but look at its tail at T = 4: a p99.9 of 57 µs. Some unlucky acquisitions waited through many backoff rounds while others repeatedly re-acquired. The MCS lock has a much worse median (727 ns, because every acquisition is a hand-off) but the best p99.9 of the spinlocks (18 µs). Which is "faster" depends entirely on whether you care about throughput or the tail.

**The maximums are scheduler artefacts.** All of the locks show maximum acquisition times of hundreds of microseconds to milliseconds (not shown above). With four spinning threads on four vCPUs, the hypervisor or the kernel occasionally preempts a lock holder, and every spinner then waits for it to be rescheduled. This is the most important failure mode of spinlocks, and it gets its own section below.

**On a bigger machine, the picture changes.** The MCS lock's advantage, spinning on a private line, grows with core count and especially across sockets, where broadcasting an invalidation to every spinner is expensive. On a 4-vCPU VM it cannot show its strength. Exercise 5 asks you to rerun this on a larger machine.

### Failure modes

#### Lock-holder preemption

A spinlock assumes the holder is running. If the scheduler preempts the holder in the middle of its critical section, every waiter spins uselessly until the holder runs again, which might be a full scheduler time slice (milliseconds) later. Worse, the spinners are consuming exactly the CPUs the holder needs to be rescheduled on.

Defences, roughly in order of strength:

- Give each thread that can take the lock its own dedicated core, so nothing else competes for it (Chapter 17).
- Spin for a bounded time and then yield or sleep. glibc's adaptive mutex and most production spinlocks do this. The `Backoff` class above yields once it reaches its maximum spin count.
- Do not hold spinlocks across anything that can block or fault: no system calls, no allocation, no I/O, no touching memory that might not be resident.
- Prefer lock-free or wait-free structures on paths where a preempted thread must not stall others. That is the main motivation for Part III.

#### Priority inversion

A low-priority thread takes a lock. A high-priority thread wants it and waits. A medium-priority thread, which does not need the lock at all, preempts the low-priority thread and runs for a long time. The high-priority thread is now effectively waiting for the medium-priority one. The Mars Pathfinder lander famously kept resetting itself because of exactly this.

Real-time operating systems, and Linux with `PTHREAD_PRIO_INHERIT` mutexes, solve it with **priority inheritance**: while a thread holds a lock that a higher-priority thread is waiting for, it temporarily runs at the waiter's priority. Spinlocks cannot do this, because the kernel does not know that a spinning thread is waiting for anything. If you run real-time priorities (`SCHED_FIFO`), use priority-inheritance mutexes for any lock shared across priorities, or avoid sharing locks across priorities at all.

#### Convoys

When a lock is held for slightly too long, waiters accumulate. Each hand-off then has to pass through the queue, and the time a thread spends waiting grows with queue length. Even after the original cause disappears, the queue can persist, because each newly woken thread holds the lock for a short time and immediately finds a crowd behind it. Lock convoys are why contended locks show the long, fat tails in the table above.

#### Deadlock

Two threads each hold one lock and wait for the other's. The classic defence is a global lock order: always acquire locks in the same order. `std::scoped_lock` acquires several locks at once using a deadlock-avoidance algorithm, which helps when you cannot impose an order. For latency-critical code the better defence is structural: hold at most one lock at a time, and never call unknown code (callbacks, virtual functions, allocators) while holding one.

### Choosing a lock

A rough guide:

| Situation | Choice |
|---|---|
| Rarely contended, any critical-section length | `std::mutex` |
| Short critical sections, contended, threads on dedicated cores, throughput matters | TTAS with backoff |
| Short critical sections, contended, tail latency or fairness matters | MCS (or ticket on small machines) |
| Many cores, multiple sockets | MCS / queued spinlock |
| Read-mostly data | a reader-writer lock, or better, a sequence lock (Chapter 7) or RCU (Chapter 12) |
| Threads may be preempted while holding | a sleeping mutex, or a spin-then-sleep hybrid |
| Real-time priorities | priority-inheritance mutex |
| The lock is the bottleneck | redesign: shard the data (Chapter 13), make it single-writer, or go lock-free |

Whatever you choose, keep critical sections short. The fastest lock in the world cannot help a critical section that does a system call.

### Summary

- `std::mutex` is a futex: two atomic operations uncontended, system calls and context switches contended.
- Spinlocks never sleep. They are right for short critical sections on dedicated cores and wrong when holders can be preempted.
- Test-and-set spins with RMWs and floods the interconnect; test-and-test-and-set spins on loads; backoff spreads out retries and makes the lock unfair; a ticket lock is fair; an MCS lock is fair and spins on private lines.
- Measured on the reference machine with two threads: backoff 17 Mops/s, ticket 2 Mops/s. Fairness costs throughput; unfairness costs tail latency.
- Lock-holder preemption, priority inversion, convoys and deadlock are the failure modes that hurt latency. Lock-free structures exist mostly to avoid the first.
