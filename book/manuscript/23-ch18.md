## Case Studies {#ch18}

The previous seventeen chapters built and measured structures one at a time. Real systems combine them, and most of the engineering lies in the combination: which thread owns which data, where data crosses between threads, and what happens when something is late. This chapter works through one system in detail, a real-time patient-monitoring pipeline, then sketches three others (a trading system, a game engine and an audio engine) to show how the same few structures recur under different constraints. It ends with a selection guide that condenses the book into a set of questions.

### A patient-monitoring pipeline

A bedside patient monitor acquires physiological signals (ECG, pulse oximetry, blood pressure, respiration), derives vital signs from them, displays them, evaluates alarm conditions, and raises alarms that a clinician must notice. Alarms are the safety-critical function. International standards such as IEC 60601-1-8 govern how medical alarm systems behave, and IEC 62304 governs how their software is developed and verified.

`examples/ch18_patient_monitor.cpp` is a simplified, simulated version of the monitor's core. It is a teaching example: the thresholds, rates and budgets in it are illustrative, not clinical or regulatory values, and a real device involves far more (and far more process) than any book chapter can show. It is, however, a complete pipeline built from this book's structures, and it runs and checks itself.

#### Requirements

The example is designed against four requirements:

1. **Latency.** An alarm condition must be raised within 10 ms of the sample that completes it. (The real clinical requirement is measured in seconds and includes detection algorithms; 10 ms is an internal budget for the pipeline's own contribution, deliberately far inside it.)
2. **Consistency.** The display must never show a torn record, such as a heart rate from one moment and an alarm state from another that contradicts it.
3. **Completeness and order.** The audit log must record every alarm transition, in order.
4. **Isolation of the critical path.** Nothing on the path from sample to alarm may allocate memory, take a lock, or block on a slower component. The display, the log and the network must not be able to delay an alarm.

The fourth requirement is the one that shapes the design. It is common for a monitor's alarm path to be delayed not by its own computation but by something it shares with a non-critical component: a lock held by the UI thread while it redraws, an allocation that contends with a logging library, a full queue to a network stack that has stalled.

#### Architecture

![The patient-monitor pipeline. There is one SPSC ring per sensor and a single evaluator that owns all alarm state. A seqlock feeds the display, and a Disruptor broadcasts alarm events.](figures/monitor.svg)

Each choice follows from a requirement and from a chapter of this book.

**One SPSC ring per sensor** (Chapter 8). Each sensor has exactly one producer and the evaluator is the only consumer, so the cheapest correct queue is the right one. The rings are bounded and pre-allocated, and they never drop: a sensor that finds its ring full spins until there is room, which can only happen if the evaluator has fallen more than 1,024 samples (two seconds of heart-rate data) behind, itself a fault that a real device would detect and report. Using separate rings, rather than one MPSC queue, means the two sensors never write the same cache line.

**A single evaluator thread owns all alarm state.** The alarm logic, the current vital signs and the set of active alarms belong to one thread, so they need no synchronisation at all. This is the single-writer principle of Chapter 14's order book, and it makes the alarm logic an ordinary sequential program that can be unit-tested exhaustively (Exercise 18.1 does exactly that).

**A seqlock for the display** (Chapter 7). The display wants the *latest* vital signs, not every sample, and it runs at 60 Hz while the evaluator runs at 750 samples per second. A seqlock gives the display a consistent `VitalsView` (heart rate, SpO₂, active alarms and a generation number, all from one moment) without the evaluator ever waiting for it. If the display thread is slow, or stalls entirely, the evaluator does not notice. Requirement 2 is met by construction: a torn read is detected and retried by the seqlock protocol.

**A Disruptor for alarm events** (Chapter 10). An alarm transition must go to two consumers, the audit logger and the annunciator (which drives the speaker and lights), and both must see every event in the same order. The Disruptor's broadcast ring does exactly this, with no copying and with each consumer at its own pace: the annunciator spins, so it reacts within microseconds, while the logger wakes once a millisecond and processes everything that has accumulated as one batch.

The Disruptor's gating has a consequence that deserves a design review. Its producer may not overwrite a slot until *every* consumer has passed it, so if the logger fell 256 events behind, the evaluator would wait for it, violating requirement 4. Here, alarm transitions are rare (a few per minute in practice), so 256 slots represent hours of margin, and the margin can be monitored. A design that must tolerate a logger that stops entirely would instead make the logger a *non-gating* consumer that detects when it has been overrun (by comparing its sequence with the producer's) and records the gap, so that the alarm path can never be held back by the log. Either choice is defensible; what matters is that it is made deliberately and written down.

**Nothing allocates after start-up.** The rings, the Disruptor's entries and the views are all allocated before the sensors start. The evaluator's hot path contains no `new`, no locks, no system calls and no logging (Chapter 11).

#### Alarm logic

Alarm evaluation is deliberately simple, with two features that every real alarm system has in some form:

- **Persistence.** A condition must hold continuously for a minimum time before the alarm is raised: 100 ms for tachycardia (heart rate above 130) and 200 ms for desaturation (SpO₂ below 88%). A single artefactual sample, such as a motion spike on the ECG or a probe shifting on a finger, does not cause an alarm.
- **Hysteresis.** Once raised, an alarm clears only when the value recovers past a second, safer threshold (heart rate below 120, SpO₂ above 90%), not merely back across the trigger. A value hovering at the threshold does not make the alarm flicker on and off.

Both features exist to fight **alarm fatigue**, the well-documented problem of clinicians becoming desensitised to frequent, non-actionable alarms, which is itself a patient-safety hazard. They are also a reminder that "low latency" in a safety system does not mean "react to everything immediately". The persistence delay is a *designed* latency, part of the specification; the pipeline's job is to add as little *undesigned* latency as possible on top of it. The measurement below therefore excludes the persistence delay and measures from the sample that completes the condition to the publication of the alarm.

#### Results

The program injects a repeating scenario of tachycardia and desaturation episodes for 20 seconds, then checks its own requirements. On the reference machine:

```text
ran 20 s: 1191 display frames, 26 alarm transitions, 14 annunciations
sample-to-alarm latency: n=26 min=728 p50=1487 p90=1935 p99=1026742 max=1026742 (ns)
  (excludes the deliberate persistence delay; measures pipeline cost only)
budget (10 ms) misses: 0   audit log entries: 26, in order: yes   display regressions: 0
  t=  1.102 s  TACHY  RAISED
  t=  1.708 s  DESAT  RAISED
  t=  2.000 s  TACHY  cleared
  t=  3.000 s  DESAT  cleared
  ...
```

Typical sample-to-alarm latency is 1.5 µs: an SPSC transfer, the alarm update, a Disruptor publication and a seqlock store. All 26 transitions were logged, in order, and the display never went backwards. The raise times show the persistence delays at work: tachycardia begins at 1.0 s and is raised 100 ms later, desaturation begins at 1.5 s and is raised 200 ms later.

One transition took 1.03 ms. With only 26 samples, that single outlier *is* the p99 and the maximum. It is still ten times inside the budget, but it is three orders of magnitude above the median, and it is the platform: on the untuned four-vCPU VM, the evaluator was descheduled for a millisecond. This is the same tail that Chapter 17 measured, and the same cure applies: isolated cores, and, because a real monitor's evaluator would block rather than spin when idle, a PREEMPT_RT kernel for bounded wake-up latency.

#### What a real device adds

A production monitor builds much more around this core. Among the additions that relate to the structures in this book:

- **Technical alarms.** A sensor that stops delivering samples (a disconnected lead, a failed probe) must raise its own alarm. Each ring's producer stamps samples with sequence numbers and times; the evaluator checks for gaps and staleness on every cycle.
- **Watchdogs.** Every pipeline stage publishes a heartbeat counter; an independent supervisor checks that each one advances and raises a technical alarm, or resets the system to a safe state, if one does not. A seqlock or a plain atomic counter per stage is all this takes.
- **Priorities and escalation.** Alarm conditions have priorities (high, medium, low) with different audible and visual signals, and unacknowledged alarms escalate. That logic belongs in the evaluator, as sequential code.
- **Deterministic resource use.** All memory, threads and queues are allocated at start-up and sized for the worst case, with the sizing argued in the design documentation; nothing grows at run time.
- **Verification evidence.** Unit tests of the alarm logic covering every transition, model-checking or careful written arguments for each synchronisation point, sanitizer runs in CI, long stress tests on the target hardware and timing measurements on the target OS (Chapter 16).

### A trading system

An electronic trading system for one exchange typically has this critical path: receive market data, update order books, run a strategy that decides whether to trade, check risk limits, and send an order. Firms compete on the time from the market-data packet arriving to the order leaving, and in the most competitive businesses that time is measured in single-digit microseconds in software, or in nanoseconds in FPGAs.

The architecture is the patient monitor's, with the dial turned further:

- **Kernel bypass** delivers packets straight from the network card to a polling thread in user space (Chapter 17).
- **One feed-handler thread per feed** decodes packets and applies updates to **single-writer order books**, flat price ladders in the fastest designs (Chapters 14 and 15), and publishes top-of-book snapshots through **seqlocks** (Chapter 7) or updates through **SPSC rings** or a **Disruptor** (Chapters 8 and 10).
- **Strategies** run on their own isolated cores, reading books or consuming update streams. Often the feed handler, book and strategy are fused into *one* thread to avoid any cross-thread hop at all; a cross-core transfer, however good, still costs tens to hundreds of nanoseconds.
- **Order objects** come from pre-faulted **pools** (Chapter 11), looked up by ID in an **open-addressing map** (Chapter 13).
- **Risk limits and configuration** are read on every order and changed rarely: **RCU** or hazard-pointer swapped objects (Chapter 12).
- **Logging and statistics** go through SPSC rings to a logging thread on a housekeeping core, with **sharded counters** (Chapter 13) for statistics, so the critical path never formats a string or takes a lock.
- **Everything is isolated and pinned**, with busy-spinning on critical cores (Chapter 17).

The patient monitor tolerates a millisecond of tail latency, though it should not need to; a trading system often does not tolerate ten microseconds. The structures are the same; the difference is how much of the platform must be removed.

### A game engine

A game engine renders a frame every 16.7 ms (60 Hz) or 8.3 ms (120 Hz). Missing the deadline causes a visible stutter, so the engine cares about the *worst* frame time, not the average. Its concurrency has a different shape: instead of a stream of events, there is a burst of parallel work every frame.

- **Job systems** split each frame's work (animation, physics, visibility, AI) into small jobs scheduled across all cores. Each worker has a **work-stealing deque** (the Chase-Lev deque): the owner pushes and pops at one end without contention, and idle workers steal from the other end with a CAS. It is a close relative of the structures in Chapters 6 and 9.
- **Data-oriented layouts** (Chapter 15) are standard: entity-component systems store each component type in a dense SoA array, so that a system such as physics streams through exactly the data it needs.
- **Per-frame arenas** (Chapter 11) provide temporary memory that is freed in one operation at the end of each frame, so the frame never calls `malloc`.
- **Double or triple buffering** separates the simulation thread from the render thread: the simulation writes frame N+1's state while the renderer reads frame N's, and the two swap at a frame boundary. It is the seqlock idea at the granularity of whole frames.
- **Command queues** from game threads to the render thread are MPSC or SPSC rings of render commands (Chapters 8 and 9).

### An audio engine

A digital audio workstation or a software synthesizer processes audio in a **callback** that the audio driver invokes every buffer period, for example every 2.7 ms for 128 samples at 48 kHz. If the callback ever takes longer, the output has an audible glitch. The callback runs on a high-priority real-time thread, and the rules of audio programming are the rules of Chapter 11 and Chapter 5 at their strictest: no allocation, no locks, no system calls, no I/O, no waiting on any other thread, ever.

- **Parameters** (volume, filter cutoff) are atomics written by the UI thread and read by the callback with relaxed or acquire loads (Chapter 6).
- **Messages** from the UI (note on, load preset) arrive through **SPSC rings** read at the top of each callback (Chapter 8). Messages back to the UI, such as meter levels, use another ring in the opposite direction, or a seqlock (Chapter 7).
- **Large objects**, such as a new sample buffer or a convolution reverb's impulse response, are built on a non-real-time thread and swapped in with an atomic pointer exchange. The old object must not be freed by the callback, since `free` may take a lock, so the callback sends the old pointer back through a ring to the thread that allocated it, which frees it: Chapter 11's **return-ring** pattern, used here for safe reclamation rather than for speed.
- **Priority inversion** (Chapter 5) is the classic audio bug: the callback blocks on a mutex held by a low-priority UI thread that has been preempted. The cure is to never share a lock with the callback.

### A selection guide

The book's advice condenses into a sequence of questions. Ask them in order, for each piece of shared data in a design.

**1. Does it need to be shared at all?** The fastest synchronisation is none. Give the data to one thread and send that thread requests (single writer, Chapters 13 and 14). Fuse stages that do not need to be separate threads.

**2. What is the communication pattern?**

| Pattern | Structure | Chapter |
|---|---|---|
| One producer, one consumer, every item | SPSC ring | 8 |
| Many producers or consumers, every item to one consumer | Bounded MPMC queue (Vyukov) | 9 |
| Every item to several consumers, in order, or a staged pipeline | Disruptor | 10 |
| Readers want only the latest value of a small struct | Seqlock | 7 |
| Readers want a large object that changes rarely | RCU or hazard-pointer swap | 12 |
| Shared lookup by key, bounded integer keys | Lock-free open-addressing map | 13 |
| Shared lookup by key, read-mostly, any types | RCU map | 13 |
| Shared ordered data, concurrent updates | Lazy skip list | 14 |
| Counters and statistics | Sharded counters | 13 |
| Short critical sections, low contention, simple code | Spinlock or mutex | 5 |

**3. What happens when it is full, empty or slow?** For every queue: when the consumer is slow, does the producer wait, drop, or overwrite? When it is empty, does the consumer spin, yield or block (Chapters 9 and 17)? Can a slow non-critical consumer delay the critical path (as the Disruptor's gating could, above)?

**4. Where does memory come from and where does it go?** Pre-allocate, pool, and pre-fault (Chapter 11). For every node freed while other threads may read it, name the reclamation scheme (Chapter 12).

**5. How is it laid out?** Pad data written by different threads onto separate cache lines (Chapter 2). Lay out hot data for its access pattern, densely, and keep cold data elsewhere (Chapter 15).

**6. How do you know it is correct?** Name every synchronising operation's partner, model-check the skeleton, run TSan and ASan in CI, and stress-test on weakly ordered hardware (Chapters 3 and 16).

**7. How do you know it is fast?** Measure latency distributions, not averages, with coordinated omission corrected, under realistic load, on a tuned platform (Chapters 1, 4 and 17). Compare against the simplest design that could work; keep the complex one only if it wins where it matters.

### Closing

The structures in this book are not exotic. A ring buffer, a sequence counter, a padded array and a few carefully ordered atomic operations account for most of the low-latency code running in exchanges, hospitals, studios and data centres. What makes them work is not cleverness but a small number of disciplines applied consistently: share as little as possible, know which thread owns what, keep the allocator and the scheduler off the critical path, lay data out for the hardware, reason explicitly about every ordering, and measure the whole distribution. Systems built this way are fast, and, as importantly, they are predictable, which is what fast systems are for. Part VI follows one more system, the acquisition software of a PET scanner, all the way from the wire format to a review package, to show these disciplines applied end to end.

### Summary

- The patient-monitor pipeline uses an SPSC ring per sensor, a single evaluator thread that owns all alarm state, a seqlock for the display and a Disruptor for alarm events. Nothing on the sample-to-alarm path allocates, locks or blocks.
- Persistence and hysteresis in the alarm logic are designed latencies that reduce alarm fatigue; the pipeline must add as little undesigned latency as possible on top.
- Measured: median sample-to-alarm latency of 1.5 µs, 26 of 26 transitions logged in order, no torn or regressing display reads, and one 1 ms outlier from the untuned VM, inside the 10 ms budget.
- Trading systems, game engines and audio engines use the same structures under different constraints: microsecond deadlines, frame deadlines and callback deadlines.
- Choose structures by asking, in order: must it be shared; what is the communication pattern; what happens when it is full, empty or slow; where does memory come from; how is it laid out; how do you know it is correct; how do you know it is fast?

### Exercises

1. **Gating.** In the patient-monitor pipeline, the audit logger is a gating consumer of the alarm Disruptor. Describe a failure of the logger that would delay alarms, and how long it would take to have an effect. Redesign the logger as a non-gating consumer that detects overruns, and say what it must record when one happens.

2. **Sensor loss.** Add a technical alarm for sensor loss to the design: what does the evaluator check, how often, and with what timeout? Which data must the sensors provide for the check to work?

3. **One queue or two?** A colleague proposes replacing the two SPSC rings with one MPSC queue, "to simplify the evaluator loop". Give two technical arguments against it, and one situation in which it would be the right choice.

4. **Trading budget.** A trading system's measured path is: network card to user space 1.2 µs, decode 150 ns, book update 40 ns, strategy 300 ns, risk check 80 ns, order encode and send 1.1 µs. Which two items would you attack first, with which techniques from this book? What would fusing the book and strategy threads save if they are currently connected by an SPSC ring?

5. **Audio reclamation.** In the audio engine, why can the callback not simply `delete` the old impulse response after swapping in the new one? Design the return path, including what happens if the UI thread swaps in three new impulse responses in a single buffer period.

6. **Hands-on: Exercise 18.1, a threshold alarm.** Implement `ThresholdAlarm::update` in `exercises/ch18/threshold_alarm.hpp` with persistence (the condition must hold continuously for `persist_ns`; any in-range sample restarts the timer) and hysteresis (clear only past `clear_at`). The tests check that short excursions do not raise the alarm and that values between the two thresholds keep it active. Then add your own tests for the boundary cases: a value exactly at the trigger, exactly at the clear threshold, and a persistence period that ends exactly on a sample.

7. **Hands-on: extend the monitor.** Add a third sensor (respiration rate at 50 Hz, with a low-rate alarm) to `ch18_patient_monitor.cpp`, with its own ring and alarm, and extend `VitalsView` and the display. Then add per-stage heartbeat counters and a supervisor thread that reports any stage that has not advanced for 100 ms. Run the result under TSan.
