## Measuring Latency Without Lying to Yourself {#ch04}

Every chapter from here on makes claims of the form "this design is faster". Those claims are only as good as the measurements behind them, and latency is unusually easy to measure wrongly. The timer has overhead comparable to the thing being timed. The optimiser deletes code whose result is unused. The first iterations run with cold caches. The operating system interrupts the measurement. And the most common way of generating load, sending the next request when the previous one returns, systematically hides exactly the stalls you are looking for.

This chapter builds the measurement tools the rest of the book uses, a calibrated cycle clock, a latency histogram and a small harness, and shows the two mistakes that invalidate more benchmarks than any other: ignoring timer overhead and coordinated omission.

### Clocks

A latency measurement needs a clock that is monotonic (never goes backwards), fine-grained, and cheap to read. Linux offers several.

`clock_gettime(CLOCK_MONOTONIC)` is the safe default. It is implemented in the vDSO, a small shared library the kernel maps into every process, so reading it does not enter the kernel. `std::chrono::steady_clock::now()` calls it on Linux. It returns nanoseconds since an arbitrary epoch and is consistent across cores.

The **time-stamp counter** (TSC) is a 64-bit register that x86 cores increment at a constant rate. On every Intel and AMD processor of the last decade it is *invariant*: its rate does not change with frequency scaling or sleep states, and it is synchronised across cores of a socket. It is read with the `rdtsc` instruction, which takes a few dozen cycles and does not enter the kernel. `rdtscp` additionally waits for all previous instructions to complete before reading the counter, which makes it the right instruction for the *end* of a timed region. TSC ticks must be converted to nanoseconds by calibrating against `CLOCK_MONOTONIC`.

On ARMv8 the equivalent is the generic timer's virtual count register, `CNTVCT_EL0`, which ticks at a fixed (often low, such as 24 MHz to 1 GHz) frequency given by `CNTFRQ_EL0`. The companion library falls back to `clock_gettime` on non-x86 platforms for simplicity.

The library wraps these in `include/llds/common/timer.hpp`:

```cpp
inline std::uint64_t now_ns() noexcept {
    timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return static_cast<std::uint64_t>(ts.tv_sec) * 1'000'000'000ull +
           static_cast<std::uint64_t>(ts.tv_nsec);
}

inline std::uint64_t cycles() noexcept { return __rdtsc(); }

inline std::uint64_t cycles_serialized() noexcept {
    unsigned aux;
    return __rdtscp(&aux);
}

class TscClock {
public:
    TscClock() { calibrate(); }
    void calibrate(std::chrono::milliseconds window = std::chrono::milliseconds(50)) {
        const auto c0 = cycles();
        const auto t0 = now_ns();
        std::this_thread::sleep_for(window);
        const auto c1 = cycles();
        const auto t1 = now_ns();
        ns_per_cycle_ = double(t1 - t0) / double(c1 - c0);
    }
    double to_ns(std::uint64_t cycle_delta) const noexcept { return cycle_delta * ns_per_cycle_; }
private:
    double ns_per_cycle_ = 1.0;
};
```

How much does each cost? `examples/ch04_timers.cpp` measures them on the reference machine:

```text
clock_gettime(CLOCK_MONOTONIC)        30.73 ns
std::chrono::steady_clock::now()      30.94 ns
rdtsc                                 17.75 ns
rdtscp                                23.24 ns
TSC: 0.4762 ns per cycle (2.100 GHz)
clock_gettime minimum observable step: 25 ns
```

These are higher than on bare metal, where `rdtsc` typically costs 6 to 10 ns and `clock_gettime` 15 to 20 ns, because this is a virtual machine. They set a floor: you cannot meaningfully time a single operation that takes less than the timer itself, and you must subtract the timer's own cost when you time operations not much longer than it.

### Timing one operation versus timing many

There are two ways to time an operation.

**Batch timing** reads the clock, runs the operation N times, reads the clock again, and divides. Timer overhead is amortised to nothing, and the result is the mean cost per operation. It cannot show you a distribution, and it is only meaningful if consecutive operations are independent; the CPU will happily overlap the next iteration with the current one, so batch timing measures *throughput*, not latency.

**Individual timing** reads the clock before and after each operation and records the difference. It shows the full distribution, including the tail, but each sample includes the timer's overhead and the timer's own jitter. It is the only way to see the tail, so it is the method we use most.

The harness offers both, in `include/llds/common/bench.hpp`:

```cpp
template <class Op>
double measure_batch(Op&& op, std::uint64_t ops);   // mean ns per op

template <class Op>
Histogram measure_each(Op&& op, const BenchOptions& opt = {});  // distribution
```

`measure_each` warms up first (running the operation a few thousand times so caches and branch predictors reach steady state), measures the timer's own minimum overhead, and subtracts it from every sample:

```cpp
template <class Op>
Histogram measure_each(Op&& op, const BenchOptions& opt = {}) {
    static const TscClock clock;  // calibrate once per process
    for (std::uint64_t i = 0; i < opt.warmup; ++i) op();

    std::uint64_t overhead = ~0ull;
    for (int i = 0; i < 1000; ++i) {
        const auto t0 = cycles();
        clobber_memory();
        const auto t1 = cycles_serialized();
        overhead = std::min(overhead, t1 - t0);
    }

    Histogram h;
    for (std::uint64_t i = 0; i < opt.iterations; ++i) {
        const auto t0 = cycles();
        op();
        const auto t1 = cycles_serialized();
        const auto d = (t1 - t0) > overhead ? (t1 - t0) - overhead : 0;
        h.record(static_cast<std::uint64_t>(clock.to_ns(d) + 0.5));
    }
    return h;
}
```

Subtracting the minimum overhead, not the mean, is deliberate: the minimum is the cost of the timer when nothing interferes, which is what was added to every sample. Subtracting the mean would subtract some jitter too and bias the tail downwards.

Timing a trivial operation (one multiply-add) with the harness shows the floor of what it can resolve:

```text
measure_each(empty-ish op): n=1000000 min=0 p50=6 p90=7 p99=10 p99.9=15 p99.99=151 max=53101 mean=6.9 (ns)
```

Anything you measure with `measure_each` has a few nanoseconds of uncertainty at the bottom and inherits whatever jitter the machine has at the top (the 53 µs maximum here is the operating system, as in Chapter 1).

### Defeating the optimiser

A benchmark that computes a value and never uses it measures nothing, because the compiler deletes the computation. A benchmark that computes the same value every iteration may be hoisted out of the loop. Two helpers prevent this:

```cpp
template <class T>
inline void do_not_optimize(T const& value) {
    asm volatile("" : : "r,m"(value) : "memory");
}

inline void clobber_memory() { asm volatile("" : : : "memory"); }
```

`do_not_optimize(x)` tells the compiler that `x` is used by an opaque piece of assembly, so it must actually be computed (and kept in a register or memory). `clobber_memory()` tells it that any memory may have been read or written, so stores before it must happen and loads after it must be redone. Both emit no instructions. They are the same tricks Google Benchmark's `DoNotOptimize` and `ClobberMemory` use.

Even with these, always sanity-check a surprising result by reading the generated assembly (`objdump -d`, or Compiler Explorer). The most embarrassing benchmark results come from measuring a loop the compiler vectorised, unrolled, or removed.

### A histogram for latencies

To report percentiles from millions of samples you need a histogram, not a sorted array of every sample. The histogram must have fine resolution at the low end (the difference between 30 ns and 40 ns matters) and wide range at the high end (a 10 ms outlier must still be recorded accurately enough). A linear histogram cannot do both. A **log-linear** histogram can: it divides the range into power-of-two "magnitudes" and splits each magnitude into a fixed number of linear sub-buckets. This is the idea behind Gil Tene's HdrHistogram.

`include/llds/common/histogram.hpp` implements a compact version with 64 sub-buckets per magnitude:

```cpp
class Histogram {
public:
    static constexpr int kSubBits = 6;                     // 64 sub-buckets
    static constexpr int kSubBuckets = 1 << kSubBits;
    static constexpr int kMagnitudes = 64 - kSubBits + 1;  // covers all of uint64
    static constexpr int kBuckets = kMagnitudes * kSubBuckets;

    void record(std::uint64_t v) noexcept {
        counts_[index_of(v)]++;
        total_++;
        min_ = std::min(min_, v);
        max_ = std::max(max_, v);
        sum_ += static_cast<double>(v);
    }

    static constexpr int index_of(std::uint64_t v) noexcept {
        if (v < kSubBuckets) return static_cast<int>(v);
        const int msb = 63 - std::countl_zero(v);
        const int mag = msb - kSubBits + 1;
        const int sub = static_cast<int>((v >> (msb - kSubBits)) & (kSubBuckets - 1));
        return mag * kSubBuckets + sub;
    }
    // percentile(), merge(), summary() ...
};
```

Values below 64 get one bucket each, so they are exact. For larger values, `index_of` finds the most significant bit, uses the next six bits below it to pick the sub-bucket, and discards the rest. The relative error of any recorded value is therefore at most 1/64, about 1.6%, whether the value is 100 ns or 100 seconds. Recording is a handful of instructions and never allocates, which matters: a histogram that allocates on the hot path measures the allocator.

The whole histogram is about 30 KiB. Each thread in a benchmark records into its own histogram, and the results are merged afterwards with `merge()`, so recording never involves shared writes.

### Coordinated omission

Now the most important section of this chapter.

Imagine you want to know how a service responds under a load of 20,000 requests per second, one every 50 µs. The obvious benchmark loop is:

```cpp
for (;;) {
    auto t0 = now();
    send_request_and_wait_for_reply();
    record(now() - t0);
    sleep_until_next_50us_slot();
}
```

Suppose the service normally replies in 2 µs, but once every 20,000 requests it stalls for 20 ms (a garbage-collection pause, a log rotation, a page-cache flush, a lock held by a slow thread).

During the stall, the benchmark is blocked waiting for the reply. It records one sample of 20 ms. Then it carries on. But in those 20 ms, a real population of clients sending at 20,000 per second would have sent 400 requests, and every one of them would have waited for the stall to end: the first about 20 ms, the next 19.95 ms, and so on down to the last. The benchmark did not send them. It *coordinated* with the system under test, backing off exactly when the system was slow, and so it *omitted* the samples that would have revealed how slow. Gil Tene named this **coordinated omission**.

The effect is not subtle. `examples/ch04_coordinated_omission.cpp` simulates exactly this scenario for two million requests and computes three histograms: the naive one (service time only), a corrected one that charges each request from its *intended* send time, and the naive one corrected after the fact by HdrHistogram's "expected interval" back-filling. The core of the simulation:

```cpp
for (std::uint64_t i = 0; i < requests; ++i) {
    const std::uint64_t service = (i % stall_every == stall_every - 1) ? stall_ns : fast_ns;
    const std::uint64_t intended = i * interval_ns;      // open-loop schedule
    const std::uint64_t start = std::max(clock, intended);
    const std::uint64_t done = start + service;
    clock = done;

    naive.record(service);               // what a closed-loop tool reports
    corrected.record(done - intended);   // what users actually experience
}
```

The results:

```text
naive (service time)        p50=2015 p99=2015     p99.9=2015     p99.99=2015     max=20000000 (ns)
corrected (from intended)   p50=2015 p99=10354687 p99.9=19136511 p99.99=19922943 max=20000000 (ns)
naive + expected-interval   p50=2015 p99=9961471  p99.9=19136511 p99.99=19922943 max=20000000 (ns)

The naive p99.9 is 9497x too optimistic.
```

![Coordinated omission in the simulation. The naive measurement never sees the stall; measured from intended send times, everything above p99 is 10 to 20 ms.](figures/chart-omission.svg)

The naive measurement says the 99.99th percentile is 2 µs. The truth is 20 ms. The naive p99.9 is wrong by a factor of almost ten thousand. And the stall occupies 2% of wall-clock time (20 ms out of every 1 s), so it is not a rare event at all: 2% of all requests are affected.

The lessons:

1. **Generate load open-loop.** Decide when each request *should* be sent, independently of when previous requests complete, and measure latency from that intended time. If the system falls behind, the requests queue up, exactly as they would in production.
2. **If you must run closed-loop**, correct for it: when a sample exceeds the expected interval, back-fill the samples that would have been taken. Exercise 4.2 asks you to implement this; HdrHistogram calls it `recordValueWithExpectedInterval`.
3. **Measure at the consumer.** In a pipeline, put the send timestamp into the message and compute latency where the message is consumed. Every pipeline benchmark in this book does this.
4. **Report the rate.** A latency number is meaningless without the load at which it was measured.

### Throughput benchmarks are not latency benchmarks

A related trap, mentioned in Chapter 1: when you flood a queue as fast as possible to measure its throughput, every message waits behind every message ahead of it. The latency you record is dominated by queue depth, not by the queue's hand-off cost. You will see this many times in later chapters, where the same queue shows hundreds of nanoseconds of latency when paced and hundreds of microseconds when flooded. Both numbers are real; they answer different questions. When you want the hand-off cost, pace the producer well below capacity. When you want the capacity, flood it, and do not quote the latency.

### A checklist for benchmarks

Before believing any number in this book, or any you produce yourself, check:

- **Environment printed.** CPU model, kernel, frequency governor, core count, and which cores were used. `llds::print_environment()` prints the first four.
- **Threads pinned.** Unpinned threads migrate between cores, which adds cache misses and scheduler noise. Pin them, and say which cores.
- **Warm-up done.** The first iterations run with cold caches, cold branch predictors, and unmapped pages.
- **Optimiser defeated.** Results consumed with `do_not_optimize`; assembly inspected if in doubt.
- **Timer overhead known.** Compared with the operation being measured, and subtracted if significant.
- **Distribution, not mean.** p50, p99, p99.9, p99.99, max, and sample count.
- **Load generated open-loop**, or corrected for coordinated omission.
- **Correctness checked.** A benchmark of a queue that silently loses messages is fast and worthless. Every benchmark in the companion code verifies its results (sequence numbers, checksums, counts).
- **Run more than once.** If two runs differ by more than the effect you are measuring, you have measured noise.
- **Frequency controlled.** Turbo boost and power-saving states change the clock rate under you. On a lab machine, fix the frequency (Appendix B); on a cloud VM, accept the noise and say so.

### Tools beyond the harness

The harness is enough for the experiments in this book. For real systems you will also want:

- **Google Benchmark**, for microbenchmarks with statistical repetition and reporting.
- **`perf stat`**, to count cycles, instructions, cache misses and branch mispredictions for a whole run (`perf stat -e cycles,instructions,cache-misses,LLC-load-misses ./prog`).
- **`perf c2c`**, which finds cache lines that bounce between cores, including false sharing, and tells you which source lines touch them. It is the most effective tool there is for the problems in Chapter 2.
- **`perf record` / `perf report`** and flame graphs, to see where time goes.
- **Intel VTune, AMD uProf or ARM Streamline** for deeper microarchitectural analysis.
- **`bpftrace`** and **`perf sched`**, to see scheduler events (wake-ups, migrations, preemptions) that cause tails.

### Summary

- Use `CLOCK_MONOTONIC` by default and the TSC (calibrated) for short intervals; know what each costs on your machine (31 ns and 18 ns on the reference VM).
- Batch timing measures throughput; individual timing measures the latency distribution. Subtract the timer's minimum overhead from individual samples.
- Defeat the optimiser with `do_not_optimize` and `clobber_memory`, and read the assembly when results surprise you.
- Record latencies in a log-linear histogram: bounded relative error, no allocation, mergeable per-thread histograms.
- Coordinated omission makes closed-loop benchmarks hide stalls. In the simulation, the naive p99.9 was 9,500 times too optimistic. Generate load open-loop and measure from intended send times.
- Flooded throughput tests report queueing delay, not hand-off latency.
