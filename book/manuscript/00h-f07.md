## Atomics and Memory Ordering, a First Look {#f07}

Atomic operations are the second way to share data without a race. They are more powerful than they look and harder to use correctly than they look, because an atomic operation does two separate jobs: it changes one variable indivisibly, and, depending on its *memory order*, it may also make *other* data visible to another thread. This chapter introduces both jobs with the smallest possible examples. Chapter 3 gives the full memory model, Chapter 6 the design techniques, and Appendix A what the orders compile to on real CPUs.

### Atomicity

`std::atomic<T>` makes each operation on one variable indivisible:

```cpp
std::atomic<std::uint64_t> processed{0};
processed.fetch_add(1, std::memory_order_relaxed);   // read-modify-write, as one step
```

`fetch_add` reads the old value and writes the new one as a single operation, so two threads incrementing concurrently never lose an increment. By contrast, `processed.store(processed.load() + 1)` is two atomic operations with a gap between them, and another thread's increment can fall into the gap. Atomic loads and stores do not compose into atomic read-modify-writes.

All modifications of one atomic variable happen in a single total order, its *modification order*, which every thread agrees on. That is what makes the counter exact. It says nothing about *other* variables.

Atomic does not necessarily mean lock-free. For large types, or on some targets, the implementation uses a hidden lock. `std::atomic<T>::is_always_lock_free` tells you at compile time; the library checks it where an algorithm depends on it.

### Relaxed: atomic, and nothing more

`std::memory_order_relaxed` gives atomicity and the modification order, and no ordering with respect to anything else. It is exactly right for a statistic such as "number of hits processed", as long as nobody uses its value to conclude that some other data is ready. The final count read after joining the workers is exact, because `join()` supplies the ordering. Exercise F5.1 used it for this reason.

### Publication: release and acquire

Now the second job. One thread prepares a message and another must read it:

```cpp
Hit payload;                          // ordinary, non-atomic data
std::atomic<bool> ready{false};

// writer, once:
payload = Hit{100, 3, 511};
ready.store(true, std::memory_order_release);

// reader, once:
while (!ready.load(std::memory_order_acquire)) std::this_thread::yield();
use(payload);                         // sees {100, 3, 511}
```

A *release* store says: everything I wrote before this store must be visible to any thread that sees this store. An *acquire* load says: if I see a value written by a release store, I also see everything that preceded it. When the reader's acquire load reads the `true` that the writer's release store wrote, the two operations *synchronise*, and the write to `payload` is guaranteed to be visible when `use(payload)` runs.

Do not think of release as "flush the caches" or of acquire as "reload from RAM". Caches on mainstream CPUs are coherent; the real issues are the compiler and the CPU reordering memory operations, which Chapter 3 explains with store buffers and litmus tests. Reason in the language's terms first, and let the compiler pick the instructions.

Without the release/acquire pair, with relaxed on either side, the program is broken in a subtle way: the reader may see `ready == true` and still read an old or half-written `payload`, which is also a data race on `payload`.

### Three relations

The guarantee above is stated with three relations, which the rest of the book uses constantly:

- **Sequenced-before**: within one thread, statements happen in program order (`payload = ...` is sequenced before `ready.store(...)`).
- **Synchronises-with**: an acquire load that reads the value of a release store synchronises with it. Unlocking a mutex synchronises with the next lock of it; a thread's completion synchronises with the `join()` that waits for it.
- **Happens-before**: the transitive combination of the two. If write W happens before read R, R sees W (or something later).

So the mailbox proof is three lines: the payload write is sequenced before the release; the release synchronises with the acquire that reads `true`; the acquire is sequenced before the payload read. Therefore the write happens before the read, and there is no race. If the acquire had read `false`, there would be no synchronisation and no guarantee, which is why the reader loops until it sees `true`.

### Reuse needs a second edge

The mailbox above publishes once. To use the slot again, the writer must not overwrite `payload` while the reader is still reading it. That is a second ordering requirement, in the opposite direction: the reader's *read* of the slot must happen before the writer's *next write* to it. It needs its own release/acquire pair, typically the reader setting a flag back with release and the writer checking it with acquire. Every reusable slot in this book, from the mailbox of Exercise 3.1 to the rings of Chapters F8 and 8, has these two edges: **publication** (writer to reader) and **reuse** (reader back to writer).

When you review lock-free code, make a table for each piece of shared non-atomic data: who writes it, who reads it, which operation marks it ready, which marks it free again, and which atomic operation provides each edge. "The index is atomic" is not an argument, because the payload is not the index.

### Sequential consistency and compare-exchange

The default memory order, `seq_cst`, is release/acquire plus one global order of all `seq_cst` operations that every thread agrees on. It is the easiest to reason about and a good default while you learn. It does not make several separate atomics into one transaction, and it does not fix lifetime bugs. Weaken an order only when you can name the edge each operation must provide, as the comments in the library do.

`compare_exchange_weak(expected, desired)` is the building block of most lock-free algorithms: if the variable equals `expected`, replace it with `desired` and return true; otherwise copy the current value into `expected` and return false. The weak form may fail spuriously, so it is always used in a loop, and anything computed from `expected` must be recomputed after a failure. Chapter 6 builds algorithms from it.

### Lock-free is about progress, not speed

*Lock-free* means some thread always makes progress, even if others are suspended at any point; *wait-free* means every thread finishes in a bounded number of its own steps. Neither means "fast", and a lock-free structure can be slower than a mutex. A loop that retries a failed `try_push` forever is not lock-free either, however lock-free `try_push` itself is. Chapter 6 defines the classes carefully, and Chapters 7 and 9 show structures that look lock-free but are not.

### Summary

- An atomic operation is indivisible; a load followed by a store is two operations.
- Relaxed gives atomicity only. It is right for counters that publish nothing.
- Release/acquire publishes ordinary data: a write before the release is visible after an acquire that reads it.
- Reusable slots need two edges, publication and reuse. Write a proof table for each shared object.
- Lock-free and wait-free are progress guarantees, not performance claims.

### Exercises

1. **Load plus store.** Two threads each run `x.store(x.load() + 1)` 1000 times on `std::atomic<int> x{0}`. Is there a data race? Is the result always 2000? What is the smallest possible result?

2. **Which order?** Choose the weakest correct order for each, and justify it: (a) incrementing a "packets dropped" statistic; (b) setting a flag that tells a worker a configuration struct is ready; (c) the worker's load of that flag.

3. **Broken mailbox.** In the mailbox, the writer uses release but the reader uses relaxed. Describe what the reader may observe, and why ThreadSanitizer reports a race on `payload`.

4. **Two edges.** For a one-slot mailbox that is reused many times, write the proof table: for `payload`, `full`, list writer, reader, publication edge and reuse edge. (Exercise 3.1 then asks you to implement it.)
