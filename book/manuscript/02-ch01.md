## Why Latency Is Different from Throughput {#ch01}

Throughput is how much work a system completes per second. Latency is how long one piece of work takes. They sound like two views of the same thing, and for a single thread doing one thing at a time they are: if each request takes 10 microseconds, you complete 100,000 per second. Once you add queues, threads, caches and an operating system, they come apart, and they often pull in opposite directions. Batching improves throughput and hurts latency. Sleeping when idle saves power and CPU time and adds wake-up latency. A lock that is fair is usually slower than one that is not. Most of the engineering in this book is about choosing the latency side of those trades deliberately and knowing what it costs.

This chapter sets the vocabulary. It explains why we describe latency with distributions instead of averages, catalogues the places where latency hides on a modern machine, and ends with a small program that shows you the jitter on your own computer before you have written a single data structure.

### One number is never enough

Suppose a service handles a million requests and you are told the mean latency was 3 microseconds. What do you know? Almost nothing. Here are two services with exactly that mean:

- Service A answers every request in 3 µs.
- Service B answers 999,500 requests in 2 µs and 500 requests in 2 ms.

For a user of service B, one request in two thousand is a thousand times slower than usual. If each page view or each trading decision makes twenty requests, about one in a hundred of them will hit a 2 ms stall. The mean says the services are identical. They are not even similar.

Latency is a distribution, and it is almost never a well-behaved one. It has a hard floor (the time the work takes when nothing goes wrong) and a long tail to the right (everything that can go wrong). We describe it with percentiles:

- **p50**, the median: half of the requests were faster than this. It tells you the common case.
- **p99**: one request in a hundred was slower. For a system that handles thousands of requests per second, "one in a hundred" happens many times a second.
- **p99.9** and **p99.99**: the tail. This is where locks, page faults, interrupts and garbage collection show up.
- **max**: the single worst observation. It is noisy and unrepeatable, but in a system with a hard deadline it is the number that matters.

Throughout this book every latency measurement is reported this way, as a set of percentiles, and Chapter 4 builds the histogram that produces them.

> **Rule of thumb.** If someone reports a mean latency without percentiles, assume the tail is bad and they have not looked.

### Why the tail dominates

There are two reasons to care about the tail more than the median.

![A latency distribution has a hard floor, a peak near the median and a long tail. The mean falls where few requests are. The shape is illustrative, on logarithmic axes.](figures/latency-tail.svg)

The first is **fan-out**. A user-facing operation often depends on many back-end operations, and it is as slow as the slowest of them. If one operation has a 1% chance of being slow, an operation that waits for 100 of them is slow with probability 1 − 0.99¹⁰⁰ ≈ 63%. The p99 of the component becomes roughly the median of the whole. Jeff Dean and Luiz Barroso called this "the tail at scale", and it is why large systems are engineered around their p99.9.

![Fan-out turns a component's tail into the whole system's median. If each back-end call is slow 1% of the time, a request that waits for 100 of them is slow 63% of the time.](figures/chart-fanout.svg)

The second is **deadlines**. In a real-time system, a result that arrives late is a wrong result. An audio buffer that is not filled by the time the sound card needs it is a click. A control loop that misses its period destabilises the plant. A trading signal that arrives after the market has moved is worthless or worse. In these systems the median is almost irrelevant: what matters is whether *every* operation finishes within its budget, which is a statement about the maximum.

### Latency budgets

It helps to know the orders of magnitude involved. The table below lists typical end-to-end budgets in different domains. The numbers are rough and vary by product, but they show the range this book covers.

| Domain | Typical budget | What happens when it is missed |
|---|---|---|
| Market-making, tick-to-trade | 1–10 µs | Another firm trades first |
| Network packet processing at 10–100 Gb/s | 50–500 ns per packet | Packets are dropped |
| Robotics / motor control loop | 100 µs–1 ms | Control instability |
| Professional audio (64-sample buffer at 48 kHz) | 1.3 ms | Audible glitch |
| Game frame at 60 Hz | 16.7 ms | Visible stutter |
| Patient-monitor alarm pipeline (internal design budget) | ~10 ms | Delayed alarm; a safety issue |
| Interactive web request | 100 ms | User notices |

Now compare those budgets with what individual operations on a modern server cost:

| Operation | Approximate cost |
|---|---|
| L1 cache hit | 1–2 ns |
| Uncontended atomic increment | 5–10 ns |
| L3 cache hit | 10–40 ns |
| Cache line transferred between cores | 40–100 ns |
| DRAM access | 80–150 ns |
| Uncontended `std::mutex` lock + unlock | 15–25 ns |
| `malloc` + `free` (fast path) | 15–50 ns |
| System call | 100 ns–1 µs |
| Context switch | 1–5 µs |
| Minor page fault | 0.5–2 µs |
| Thread wake-up from a condition variable | 5–50 µs |
| Scheduler time slice | 1–10 ms |

The first lesson is in the gap between the two tables. A 10 µs budget is 100 DRAM accesses or *two* thread wake-ups. A 1 ms budget is generous for computation but disappears if the scheduler decides your thread should wait for the next time slice. Low-latency code is mostly the art of staying in the top half of the second table.

### Where latency hides

When a piece of code takes longer than it should, the extra time almost always comes from one of a small number of sources. It is worth listing them now, because each later chapter attacks one or more of them.

**The memory hierarchy.** A load that hits in L1 costs a nanosecond; the same load that misses all the way to DRAM costs a hundred times more. A data structure that chases pointers through memory (a linked list, a tree of small nodes, a hash map with chaining) pays the miss cost on every hop. Chapter 2 measures this, and Chapters 13 to 15 design around it.

**Coherence traffic.** When two cores write to the same cache line, the line must travel between them, and each transfer costs tens of nanoseconds. This happens even when the two cores write *different* variables that happen to share a line (false sharing). Contended atomics and locks are, at the hardware level, mostly coherence traffic. Chapters 2, 5 and 8 are about avoiding it.

**Synchronisation.** A thread that waits for a lock, a condition variable or a future is not making progress. If it waits by sleeping, it also pays the wake-up cost, which is set by the scheduler, not by your code. Chapters 5, 7 and 9 cover lock design and waiting strategies.

**The allocator.** `new` and `delete` are usually fast, but their worst case is not: a call that needs to refill a thread cache, take a global lock, or ask the kernel for memory can take microseconds. Allocation also scatters objects through memory, which hurts the cache. Chapter 11 is about allocation-free hot paths.

**The operating system.** Your thread runs only when the scheduler lets it. Timer interrupts, other processes, kernel threads, interrupt handlers for the network card and the disk, and page faults all steal time from it. On a virtual machine the hypervisor adds another layer of the same. Chapter 17 shows how to take most of this away.

**The hardware itself.** CPUs change frequency to save power or to stay within thermal limits. They take *system management interrupts* that are invisible to the operating system. They share execution resources between hyper-threads. Some of this can be controlled from the BIOS and the kernel command line; some cannot.

Notice that only the first three sources are about the data structure. The rest are about the environment it runs in. A perfect lock-free queue running on a thread that the scheduler preempts for 4 ms will deliver a 4 ms latency. That is why this book spends time on measurement and system tuning, not just on algorithms.

### Jitter: the time you did not ask for

The word **jitter** describes variation in latency that is not caused by variation in the work. If a function always does the same computation, any difference between its fastest and slowest runs is jitter, and it comes from the sources above.

You can see jitter directly with a very simple experiment: have a thread do nothing except read the clock in a tight loop, and record the gap between consecutive reads. On a perfectly quiet core, every gap would equal the cost of reading the clock, about 20 to 30 ns. Any longer gap means something else ran on that core, or the core itself stalled, between two reads.

The companion program `examples/ch01_jitter.cpp` does exactly this. Here is its core:

```cpp
const auto start = llds::now_ns();
auto prev = start;
for (;;) {
    const auto t = llds::now_ns();
    const auto gap = t - prev;
    gaps.record(gap);                 // a latency histogram (Chapter 4)
    if (gap > 1'000) {
        ++over_1us;
        stolen_ns += gap;
    }
    if (gap > worst) {
        worst = gap;
        worst_at = t - start;
    }
    prev = t;
    if (t - start > duration_ns) break;
}
```

`llds::now_ns()` reads `CLOCK_MONOTONIC` through `clock_gettime`, which on Linux runs entirely in user space (through the vDSO) and costs about 31 ns on the reference machine (Chapter 4 measures it; on bare metal it is nearer 15 to 20 ns). The thread is pinned to one CPU so the scheduler cannot move it.

Here is a five-second run on the reference machine, a 4-vCPU cloud virtual machine:

```text
clock-read gaps on cpu 0:
  n=151846309 min=28 p50=31 p90=32 p99=43 p99.9=59 p99.99=2687 max=2526066 mean=32.9 (ns)
worst stall: 2526.1 us at t=4.965 s
stalls > 1 us: 20886, > 10 us: 6412
time stolen by stalls > 1 us: 3.893% of the run
```

Read the distribution from left to right. The median gap is 31 ns, which is just the cost of reading the clock. The 99th percentile is 43 ns and the 99.9th is 59 ns: still nothing but clock reads, with the occasional cache miss. Then, at the 99.99th percentile, the gap jumps to 2.7 µs, and the worst gap is 2.5 *milliseconds*. Over five seconds, the thread was interrupted for more than a microsecond about 21,000 times (roughly 4,000 times a second, several times the kernel tick, which is 250 or 1,000 Hz on most distributions; on a virtual machine, hypervisor exits, steal time and device interrupts add to it, and Exercise 6 asks you to find out which), and more than 10 µs about 6,400 times. In total almost 4% of the core's time went to something other than this thread.

Nothing in the loop could have caused any of that. The program does the same thing on every iteration. Every gap above about 60 ns is jitter imposed from outside.

Try it on your own machine, and then try it on a different core:

```sh
./build/ch01_jitter
./build/ch01_jitter --cpus=3,0
```

On a laptop with a desktop environment running, expect a worse tail. On a server where CPU 3 is isolated from the scheduler and from interrupts (Chapter 17), you can expect the 99.99th percentile to drop to well under a microsecond and the maximum to tens of microseconds or less.

> **The floor and the tail.** Every latency distribution has a *floor*, set by the work and the hardware, and a *tail*, set mostly by the environment. Data-structure design moves the floor and the near tail (p99). System design moves the far tail (p99.99 and max). You need both.

### Throughput and latency pull apart

It is tempting to treat throughput benchmarks as latency benchmarks: if a queue moves 50 million messages a second, surely each message takes 20 ns? Not at all. That 20 ns is the *inverse throughput*, the average spacing between messages when the queue is saturated. The latency of one message, the time from when the producer pushes it to when the consumer sees it, can be much higher. If the queue holds 1,000 messages when a new one arrives, that message waits behind all of them.

This is Little's law: in a stable system, the average number of items inside it equals the arrival rate times the average time each spends inside. A system run at full throughput tends to fill every queue, so the latency it delivers is dominated by queueing. A system that must deliver low latency must therefore run *below* its maximum throughput, with spare capacity to absorb bursts.

You will see this effect in almost every benchmark in Part III: the same queue shows a latency of a few hundred nanoseconds when the producer is paced well below capacity, and hundreds of microseconds when the producer floods it. Neither number is wrong, but they answer different questions, and confusing them is one of the most common mistakes in performance work.

Some design choices that improve throughput make latency worse:

- **Batching.** Processing items in groups amortises fixed costs, but the first item in a batch waits for the last.
- **Sleeping when idle.** Blocking in the kernel frees the CPU for other work, but waking up takes microseconds.
- **Larger buffers.** They absorb bursts and keep producers from stalling, but a full large buffer is a long wait.
- **Work stealing and dynamic load balancing.** They keep all cores busy, but move work and data between cores, which costs cache misses.

And some choices that improve latency cost throughput or efficiency:

- **Busy-waiting.** A consumer that spins on an empty queue reacts within nanoseconds, but burns a core doing nothing.
- **Dedicated cores.** Pinning a thread to an isolated core removes scheduler jitter, but that core is lost to everything else.
- **Pre-allocation.** Reserving memory up front avoids allocator stalls, but wastes memory that may never be used.
- **Over-provisioning.** Running at 30% utilisation leaves room for bursts, but you pay for the other 70%.

There is no universally right choice. There is only the choice that meets your latency budget at an acceptable cost, and you can only find it by measuring.

### Determinism

For some systems, *predictable* latency matters more than *low* latency. A control loop that always takes 400 µs is easier to design around than one that usually takes 100 µs and occasionally takes 2 ms. A medical device whose alarm path has a proven upper bound is certifiable; one whose alarm path is "usually fast" is not.

Determinism pushes towards a particular style of code:

- bounded loops and bounded queues, so the worst case is known;
- no allocation after start-up, so the allocator's worst case never applies;
- no blocking calls on the critical path, so the scheduler's behaviour does not matter;
- wait-free or at least lock-free operations where several threads interact, so one stalled thread cannot stall another;
- simple data layouts, so cache behaviour is predictable.

You will see these principles throughout the book. They are not always the fastest choice on average, but they make the tail short and the maximum knowable.

### Progress guarantees in one paragraph

Concurrent algorithms are classified by what they promise about progress. A **blocking** algorithm (anything that takes a lock) can make every thread wait if one thread is delayed while holding the lock. A **lock-free** algorithm guarantees that *some* thread always makes progress: if one thread is delayed, the others can still complete their operations. A **wait-free** algorithm guarantees that *every* thread completes its operation in a bounded number of its own steps, regardless of what other threads do. These guarantees are about robustness to delays (preemption, page faults, a thread on a slow core), not about speed. A well-designed lock can be faster than a lock-free alternative. But a lock-free structure cannot be stalled by a preempted thread, and that property is often exactly what a low-latency system needs. Chapter 6 makes these definitions precise.

### A toy pipeline

Most systems in this book have the same shape: a stream of events flows through a sequence of stages, each running on its own thread, connected by queues.

```text
 [feed] --queue--> [parse] --queue--> [decide] --queue--> [act]
```

The feed might be a network card, a sensor or a file. Each stage does a small amount of work. The end-to-end latency of an event is the sum of the time it spends in each stage plus the time it spends in each queue, plus every hand-off between cores. If the stages are fast (say 200 ns each), the hand-offs and the queueing dominate. That is why so much of this book is about queues: in a well-designed pipeline, the queues *are* the latency.

You will build exactly this kind of pipeline several times: with chained queues in Chapter 10, with a Disruptor ring in the same chapter, tuned end to end in Chapter 17, and as a complete patient-monitoring system in Chapter 18.

### Summary

- Latency is a distribution. Report it as percentiles (p50, p99, p99.9, p99.99, max), never as a mean alone.
- The tail matters more than the median, because of fan-out and because of deadlines.
- Typical budgets range from about a microsecond to tens of milliseconds; know which operations fit inside yours.
- Latency hides in the memory hierarchy, coherence traffic, synchronisation, the allocator, the operating system and the hardware.
- Jitter is latency you did not ask for. You can see it with nothing more than a loop that reads the clock.
- Throughput and latency pull apart: saturated systems are dominated by queueing.
- Determinism (bounded, allocation-free, non-blocking code) is often worth more than raw speed.

### Exercises

1. **Fan-out.** A request fans out to 50 back-end calls in parallel and completes when all have answered. Each back-end call independently exceeds 1 ms with probability 0.2%. What fraction of requests exceed 1 ms? What per-call probability would you need for 99% of requests to complete within 1 ms?

2. **Same mean, different tails.** Construct two latency distributions with the same mean and the same median but p99.9 values that differ by a factor of 100. What does this tell you about benchmarks that report only the mean and median?

3. **Little's law.** A pipeline stage receives 2 million events per second and on average holds 600 events in its input queue. What is the average time an event spends in the queue? If you need the average below 50 µs at the same arrival rate, how many events may the queue hold on average?

4. **Budget arithmetic.** Your end-to-end budget is 5 µs. The pipeline has four stages, each doing 300 ns of computation, connected by three queues. Each hand-off between cores costs about 100 ns when the queue is empty. How much of the budget is left for queueing delay and jitter? How would the answer change if each stage blocked on a condition variable when idle (wake-up cost 20 µs)?

5. **Hands-on: your machine's jitter.** Run `ch01_jitter` on every CPU of your machine (`--cpus=N,0` for each N). Which CPU is quietest? Which is noisiest? Run it again while compiling the companion project in another terminal (`cmake --build build -j`). What happens to p99.99 and max?

6. **Hands-on: what is in the tail?** Modify `ch01_jitter.cpp` to record the timestamps of the 20 largest gaps. Are they periodic? Compare the period with your kernel's timer frequency (`grep CONFIG_HZ /boot/config-$(uname -r)`), and with `/proc/interrupts` sampled before and after the run.
