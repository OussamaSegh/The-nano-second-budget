## Concurrent Hash Maps {#ch13}

The hash map is the most used data structure in server software and the one most often wrapped in a single mutex and forgotten. In a low-latency system, it usually holds something every thread reads: instruments by symbol, sessions by connection, devices by serial number, orders by ID. This chapter measures what the single mutex costs, then builds three alternatives that each fit a different workload: lock striping, a lock-free open-addressing table, and a read-copy-update map built on Chapter 12's epochs. Its last section is about the "map" that causes more contention in practice than any other: the statistics counter.

### Why hash maps are hard to make concurrent

A sequential hash map has four operations that interact badly with concurrency.

- **Lookup** walks a bucket's chain or a probe sequence. If a concurrent erase frees a node on that chain, the lookup reads freed memory (Chapter 12's problem).
- **Insert** may trigger a **resize**, which moves *every* element. Any concurrent operation, on any key, is affected.
- **Erase** in an open-addressing table cannot simply empty a slot, because that would break the probe sequences of other keys that collided past it.
- **Iteration** is defined in terms of a stable set of buckets, which a resize invalidates.

Standard containers solve none of this, which is why `std::unordered_map` needs an external lock. Every concurrent hash map makes a set of trade-offs among these four, and the right one depends on the ratio of reads to writes, on whether the key space is bounded, and on what the values are.

### Measurements

`examples/ch13_maps.cpp` runs T threads, each performing two million operations on uniformly random keys out of 10,000 (all present). A fraction of operations are writes (overwrites of existing keys); the rest are lookups. Five maps are compared: `std::unordered_map` under a `std::mutex`, the same under a `std::shared_mutex`, the striped map, the lock-free integer map and the RCU map. Throughput, in millions of operations per second for all threads together, on the reference machine:

```text
writes                 0%              0.01%              5%
threads            T=1    T=4       T=1    T=4       T=1    T=4
mutex             40.4   10.8      40.5   10.8      40.3    8.0
shared_mutex      35.1   15.1      38.7   14.6      35.7    2.1
striped           60.7   65.1      59.4   66.1      57.6   55.6
lock-free int    108.7  317.7     106.5  365.8     101.4  228.4
rcu               71.4  273.9      13.8   17.0        -      -
```

(The RCU map is not run at 5% writes, for reasons that will become obvious.)

Four results stand out:

1. **The single mutex does not just fail to scale; it goes backwards.** Four threads achieve a quarter of the throughput of one. Every operation, including every lookup, moves the mutex's cache line between cores, and that transfer costs more than the lookup itself.
2. **The reader-writer lock is no rescue.** `std::shared_mutex` was meant for exactly this read-mostly workload, and with pure reads it is only a little better than the mutex (15.1 against 10.8) because taking a *shared* lock still writes the reader count in the lock word: every reader writes the same line. With 5% writes it collapses to 2.1 M ops/s, a fiftieth of the lock-free map's single-thread figure, because writers must wait for the reader count to drain and readers queue behind waiting writers.
3. **Lock striping prevents collapse but does not scale.** With 64 independent locks, threads rarely contend for the same one, and the striped map holds about 60 M ops/s at any thread count. It does not *increase*, however, and the reason is instructive (below).
4. **Maps whose readers do not write scale linearly.** The lock-free map's lookups and the RCU map's lookups are pure loads, so they triple or quadruple with four threads. The RCU map's single write per 10,000 operations, however, cuts its throughput by a factor of sixteen.

### Lock striping

**Lock striping** splits the map into N independent shards, each with its own lock and its own `unordered_map`, and picks the shard from the key's hash. It is the simplest concurrent map that works, and it accepts any key and value type (`include/llds/map/striped_hash_map.hpp`):

```cpp
template <class K, class V, std::size_t Stripes = 64, class Hash = std::hash<K>,
          class Lock = TtasLock>
class StripedHashMap {
public:
    std::optional<V> find(const K& k) const {
        auto& s = shard(k);
        std::lock_guard g(s.lock);
        auto it = s.map.find(k);
        if (it == s.map.end()) return std::nullopt;
        return it->second;
    }
    // insert_or_assign, insert, erase, update(k, f) follow the same pattern
private:
    struct alignas(kFalseSharingRange) Shard {
        mutable Lock lock;
        std::unordered_map<K, V, Hash> map;
    };
    Shard& shard(const K& k) const;   // mixes the hash, then uses the low bits
    std::array<Shard, Stripes> shards_;
};
```

Three details matter. Each shard is padded to its own 128-byte region, so two shards' locks never share a cache line (Chapter 2). The hash is **mixed** before choosing the stripe, because libstdc++'s `std::hash` for integers is the identity function, and sequential keys would otherwise hit stripes in a pattern that correlates with the inner map's buckets. And each shard can resize independently, so a resize stalls only the threads that want that shard.

So why does the striped map not scale? Contention is low, since four threads spread over 64 stripes rarely collide. But each lookup still *writes* its stripe's lock word, twice (acquire and release). If another thread used that stripe last, the cache line is in that thread's core, and getting it costs a transfer of 50 to 100 ns. With four threads and uniform keys, the chance that the previous user of a stripe was another thread is three in four. **An uncontended lock is not a free lock**: the line still migrates. The striped map is a good default when writes are frequent and values are complex. It is a poor choice for read-mostly data, which is most data.

### A lock-free open-addressing table

If the keys and values are machine words, a far faster design is possible. `ConcurrentIntMap` (`include/llds/map/concurrent_int_map.hpp`), in the style of Jeff Preshing's "world's simplest lock-free hash table" and Cliff Click's non-blocking hash map, is a single flat array of cells probed linearly:

```cpp
struct Cell {
    std::atomic<std::uint64_t> key{kEmptyKey};     // 0 means empty
    std::atomic<std::uint64_t> value{kTombstone};  // ~0 means absent
};
```

The whole design rests on one rule: **once a key has been written into a cell, it never changes.** Cells are claimed, never released. With that rule, a lookup never needs reclamation (there are no nodes to free), and probe sequences never break (a claimed cell is never emptied):

```cpp
std::optional<std::uint64_t> find(std::uint64_t key) const noexcept {
    for (std::size_t i = hash(key), n = 0; n < cap_; i = (i + 1) & mask_, ++n) {
        const auto k = cells_[i].key.load(std::memory_order_acquire);
        if (k == key) {
            const auto v = cells_[i].value.load(std::memory_order_acquire);
            if (v == kTombstone) return std::nullopt;
            return v;
        }
        if (k == kEmptyKey) return std::nullopt;   // probe chain ends here
    }
    return std::nullopt;
}
```

`find` is wait-free: a bounded sequence of loads, with no retries. Inserting claims a cell by CAS on its key, then stores the value:

```cpp
Cell* claim(std::uint64_t key) noexcept {
    for (std::size_t i = hash(key), n = 0; n < cap_; i = (i + 1) & mask_, ++n) {
        auto k = cells_[i].key.load(std::memory_order_acquire);
        if (k == key) return &cells_[i];
        if (k == kEmptyKey) {
            if (cells_[i].key.compare_exchange_strong(k, key, std::memory_order_acq_rel))
                return &cells_[i];
            if (k == key) return &cells_[i];   // another thread inserted the same key
        }
    }
    return nullptr;   // full
}

bool put(std::uint64_t key, std::uint64_t value) noexcept {
    Cell* c = claim(key);
    if (!c) return false;
    c->value.store(value, std::memory_order_release);
    return true;
}
```

Erasing stores a **tombstone** in the value; the key stays, so the cell stays claimed and the next insert of the same key reuses it. Atomic read-modify-write on values (`fetch_add`, or `insert` that only succeeds if absent) is a CAS loop on the value word.

Is it linearizable? Consider a lookup that runs concurrently with the first insert of a key. It may find the key already claimed but the value still `kTombstone`, and report "absent". That is correct: the insert's linearization point is the value store, not the key CAS, and the lookup happened before it. A later lookup that sees the value is guaranteed, by the release-acquire pair on `value`, to see everything the inserting thread wrote before it.

The table's speed comes from three properties, all of which were themes of Part I. Lookups write nothing, so the table's cache lines can be in the *shared* state in every core's cache at once; this is why throughput triples with four threads. Cells are 16 bytes, four to a cache line, and linear probing walks forward through memory, so a probe sequence of length three usually costs one cache miss. And there is no pointer chasing at all.

The price is paid in flexibility:

- **Keys and values are 64-bit words.** For larger values, store an index into a separate pool, or a pointer protected by hazard pointers.
- **One key value is reserved** (here 0) to mean empty, and one value (here all ones) to mean absent.
- **There is no resize.** Size the table for the worst case at a load factor of 0.5 or less; linear probing's cost rises steeply above 0.7. Click's design adds a cooperative, incremental resize in which every thread helps migrate cells to the new table, but it is complicated, and in a low-latency system a resize on the hot path is undesirable anyway.
- **Erased cells are never reclaimed.** A workload that inserts an endless stream of new keys (order IDs, say) eventually fills the table with tombstones. Either the key space must be bounded (instruments, beds, devices, connections), or the table must be rebuilt periodically off the hot path.

For bounded key spaces, those restrictions cost nothing, and the result is a map that answers 300 million lookups per second on four ordinary cores.

### A read-copy-update map

The third design makes the opposite trade. `RcuMap` (`include/llds/map/rcu_map.hpp`) holds an atomic pointer to an *immutable* `std::unordered_map`. Readers take an epoch guard, load the pointer, and look the key up in the snapshot. Writers copy the whole snapshot, change the copy, publish it with one store, and retire the old one:

```cpp
std::optional<V> find(const K& k) const {
    EpochDomain::Guard g;
    const Snapshot* s = current_.load(std::memory_order_acquire);
    auto it = s->find(k);
    if (it == s->end()) return std::nullopt;
    return it->second;
}

template <class F>
void update(F&& mutate) {
    std::lock_guard lock(writer_mutex_);           // writers are serialized
    const Snapshot* old = current_.load(std::memory_order_relaxed);
    auto* fresh = new Snapshot(*old);
    mutate(*fresh);
    current_.store(fresh, std::memory_order_release);
    EpochDomain::global().retire(const_cast<Snapshot*>(old));
}
```

With no writes, the RCU map scales almost perfectly (71 to 274 M ops/s), because readers write only their own epoch record. It accepts any key and value types, readers see a **consistent snapshot** (the `read(f)` member lets a reader look up several keys in the same version, which no other map in this chapter can offer), and iteration is trivial and safe.

But each write copies all 10,000 entries, which takes on the order of a millisecond, so at one write per 10,000 operations the benchmark spends most of its time copying, and throughput falls to 14 to 17 M ops/s. At 5% writes it would never finish. The RCU map is the right design for exactly one workload, and it is a common one: **read constantly, write rarely, and want snapshots**. Routing tables, symbol directories, device registries, feature flags and alarm-limit tables are all of this kind. For them, the copy is the *point*: it gives readers a version that never changes under them.

When the map is too large to copy on every write, the standard refinement is to copy only what changes: a persistent (immutable, structure-sharing) hash trie, such as a HAMT, shares all unchanged subtrees between versions, so a write copies one path of about log₃₂ n nodes. Another is to batch: collect writes for a few milliseconds and publish one new version for all of them.

### Other designs worth knowing

- **Split-ordered lists** (Shalev and Shavit, 2006) keep all items in one lock-free sorted list and treat the bucket array as shortcuts into it, so the table can grow without moving items.
- **Concurrent cuckoo hashing** (`libcuckoo`) gives each key two candidate buckets and uses fine-grained locks with optimistic, lock-free reads; it reaches high load factors.
- **Folly's `ConcurrentHashMap`** shards the table and uses hazard pointers for lock-free reads with locked writes, the common industrial compromise.
- **Intel oneTBB's `concurrent_hash_map`** uses per-bucket reader-writer locks and "accessor" handles that hold a lock while you use the element.
- **Swiss tables** (Abseil's `flat_hash_map`, Boost's `unordered_flat_map`) are not concurrent at all, but they are the fastest *single-threaded* maps, and a single-writer design (one thread owns the map, others send it requests through a queue) built on one often beats every concurrent map.

That last point deserves emphasis. The best concurrent map is often no concurrent map: give each shard of data to one thread, route requests by key to the owner, and let every map be single-threaded. This is how most matching engines, many databases (ScyllaDB's shard-per-core design, for one) and every actor framework work.

### Counters: the most contended map

The most contended shared data in a real system is often not a map at all but a set of statistics counters: messages received, orders sent, alarms raised, bytes per device. Every thread increments them on every event, and if they are plain `std::atomic<uint64_t>` objects, every increment is a contended RMW on a shared line. Chapter 6 measured exactly this: with four threads incrementing one counter, each thread's increment took about 115 ns (29 ns of wall time per increment across the four), against 7 ns for one uncontended thread.

The fix is to **shard**: give each thread (or each group of threads) its own padded counter, and make the rare *read* sum all the shards. Writes become uncontended; reads become slower, which is the right trade for statistics that are read once a second by a monitoring thread. Exercise 13.1 builds a `ShardedCounter` this way. The same technique gives per-core free lists (Chapter 11), per-thread histograms that are merged at the end of a benchmark (Chapter 4), and Linux's per-CPU counters.

### Choosing

| Workload | Map |
|---|---|
| Integer keys from a bounded space, any read/write mix | Lock-free open addressing |
| Read constantly, write rarely, want snapshots | RCU map |
| Arbitrary types, frequent writes, moderate rates | Striped map |
| Very high rates on partitionable keys | Shard by key to owner threads, single-threaded maps |
| Counters and statistics | Sharded counters, summed on read |
| Low rates, simple code | `std::mutex` + `std::unordered_map` |

Avoid `std::shared_mutex` on hot paths. Its name promises scalable reads, but readers still write the lock word, and its behaviour under even light writing was the worst in the benchmark.

### Summary

- Concurrency breaks hash maps at lookup (freed nodes), insert (resize), erase (probe chains) and iteration (moving buckets).
- A single mutex drops from 40 to 11 M ops/s when going from one thread to four; `std::shared_mutex` falls to 2 M ops/s with 5% writes.
- Lock striping avoids collapse (about 60 M ops/s at any thread count) but does not scale, because every lookup still writes a lock line.
- A lock-free open-addressing table with immutable keys needs no reclamation, has wait-free lookups and scales linearly: 109 M ops/s on one thread, 318 to 366 M ops/s on four. It requires word-sized keys and values, a bounded key space and no resize.
- An RCU map gives any-type snapshots with linearly scaling reads (274 M ops/s on four threads), but every write copies the map.
- Sharded counters, summed on read, remove the most common source of contention in real systems.
