## Coincidence Sorting {#ch20}

Coincidence sorting is the heart of a PET acquisition pipeline: out of a stream of millions of hits a second, find the pairs that came from one annihilation. It is also an algorithm whose *specification* belongs to physicists and whose *implementation* belongs to software engineers, which makes it a good place to practise keeping the two apart. This chapter specifies one pairing rule exactly, implements it three times (a slow oracle, a batch sliding window and a streaming sorter) and tests them against each other. It then solves the problem that comes before sorting, merging several independent sources into one time-ordered stream, and ends with how the pipeline estimates the coincidences that are wrong.

### What counts as a coincidence

Two hits form a *prompt* coincidence when they are on different detector modules and their times differ by no more than the coincidence window. The window is set by the timing resolution of the detectors and the size of the scanner: a few nanoseconds is typical, and scanners with time-of-flight capability resolve the difference within the window to a few hundred picoseconds, which tells reconstruction roughly *where* along the line the annihilation happened.

![Hits from different modules on a time axis. A pair falls inside one window, a lone hit stays a single, and three hits in one window form a multiple. The delayed window, which has the same width but is shifted, counts randoms.](figures/coincidence-window.svg)

Not every prompt coincidence is a good one. A **true** coincidence pairs the two photons of one annihilation. A **scattered** coincidence also comes from one annihilation, but one photon was deflected in the body, so the line between the detectors misses the true origin; scattered photons have lost energy, which is why the energy window of Chapter 21 rejects many of them. A **random** coincidence pairs photons from two different annihilations that happened to arrive within the window. Randoms grow with the square of the activity: for two detectors with singles rates *S*₁ and *S*₂ and a window of total width 2τ, the random rate is approximately 2τ·*S*₁·*S*₂. Doubling the window doubles the randoms, which is one reason the window is kept as narrow as the timing resolution allows.

The simulation in `ch19_pet_daq.cpp` produces all three. Its module-separation histogram shows them: after the energy window, about 2.3 million accepted coincidences are between opposite modules (mostly trues), and about 1.5 million are between modules one to three apart (randoms, plus trues whose partner landed on a neighbouring module).

### Policies change the science

When three or more hits fall within one window, a *multiple*, there is no single right answer. Common policies include:

- **Take all pairs**: every eligible pair is a coincidence. Simple and unbiased in a certain sense, but it adds randoms.
- **Kill multiples**: discard the whole group. Fewer randoms, but some trues are lost, and the loss grows with the count rate.
- **Take the winner**: keep one pair, chosen by energy or another criterion.

There is a second choice, independent of the first, about how windows are formed. In a **multiple-window** scheme every hit opens its own window, so windows overlap and a hit can pair with hits both before and after it. In a **single-window** scheme the first unassigned hit opens a window, every hit within the window of *that* hit joins its group, and the next window opens after the group; groups do not overlap.

These choices change the counts of trues, scatters and randoms that reach reconstruction, and with them the image. They are not implementation details. An optimisation that changes the policy, say by quietly switching from multiple windows to single windows because the code is simpler, changes the science. So the first step is to write the rule down exactly.

### The specification

The library implements multiple windows with "take all pairs":

> Given hits in non-decreasing time order, emit every pair (*i*, *j*), *i* < *j*, whose modules differ and whose time difference is at most `window`. Emit pairs ordered by *j*, then by *i*.

The ordering clause is part of the specification so that implementations can be compared output for output. Exercise 20.1 implements the single-window alternative with both multiples policies.

### Implementation 1: the oracle

The specification transcribed, with no cleverness, from `include/llds/pet/coincidence.hpp`:

```cpp
constexpr bool eligible(const Hit& a, const Hit& b, std::uint64_t window) noexcept {
    return a.module != b.module && tick_distance(a.tick, b.tick) <= window;
}

inline std::vector<Coincidence> pairs_oracle(std::span<const Hit> hits, std::uint64_t window) {
    std::vector<Coincidence> out;
    for (std::size_t j = 0; j < hits.size(); ++j)
        for (std::size_t i = 0; i < j; ++i)
            if (eligible(hits[i], hits[j], window)) out.push_back({hits[i], hits[j]});
    return out;
}
```

It is O(n²), far too slow for a real stream, and that does not matter: its job is to be obviously right. `tick_distance` subtracts the smaller timestamp from the larger, so it cannot wrap (Chapter F4).

A worked example fixes the rule in mind. Take hits (time, module) = (0, A), (2, B), (5, A), (12, C) with a window of 5. Pair (0, 1) qualifies: 2 apart, different modules. Pair (0, 2) is within the window but both hits are on module A. Pair (1, 2) qualifies: 3 apart. The hit at 12 is more than 5 from all the others. So the output is (0, 1), (1, 2). The test suite checks exactly this example.

### Implementation 2: the sliding window

Because the input is sorted, a hit that is too old to pair with hit *j* is too old for every later hit too. So a lower index `first` only ever moves forward:

```cpp
inline std::vector<Coincidence> window_pairs(std::span<const Hit> hits, std::uint64_t window) {
    std::vector<Coincidence> out;
    std::size_t first = 0;
    for (std::size_t j = 0; j < hits.size(); ++j) {
        if (j && hits[j].tick < hits[j - 1].tick) throw std::invalid_argument("window_pairs: input not sorted");
        while (hits[j].tick - hits[first].tick > window) ++first;   // first <= j: no underflow
        for (std::size_t i = first; i < j; ++i)
            if (hits[i].module != hits[j].module) out.push_back({hits[i], hits[j]});
    }
    return out;
}
```

Note `> window`, not `>=`: a hit exactly `window` away still pairs, because the specification says "at most". That boundary is the kind of thing that differs between a draft and the code, which is why the tests generate time gaps of a few ticks, so that boundary cases occur constantly.

What is the cost? `first` advances at most *n* times in total, but the inner loop examines every hit in the current window. The work is O(*n* + *C*), where *C* is the number of candidates examined. In a sparse stream *C* is small; in a dense window it is not. If *k* hits share a window, all pairs among them are candidates, so the work and, under "take all pairs", the *output* are quadratic in *k*. A sliding window does not make an all-pairs problem linear. It makes it proportional to the answer, which is the best any implementation of this specification can do.

The test suite compares `window_pairs` with the oracle on 500 random inputs of up to 120 hits, with random windows and between one and five modules, comparing whole output vectors. That catches a missing pair, an extra pair and a pair in the wrong order, none of which a count would reliably catch.

### Implementation 3: streaming

A pipeline cannot collect all hits and then sort; it must emit coincidences while hits are still arriving, from batches whose boundaries have nothing to do with the physics. Split the worked example into two chunks, [(0, A), (2, B)] and [(5, A), (12, C)], and process each chunk with `window_pairs` separately: pair (1, 2) is lost, because its two hits are in different chunks. A streaming sorter must keep, across chunk boundaries, every hit that could still pair with a future hit, and no more.

`StreamingSorter` keeps those hits in a fixed-capacity ring, allocated once, so pushing a hit never allocates:

```cpp
template <class Sink>
Status push(const Hit& h, Sink&& sink) {
    if (have_last_ && h.tick < last_tick_) { ++c_.out_of_order; return Status::out_of_order; }
    have_last_ = true;
    last_tick_ = h.tick;
    ++c_.hits_in;
    // Retire hits that are now too old for this and every later hit.
    while (head_ != tail_ && h.tick - ring_[head_ & mask_].tick > window_) ++head_;
    for (auto i = head_; i != tail_; ++i) {
        const Hit& r = ring_[i & mask_];
        if (r.module != h.module) { sink(Coincidence{r, h}); ++c_.pairs_out; }
    }
    Status st = Status::ok;
    if (tail_ - head_ == cap_) { ++head_; ++c_.forced_evictions; st = Status::evicted_oldest; }   // full: say so
    ring_[tail_++ & mask_] = h;
    // ... update retained_peak
    return st;
}
```

It is `window_pairs` turned inside out: the retained ring plays the role of `hits[first..j)`, and the pairs come out in the same order. The ring uses the monotonic-index technique of Chapter 8's `SpscRing`, but with no atomics, because one thread owns it entirely.

Two things can go wrong, and both are counted and reported instead of hidden:

- **Out-of-order input.** The sorter requires sorted input; a hit earlier than its predecessor is rejected and counted. Making it the merger's job to sort (below) keeps that requirement easy to meet.
- **Overflow.** A bounded time window does *not* bound memory: if enough hits arrive within one window, more must be retained than any fixed buffer holds. When the ring is full, the oldest hit is evicted early and the pairs it would have formed are lost. That is a policy, and like every loss in Chapter 19 it is counted (`forced_evictions`). In the example run the peak was 11 retained hits against a capacity of 1,024.

The streaming output must equal the batch output for every way of cutting the input into chunks. The test does exactly that: for 60 random inputs of 40 hits, it tries every split position, including empty chunks at either end, and compares with `window_pairs`. Another test sends ten hits with the same timestamp, the densest possible window, and checks both the 25 cross-module pairs and that a ring of four reports six forced evictions.

### Merging sources with watermarks

The sorter needs one time-ordered stream; the hardware delivers several. Each source's own hits are in order (the simulated sources guarantee it with a small reorder heap, as front-end electronics do), but the sources are independent threads with independent delays. When the merger holds a hit at time *t* from source 0, it cannot know whether source 1 will still deliver something earlier.

The solution is a **watermark**. With each batch, a source sends a *promise*: no hit it sends from now on will be earlier than *P*. The merger's watermark is the minimum promise over all open sources, and any buffered hit earlier than the watermark is final: no source can still send anything before it. `WatermarkMerger` in `include/llds/pet/merge.hpp` buffers each source's hits in its own fixed ring and emits, in time order, everything below the watermark:

```cpp
std::uint64_t watermark() const noexcept {
    std::uint64_t w = kClosed;
    for (const auto& s : src_) w = s.promise < w ? s.promise : w;
    return w;
}

template <class Sink>
std::size_t drain(Sink&& sink) {
    const std::uint64_t w = watermark();
    std::size_t n = 0;
    for (;;) {
        Source* best = nullptr;
        for (auto& s : src_) {
            if (s.head == s.tail) continue;
            const Hit& h = s.buf[s.head & mask_];
            if (h.tick >= w && w != kClosed) continue;
            if (!best || h.tick < best->buf[best->head & mask_].tick) best = &s;
        }
        if (!best) return n;
        sink(best->buf[best->head++ & mask_]);
        ++n;
    }
}
```

With a handful of sources a linear scan of the heads is faster than a heap. Ties between sources are broken by source index, so the output is deterministic, which the test relies on: 200 random interleavings of up to four sources must produce exactly a stable sort of all their hits.

The promise must be **correct**, and getting it right is subtler than it looks. While writing the example, the first version of the source sent "the current event time" as its promise. But a source's reorder heap can still hold hits earlier than that, which it sends in the *next* batch, breaking its own promise. The merger detected it (it refuses a hit below its source's promise), and the fix is to promise the minimum of the event time and the earliest hit still buffered. This is the general rule for watermarks: a promise must cover everything the source has not yet sent, not just what it has not yet seen.

A watermark also has a **liveness** problem, visible in its definition: a source that stops sending stops the watermark, and with it the whole merge. That is not a bug in the merger; it is the contract. Real systems add heartbeats, so that an idle source still advances its promise, and a timeout, after which a silent source is *excluded*: closed, with a fault recorded saying that its data is missing from that point. The test "a silent source holds the watermark" shows both halves. And because each source's buffer is bounded, a stalled watermark eventually fills the other sources' buffers too, at which point the sorter stops taking their batches and backpressure (Chapter 19) reaches the one place allowed to drop. The bound on per-source buffering is therefore also a bound on how much disorder between sources the system tolerates.

### Estimating the randoms

Reconstruction needs to know how many of the prompt coincidences on each line of response are randoms, so that it can correct for them. One standard estimate is the **delayed window**: pair each hit with the hits that arrive about *D* later, where *D* is far longer than any true time difference (tens of nanoseconds, say). No true or scattered pair can be that far apart, so every delayed coincidence is random, and because randoms are uncorrelated in time, the delayed count estimates the randoms in the prompt window of the same width. The delayed window must have the same shape as the prompt window, here "each hit pairs with later hits at most `window` after it", shifted by *D*; a wider delayed window counts proportionally more randoms. Exercise 20.2 implements the count with the same two-pointer idea as the sliding window. (The other common estimate computes 2τ·*S*₁·*S*₂ from the singles rates.)

### Summary

- Prompt coincidences are trues, scatters and randoms. Randoms scale with the window width and the product of the singles rates.
- Window schemes (multiple or single) and multiples policies (take all, kill, take winner) change the science; specify them exactly.
- Keep an O(n²) oracle as the executable specification and compare whole outputs, not counts.
- The sliding window is O(n + C); dense windows are still quadratic. A bounded window does not bound memory.
- A streaming sorter must equal the batch result for every chunking. Count rejections and evictions.
- Merge sources with watermarks. A promise must cover everything not yet sent; a silent source stalls the merge and must be detected and excluded.
