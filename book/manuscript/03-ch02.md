## The Memory Hierarchy, in Nanoseconds {#ch02}

A modern CPU core can retire four or more instructions per nanosecond. It can only do that if the data those instructions need is already close by. Memory is not a flat array of bytes with uniform access cost; it is a hierarchy of caches, each larger and slower than the one above it, glued together by a coherence protocol that keeps every core's view consistent. Almost every performance effect in concurrent programming, from false sharing to the cost of a lock, is a consequence of how this hierarchy works.

This chapter measures the hierarchy, explains the coherence protocol in enough detail to predict the cost of sharing data between cores, and introduces the layout techniques used in every data structure later in the book.

### Caches and cache lines

Between a core and DRAM sit several levels of cache. A typical server core in the mid-2020s has:

| Level | Size (per core unless noted) | Latency | Shared by |
|---|---|---|---|
| L1 data | 32–64 KiB | 4–5 cycles (~1.5–2 ns) | one core |
| L2 | 1–2 MiB | 12–16 cycles (~4–6 ns) | one core |
| L3 (last-level cache) | 1.5–4 MiB per core, 30–500 MiB total | 40–80 cycles (~15–40 ns) | all cores on a die or socket |
| DRAM | gigabytes | ~80–150 ns | the whole socket |
| Remote NUMA DRAM | gigabytes | ~130–250 ns | another socket |

Caches do not store individual bytes. They store **cache lines**, aligned blocks of 64 bytes on every mainstream x86-64 and ARM server core (Apple's M-series cores use 128-byte lines). When you load one byte, the whole 64-byte line containing it is brought into L1. When you write one byte, the core must own the whole line.

Two consequences follow immediately and will come up again and again:

1. **Spatial locality is free.** Once you have paid for one byte of a line, the other 63 cost almost nothing. Arrays of small, contiguous elements are cheap to scan; linked structures that scatter elements across memory are not.
2. **Lines, not variables, are the unit of sharing.** Two variables that sit in the same line are, from the hardware's point of view, one object. If two cores write to them, they fight over the line even though the program never shares a variable.

The hardware also tries to hide latency by **prefetching**: when it sees a regular access pattern (sequential addresses, or a constant stride), it fetches lines before they are asked for. Intel cores additionally have an *adjacent-line prefetcher* that, on a miss, fetches the line's 128-byte-aligned partner as well. That is why the companion library pads shared variables to 128 bytes, not 64, as you will see shortly.

### Measuring the hierarchy: the pointer chase

To measure the latency of each level, we need a sequence of loads that the CPU cannot overlap or prefetch. The classic technique is a **pointer chase**: build a random cyclic permutation of cache-line-sized nodes in a buffer, and follow it. Each load's address is the result of the previous load, so the loads are strictly serial, and the random order defeats the prefetchers. The time per step is the load-to-use latency of whichever level of the hierarchy the buffer fits in.

Here is the heart of `examples/ch02_cache_latency.cpp`:

```cpp
struct alignas(64) Line {
    Line* next;
    char pad[56];
};

static double chase_ns(std::size_t bytes, std::uint64_t steps) {
    const std::size_t n = std::max<std::size_t>(bytes / sizeof(Line), 2);
    std::vector<Line> lines(n);
    std::vector<std::size_t> order(n);
    std::iota(order.begin(), order.end(), 0);
    std::shuffle(order.begin() + 1, order.end(), std::mt19937_64(42));
    for (std::size_t i = 0; i < n; ++i)
        lines[order[i]].next = &lines[order[(i + 1) % n]];

    Line* p = &lines[0];
    for (std::size_t i = 0; i < n; ++i) p = p->next;  // warm up
    const auto t0 = llds::now_ns();
    for (std::uint64_t i = 0; i < steps; ++i) p = p->next;
    const auto t1 = llds::now_ns();
    llds::do_not_optimize(p);
    return static_cast<double>(t1 - t0) / static_cast<double>(steps);
}
```

The program runs the chase for working sets from 4 KiB to 512 MiB. On the reference machine:

```text
 working set    ns/load
        4 KiB       1.80
       16 KiB       1.78
       32 KiB       1.80      <- L1 (48 KiB per core)
       64 KiB       5.68
      256 KiB       5.80
      512 KiB       6.47
        1 MiB       8.96      <- L2 (2 MiB per core)
        2 MiB      25.51
        4 MiB      37.06
        8 MiB      38.84      <- L3 (260 MiB shared) ...
       16 MiB     114.50      <- ... but now every load also misses the TLB
       64 MiB     145.17
      256 MiB     168.33
      512 MiB     184.62      <- larger than L3: DRAM plus TLB misses
```

![The pointer chase on the reference machine. Each plateau is one level of the hierarchy; the jump at 16 MiB is the TLB running out, not the cache.](figures/chart-chase.svg)

The plateaus are unmistakable. Up to 32 KiB every load hits L1 and costs 1.8 ns, about four cycles at 2.1 GHz. Between 64 KiB and 1 MiB loads hit L2 at around 6 ns. From 2 to 8 MiB we are in L3 at 25 to 40 ns.

The jump at 16 MiB needs explaining, because this processor's L3 is 260 MiB: a 16 MiB buffer fits in it many times over. The culprit is the **TLB**, the cache of virtual-to-physical address translations. With ordinary 4 KiB pages, the second-level TLB on this core holds 2,048 entries, which covers exactly 8 MiB. Beyond that, almost every load in the random chase needs a *page-table walk* before it can even look in the cache, and the walk is itself a short sequence of dependent memory accesses. The data is still in L3; finding it has become three times more expensive. Only at 512 MiB, beyond the L3, are we finally paying for DRAM as well.

This is a useful lesson in reading measurements: the obvious explanation (we fell out of the cache) was wrong, and only the hardware's published parameters showed why. Huge pages (2 MiB instead of 4 KiB) cover 4 GiB with the same TLB, and make the 16 to 256 MiB rows drop back towards L3 latency; Exercise 7 asks you to try it, and Chapter 11 and Appendix B show how to use huge pages in practice.

The ratio between the first and last rows is a factor of 100. A data structure whose hot operations touch three cache lines in L1 runs in single-digit nanoseconds. The same structure, scattered across a large heap, takes half a microsecond.

> **Design rule.** Count cache lines, not instructions. For most data-structure operations, the number of distinct cache lines touched, and where they live, predicts the cost far better than the number of instructions executed.

### Coherence: how cores agree on memory

Each core has its own L1 and L2. If two cores cache the same line and one of them writes it, the other's copy must be invalidated or updated, or the program would see stale data. The hardware mechanism that guarantees this is the **cache-coherence protocol**. Intel uses a variant called MESIF, AMD uses MOESI, and ARM's protocols differ in detail, but all of them are elaborations of **MESI**, named after the four states a cache line can be in within one core's cache:

- **Modified (M):** this core has the only copy, and it has been written. Memory is stale.
- **Exclusive (E):** this core has the only copy, and it matches memory.
- **Shared (S):** several cores may have read-only copies.
- **Invalid (I):** this core does not have the line.

![One cache line under MESI as two cores read and write it. A write by one core invalidates the other copy, and the next read by the first core has to fetch the line again.](figures/mesi.svg)

The rules that matter for performance are few:

1. **Reading** a line requires it to be in M, E or S in your cache. If it is not, you fetch it. If another core has it in M, that core must supply it (and usually downgrade to S).
2. **Writing** a line requires it to be in M or E in your cache. If it is in S, you must first *invalidate* every other copy. If it is in I, you must fetch it *and* invalidate every other copy (a "read for ownership").
3. Every such transfer or invalidation is a message through the on-chip interconnect, and costs tens of nanoseconds when the other core is on the same die and over a hundred when it is on another socket.

From these rules you can predict the cost of almost any sharing pattern:

- **Many readers, no writers:** after the first read, every core has the line in S. Reads are local and fast. Read-only sharing scales perfectly.
- **One writer, no readers:** the line stays in M in the writer's cache. Writes are local and fast.
- **One writer, one reader:** each write invalidates the reader's copy; each read after a write fetches the line back. The line ping-pongs. Each round trip costs a cross-core transfer.
- **Many writers:** each write must take the line exclusively from whoever had it last. Writes serialise on the line, and throughput collapses as you add cores.

This is why a shared counter incremented by all threads scales so badly, and why the data structures in this book go to great lengths to make every frequently written cache line have exactly one writer.

### False sharing

The most surprising consequence of line-granularity coherence is **false sharing**: two threads that write *different* variables still fight over the line if the variables share it.

`examples/ch02_false_sharing.cpp` makes this concrete. Two threads each increment their own counter 50 million times, with relaxed atomics so that nothing is shared at the language level. In the first run the counters are adjacent:

```cpp
struct Together {
    std::atomic<std::uint64_t> a{0};
    std::atomic<std::uint64_t> b{0};
};
```

In the second they are padded apart:

```cpp
struct Apart {
    alignas(llds::kFalseSharingRange) std::atomic<std::uint64_t> a{0};
    alignas(llds::kFalseSharingRange) std::atomic<std::uint64_t> b{0};
};
```

The result on the reference machine:

```text
sizeof(Together)=16  sizeof(Apart)=256
same line:       34.15 ns per increment
separate lines:   6.77 ns per increment
slowdown from false sharing: 5.0x
```

![False sharing measured: the same increments, five times slower when the two counters share a cache line.](figures/chart-false-sharing.svg)

Same code, same work, five times slower. On a two-socket machine the factor is often 10 to 50. The program contains no data race and no shared variable; the slowdown is entirely a property of memory layout.

False sharing is common in real code because it is invisible in the source. The usual culprits are:

- arrays of per-thread counters or per-thread state (`stats[thread_id]++`);
- a lock and the data it protects in the same line, contended by waiters spinning on the lock while the owner writes the data;
- a queue's head and tail indices declared next to each other;
- small objects allocated consecutively by different threads from the same allocator.

The fix is always the same: give each independently written variable its own line, by alignment, padding, or both.

### Padding in the companion library

The companion library defines its padding constants in `include/llds/common/cacheline.hpp`:

```cpp
inline constexpr std::size_t kCacheLine = 64;
inline constexpr std::size_t kFalseSharingRange = 128;

template <class T, std::size_t Align = kFalseSharingRange>
struct alignas(Align) Padded {
    T value;
    // ...
};
```

C++17 introduced `std::hardware_destructive_interference_size` for exactly this purpose: the minimum offset between two objects that avoids false sharing. In principle you should use it. In practice there are two problems. First, GCC warns that its value depends on `-mtune` flags and may differ between translation units, which would break the ABI of any type that uses it. Second, the value it reports (64 on x86) does not account for the adjacent-line prefetcher, which effectively makes the false-sharing range 128 bytes on Intel parts. The library therefore pins both values explicitly: 64 for "one cache line" and 128 for "far enough apart that neighbours never interfere".

`alignas(128)` on a member does two things: it places the member at an address that is a multiple of 128, and it makes the enclosing type's alignment at least 128, so its size is rounded up to a multiple of 128 as well. That is why `sizeof(Apart)` is 256: two members, each starting a fresh 128-byte block.

Padding is not free. It multiplies the memory footprint of small objects and can push a hot structure out of L1. Pad the things that are *written by different threads*; leave read-only data and single-thread data packed tightly.

### Hyper-threads

Most x86 server cores and some ARM cores run two hardware threads per physical core (Intel calls this Hyper-Threading; the generic term is simultaneous multithreading, SMT). The two hardware threads share the core's L1 and L2 caches and its execution units. Operating systems present each hardware thread as a separate CPU.

For our purposes this has two effects. Communication between two hyper-threads of the same core is cheap, because the data never leaves the shared L1. But the two threads compete for execution resources, so a latency-critical thread whose sibling is busy runs slower and less predictably. The usual low-latency practice is to disable SMT in the BIOS, or to leave the sibling of each critical core idle. `lscpu -e` shows which logical CPUs share a core.

### NUMA

On a machine with more than one socket, each socket has its own memory controllers and its own DRAM. A core can access memory attached to the other socket, but at a higher latency (typically 1.5 to 2 times) and lower bandwidth. This is **non-uniform memory access** (NUMA). Many large single-socket processors (AMD EPYC, for example) are internally divided into several NUMA-like domains as well.

Coherence traffic across sockets is also much more expensive than within one: a cache line transferred between cores on different sockets can cost 150 to 300 ns. Every cost in this book that involves a cross-core transfer gets worse, sometimes by a factor of three or more, when the cores are on different sockets.

The practical rules are:

- keep the threads of one pipeline, and the memory they share, on one NUMA node (`numactl --cpunodebind=0 --membind=0`);
- allocate memory from the thread that will use it ("first touch": Linux places a page on the node of the core that first writes it);
- use `lscpu` and `numactl --hardware` to learn the topology before choosing cores.

Our reference machine is a small single-node virtual machine, so its cross-core numbers are on the optimistic side. Expect worse on a large server, and much worse across sockets.

### What this means for data structures

The rest of the book relies on a handful of principles derived from this chapter. They are worth stating explicitly, because every design in Parts II to IV can be explained in terms of them:

1. **One writer per cache line.** Every line that is written frequently should be written by one thread. If two threads must write, give each its own line.
2. **Separate read-mostly data from write-heavy data.** A line that is read by many and written by one is fine *if writes are rare*; each write invalidates every reader's copy.
3. **Prefer contiguous memory.** Arrays beat linked structures because they use whole cache lines and work with the prefetcher. When you must link, keep nodes in a contiguous pool (Chapter 11).
4. **Batch cross-core communication.** Each cross-core transfer costs tens of nanoseconds regardless of how many bytes it carries (up to a line). Moving 64 bytes costs about the same as moving 8.
5. **Cache what other cores publish.** If you need to know another core's progress (a queue index, say), keep a local copy and only re-read the shared one when the local copy is not enough. This one idea makes the SPSC queue in Chapter 8 several times faster.

### Summary

- Memory is a hierarchy. L1, L2, L3 and DRAM latencies differ by a factor of about 100; on the reference machine they are roughly 1.8, 6, 30 and 120 to 185 ns.
- Caches move 64-byte lines. Spatial locality is free; scattered data is expensive.
- The coherence protocol (MESI and its variants) lets many cores read a line cheaply but serialises writers. A line written by one core and read by another ping-pongs between them.
- False sharing makes independent variables in the same line contend. Measured slowdown on the reference machine: 5×.
- Pad independently written data to 128 bytes; keep read-only and thread-private data packed.
- Hyper-threads share a core's caches and execution units; NUMA makes cross-socket memory and coherence expensive.
