## Bytes, Integers and Defensive Parsing {#f04}

Data acquisition software spends its life turning bytes from hardware into numbers and numbers into decisions. Both steps have traps that are easy to fall into and hard to see in testing: a struct is not a wire format, unsigned arithmetic wraps, signed arithmetic must not overflow, and a floating-point value can be "not a number". This chapter shows how to parse and compute defensively, and ends with the idea that runs through Part VI: a slow, obviously correct reference implementation is a valuable piece of engineering.

### A wire format is not a struct

Suppose a device sends records of exactly 16 bytes: an 8-byte timestamp, a 4-byte sequence number, a 2-byte module number and a 2-byte energy, all little-endian. (This is the synthetic format of Chapter 19.) It is tempting to write:

```cpp
const Hit* h = reinterpret_cast<const Hit*>(packet);   // don't
```

This is wrong in several independent ways. The `Hit` struct may have padding the wire format does not, or a different field order. The packet buffer may not be aligned the way a `Hit` must be. On a big-endian host the bytes would be read in the wrong order. And in C++ there is no `Hit` object at that address, so reading through the pointer is undefined behaviour even when the layout happens to match. It may pass every test on your machine and fail on the target.

Build the value from the bytes instead:

```cpp
template <class U>
std::optional<U> read_le(std::span<const std::byte> in, std::size_t at) noexcept {
    if (at > in.size() || in.size() - at < sizeof(U)) return std::nullopt;   // fits?
    U v = 0;
    for (std::size_t i = 0; i < sizeof(U); ++i)
        v |= static_cast<U>(static_cast<U>(std::to_integer<unsigned>(in[at + i])) << (8 * i));
    return v;
}
```

`std::byte` is raw storage, neither a character nor a number; `std::to_integer` turns it into one. *Little-endian* means the least significant byte comes first, so the bytes `01 02` mean 1 + 2 × 256 = 513. Building the value with shifts expresses that rule directly, and the code gives the same answer on any host.

Two details in it are easy to get wrong. The bounds check is written as two comparisons because `at + sizeof(U)` can itself overflow when `at` is huge, and then a wrapped sum would pass the check. And each byte is widened to `U` *before* it is shifted: the byte for position 7 is shifted by 56 bits, and shifting a 32-bit `int` by 56 is undefined behaviour.

Length is only the first check. After decoding, validate the *meaning*: a module number must be below the number of modules, for instance. A real protocol adds more (a version, a message type, a checksum, reserved bits that must be zero, resynchronisation after a bad record). Those rules come from the hardware team's specification; do not invent them, and do not skip them.

### Integer arithmetic that does what you meant

**Unsigned arithmetic wraps** modulo 2^N. That is well defined, but it is often not what the algorithm needs. The classic mistake is a distance between two timestamps:

```cpp
std::uint64_t d = a.tick - b.tick;           // wrong: if b > a this wraps to about 1.8e19
std::uint64_t d = a.tick > b.tick ? a.tick - b.tick
                                  : b.tick - a.tick;   // right: smaller from larger
```

Reaching for `std::abs` does not help: `std::abs(a.tick - b.tick)` on `std::uint64_t` does not even compile, because there is no unsigned overload (and the subtraction would already have wrapped). Casting to a signed type first is no better, since a difference above 2^63 does not fit.

Wrapping is sometimes exactly what you want. Sequence numbers in a 32-bit counter wrap from 0xffffffff to 0, and the number of records missing between `expected` and `seen` is `seen - expected` computed in `uint32_t`, which is correct across the wrap as long as fewer than 2^31 records are missing. Exercise 19.1 builds on that.

**Signed overflow is undefined behaviour**, not wrap-around. The compiler may assume it never happens and optimise accordingly, so `if (x + 1 < x)` can be deleted entirely. Check ranges *before* a signed operation that could overflow, or use an unsigned type with a documented modular meaning.

**Hardware counters are short.** A detector front end might count time in a 40-bit or 48-bit register that wraps every few minutes or hours. Software must *extend* it to a monotonic 64-bit value, which requires knowing the counter width, the maximum gap between readings and how much the input can be reordered. Without those assumptions, the same short counter value can mean different moments. The rest of this book assumes timestamps have already been extended, and says so wherever it matters.

**Name units.** A value called `tick` with a comment saying "picoseconds" is better than one called `time_ns` that is actually in some other unit. Every interface that carries a time should say which clock and which unit.

### Floating point: finite or not

Floating-point values include infinities and NaN ("not a number"). NaN compares false with everything, including itself, so `x < limit` and `x >= limit` are both false when `x` is NaN. A check written as a single inequality therefore lets NaN through on one side. And arithmetic on finite inputs can overflow to infinity. Validate inputs *and* results:

```cpp
inline std::optional<double> checked_calibrate(double raw, double gain, double offset) noexcept {
    if (!std::isfinite(raw) || !std::isfinite(gain) || !std::isfinite(offset) || !(gain > 0))
        return std::nullopt;
    const double e = raw * gain + offset;
    if (!std::isfinite(e)) return std::nullopt;
    return e;
}
```

Do not silently clamp out-of-range results to a limit. Clamping changes the meaning of the data and hides configuration errors. If saturation is part of the requirements, specify it, count how often it happens, and test it.

### The slow oracle

Before you write a fast implementation of anything, write a slow one that is obviously correct: a direct transcription of the specification, with no cleverness. For coincidence pairing (Chapter 20) that is a double loop over all pairs, O(n²), that anyone can check by reading it. It then becomes an *oracle*: on thousands of random inputs, the fast implementation must produce exactly the oracle's output. This catches missing results, extra results and wrong order, which a test that only checks a total does not.

An oracle checks that two implementations agree. It does not check that they implement the *right* rule. Both can faithfully implement a pairing policy that the physicists did not want. Write the rule down, have the people who own it review it, and keep the oracle as its executable form.

### Summary

- Never cast a byte buffer to a struct pointer. Check the length, then build each field from bytes.
- Validate meaning as well as length. Real protocols specify more checks than this book's synthetic one.
- Unsigned arithmetic wraps; subtract the smaller from the larger for distances. Signed overflow is undefined.
- NaN fails every comparison: use `std::isfinite`, on inputs and on results. Do not clamp silently.
- A slow, obviously correct oracle is the reference that fast code is tested against.
