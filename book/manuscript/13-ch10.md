## The Disruptor Pattern and Broadcast Rings {#ch10}

In 2010 the London Multi-Asset Exchange (LMAX) published a paper describing how its trading platform processed six million orders per second on a single thread, and the data structure that fed that thread. They called it the **Disruptor**. Its central idea is a ring buffer, like the SPSC ring, but one in which entries are not removed when they are read. Instead, every consumer reads every entry, at its own pace, and tracks its own position with its own sequence counter. Consumers can depend on each other's progress, which turns a single ring into an entire pipeline of stages with no queues between them.

This chapter explains the pattern, builds a single-producer Disruptor with dependent consumers, and compares a pipeline built on it with the same pipeline built from chained SPSC rings.

### From queue to log

A queue is destructive: popping an element removes it, so each element is seen by exactly one consumer. Many pipelines need something else. A market-data handler wants to journal every message to disk, replicate it to a backup, *and* process it, and it wants the journal and the replicator to run in parallel with processing, not in series. With queues, the producer must push each message into three queues (three copies, three hand-offs), or one consumer must forward to the next (serialising them).

The Disruptor replaces the queue with a **log**: a ring of pre-allocated entries, a producer cursor that says how far the log has been written, and one **sequence** per consumer that says how far that consumer has read. A consumer may read any entry up to the producer cursor (and up to the sequences of any consumers it depends on). The producer may overwrite an entry only when every consumer that must see it has moved past it.

```text
             producer cursor = 41
                     |
   ... [37][38][39][40][41][  ][  ] ...     ring of entries (pre-allocated)
             |       |
     journal = 38   parse = 40
                     |
            process = 39  (depends on parse)
```

Because entries stay in place, a consumer can annotate them (the parse stage writes its parsed fields into the entry) and a later stage can read the annotations. No data is copied between stages. And because each consumer's sequence is written only by that consumer, the single-writer principle from Chapter 2 holds everywhere: the producer writes the cursor and the entries, each consumer writes its own sequence (and its own fields of each entry), and nobody does a read-modify-write.

### Sequences

A sequence is a padded 64-bit counter. In `include/llds/queue/disruptor.hpp`:

```cpp
struct alignas(kFalseSharingRange) Sequence {
    std::atomic<std::int64_t> value{-1};
    std::int64_t get() const noexcept { return value.load(std::memory_order_acquire); }
    void set(std::int64_t v) noexcept { value.store(v, std::memory_order_release); }
};
```

The value is the highest sequence number the owner has *finished*. It starts at −1 (nothing yet). Signed integers make the "nothing yet" state natural and keep comparisons simple; at a billion entries a second a signed 64-bit counter lasts 292 years.

The `set` with release and the `get` with acquire are the publication pattern again. When the producer sets the cursor to *s*, everything it wrote into entries up to *s* becomes visible to any consumer that reads the cursor. When the parse stage sets its sequence to *s*, everything it wrote into entries up to *s* becomes visible to the process stage that depends on it. And when the last consumer sets its sequence to *s*, the producer may reuse the entries up to *s*.

### The ring

The class holds the entries, the producer cursor, the registered consumers and the *gating* set: the sequences the producer must wait for before wrapping around.

```cpp
template <class T>
class Disruptor {
public:
    explicit Disruptor(std::size_t capacity);

    // wiring (before any thread starts)
    Sequence& add_consumer(std::vector<const Sequence*> deps = {});
    void set_gating(std::vector<const Sequence*> gating);

    // producer
    std::int64_t claim(std::int64_t n = 1) noexcept;
    T& operator[](std::int64_t seq) noexcept;
    void publish(std::int64_t seq) noexcept;

    // consumer
    std::int64_t wait_for(std::int64_t seq, const std::vector<const Sequence*>& deps) const noexcept;
    std::int64_t available(const std::vector<const Sequence*>& deps) const noexcept;
};
```

The entries are allocated once, in the constructor, as an array of `T`. They are default-constructed and then reused for the life of the ring, which is another of the Disruptor's ideas: there is no per-message construction or allocation, only field assignment into an existing object.

#### The producer

```cpp
std::int64_t claim(std::int64_t n = 1) noexcept {
    const std::int64_t next = claimed_ + n;
    const std::int64_t wrap_point = next - cap_;
    if (wrap_point > gating_cache_) {
        std::int64_t min_seq;
        while (wrap_point > (min_seq = min_gating())) cpu_relax();
        gating_cache_ = min_seq;
    }
    claimed_ = next;
    return next;
}

void publish(std::int64_t seq) noexcept { cursor_.set(seq); }
```

To claim the next *n* slots, the producer computes the highest sequence it wants (`next`) and the sequence that slot last held one lap ago (`wrap_point = next - capacity`). It may proceed only if every gating consumer has finished `wrap_point`. Like the SPSC ring's producer, it keeps a cached copy of the slowest consumer's position (`gating_cache_`) and only recomputes the minimum over all gating sequences when the cache says it might be about to overrun. Then it writes the entry in place and publishes it by storing the cursor.

This is a single-producer Disruptor: `claimed_` and `gating_cache_` are plain members, written only by the producer. The original LMAX Disruptor also offers a multi-producer sequencer, which claims slots with an atomic `fetch_add` on the cursor and then needs a per-slot "available" flag, because slots can be published out of order. The single-producer version is faster and covers the common case: most pipelines have one thread reading the network or the sensor.

#### Consumers and batching

A consumer waits until the entries it wants are available, then processes *all* of the available entries before publishing its progress:

```cpp
std::int64_t wait_for(std::int64_t seq, const std::vector<const Sequence*>& deps) const noexcept {
    for (;;) {
        std::int64_t avail = cursor_.get();
        for (const Sequence* d : deps) avail = std::min(avail, d->get());
        if (avail >= seq) return avail;
        cpu_relax();
    }
}
```

`wait_for` returns the highest sequence the consumer may read, which may be well beyond the one it asked for. The consumer's loop in `examples/ch10_pipeline.cpp` looks like this:

```cpp
std::int64_t next = 0;
while (next <= last) {
    const auto avail = ring.wait_for(next, deps);
    for (; next <= avail; ++next) on_event(ring[next]);
    me.set(avail);  // one store per batch, not per event
}
```

This **natural batching** is one of the Disruptor's most valuable properties. When the consumer keeps up, each batch has one entry and latency is minimal. When it falls behind, batches grow automatically, the per-entry cost of reading the cursor and publishing the sequence is amortised over the batch, and the consumer catches up faster. Throughput rises exactly when it is needed, without any tuning parameter.

#### Dependencies

`add_consumer(deps)` registers a consumer that may only read entries that every sequence in `deps` has passed. In the example pipeline:

```cpp
llds::Disruptor<Event> ring(1024);
llds::Sequence& parse_seq   = ring.add_consumer();              // reads after the producer
llds::Sequence& journal_seq = ring.add_consumer();              // in parallel with parse
llds::Sequence& process_seq = ring.add_consumer({&parse_seq});  // only after parse
ring.set_gating({&process_seq, &journal_seq});                  // producer waits for the leaves
```

`parse` and `journal` both read straight after the producer and run in parallel. `process` reads an entry only after `parse` has filled in its parsed fields. The producer only needs to wait for the *last* stages of each branch (`process` and `journal`), because `process` can never be ahead of `parse`. Gating on fewer sequences makes `min_gating` cheaper.

### Measurements

`examples/ch10_pipeline.cpp` builds the same three-stage computation (produce, parse, process) twice: once with two SPSC rings between three threads, and once on a Disruptor with the extra journal consumer running in parallel. Each event carries its publish timestamp, and latency is measured at the process stage. As in Chapter 9, each version runs flooded (to measure capacity) and paced at one event per microsecond (to measure hand-off latency):

```text
chained SPSC  flood     7.49 M ev/s  e2e p50=270335 p99=  385023 ns
disruptor     flood     6.96 M ev/s  e2e p50=  5439 p99=  115711 ns  (+journal)
chained SPSC  paced     1.00 M ev/s  e2e p50=   499 p99=  348159 ns
disruptor     paced     1.00 M ev/s  e2e p50=   455 p99=  227327 ns  (+journal)
```

![The same three-stage pipeline on chained SPSC rings and on a Disruptor. Flooded, the chained rings queue up and the median grows fifty-fold; paced, the two are equal.](figures/chart-pipeline.svg)

Flooded, the two designs have similar capacity, about 7 to 7.5 million events a second, even though the Disruptor is also running a fourth thread (the journal) on this four-vCPU machine. But look at the latency under flood: the chained rings show a median of 270 µs, the Disruptor 5 µs. The chained version has two 1,024-entry rings, and when the producer floods them, both fill: an event waits behind up to 2,048 others (Little's law: 2,048 events at 7.5 million a second is 273 µs). The Disruptor has one ring, its stages read the same entries, and natural batching lets the downstream stages catch up in large gulps, so the effective queue depth stays much lower.

Paced, both deliver about 450 to 500 ns from publish to process at the median: two hand-offs between cores, as in Chapter 8. The p99 values in the hundreds of microseconds are, again, the virtual machine: with four or five busy-spinning threads on four vCPUs, every hypervisor or kernel interruption makes the next few hundred events queue up behind it. Because the measurement is open-loop (each event's latency is measured from its own publish time, Chapter 4), those queued events are all counted, as they should be.

### What the Disruptor gets right

It is worth listing the design principles, because they apply far beyond this one structure:

1. **Pre-allocate everything.** The entries exist for the life of the ring. Messages are written into them, not allocated.
2. **Single writer for every variable.** The cursor has one writer, each sequence has one writer, each field of an entry has one writer (the stage that fills it in).
3. **No locks, no RMWs on the single-producer path.** Every hand-off is a release store and an acquire load.
4. **Cache what you can.** The producer caches the slowest consumer's position.
5. **Batch naturally.** Consumers process everything available and publish once.
6. **Keep consumers independent.** A slow journal does not slow the processing stage until the ring is about to wrap.

### What it does not do

- **It does not drop.** If any gating consumer stops, the producer eventually blocks. A ring that feeds an optional consumer (a monitoring tap, say) must either not gate on it, accepting that it may miss entries, or detect that it has fallen too far behind and cut it off.
- **It is not a work queue.** Every consumer sees every entry. To spread work across several identical workers, either give each worker every *k*-th entry (worker *i* handles entries with `seq % k == i` and the producer gates on all of them) or put an MPMC queue after the ring.
- **Entries must be safe to reuse.** If an entry holds a `std::string` or a `std::vector`, assigning into it may allocate. Keep entries plain, or give them fixed-capacity buffers.
- **Waiting is the user's problem.** `wait_for` spins. The LMAX library offers several wait strategies (busy-spin, yielding, sleeping, blocking with a lock and condition variable); the trade-offs are exactly those in the table at the end of Chapter 9.

### Summary

- The Disruptor is a ring of pre-allocated entries that are read, not removed. Each consumer tracks its own sequence; the producer waits for the slowest gating consumer before wrapping.
- Consumers can depend on other consumers, which builds a pipeline with no queues and no copies between stages.
- Natural batching makes consumers process everything available and publish once, so they catch up quickly under load.
- Measured: similar capacity to chained SPSC rings (7 to 7.5 million events a second) while running an extra consumer, a median latency under flood of 5 µs instead of 270 µs, and the same 450 to 500 ns hand-off when paced.
- It never drops and every consumer sees every entry; design gating and entry types accordingly.

### Exercises

1. **Gating.** In the example pipeline, the producer gates on `process` and `journal` but not on `parse`. Prove that this is enough: show that `process`'s sequence can never exceed `parse`'s.

2. **Wrap point.** With a ring of 1,024 entries, the producer has claimed up to sequence 5,000 and wants to claim one more. Which sequence must every gating consumer have finished? Express the condition in terms of `claimed_`, the capacity and the minimum gating sequence.

3. **Multi-producer.** Sketch a multi-producer `claim` that uses `fetch_add` on a shared counter. Why is storing the cursor after writing the entry no longer enough, and how could a per-entry "published" flag (or sequence number, as in Vyukov's queue) fix it?

4. **Work splitting.** Show how to use one Disruptor to spread work across three identical workers, each processing a third of the entries. What is the gating set? What happens to latency if one worker is slow?

5. **Hands-on: Exercise 10.1, a batching consumer step.** Implement `drain()` in `exercises/ch10/drain.hpp`: process every entry available to a consumer (given its dependencies) in order, call the handler for each with an end-of-batch flag on the last one, then publish progress with one store. The tests check batching and that a dependent stage never overtakes its dependency. Then rewrite the consumers in `ch10_pipeline.cpp` to use your `drain()`.

6. **Hands-on: a slow journal.** Add a `std::this_thread::sleep_for(1ms)` every 10,000 entries in the journal consumer of `ch10_pipeline.cpp`. What happens to the end-to-end latency at the process stage? What changes if you remove `journal_seq` from the gating set? What can now go wrong?
