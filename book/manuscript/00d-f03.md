## Templates, Lambdas and Type Traits {#f03}

Almost every data structure in this book is a template, and almost every thread is started with a lambda. This chapter teaches you to read both, and to read the compile-time checks (type traits and `static_assert`) that the library uses to reject types it cannot handle safely.

### Reading a template one piece at a time

```cpp
template <class T, std::size_t N>
class ModRing {
    static_assert(N >= 2, "one slot always stays empty, so N >= 2");
    // ...
};

ModRing<std::uint32_t, 8> small;   // one type
ModRing<Hit, 1024> large;          // a different, unrelated type
```

`template <class T, std::size_t N>` describes a family of classes. `T` is a type parameter and `N` a value known at compile time. Each combination of arguments you use is *instantiated*: the compiler generates a separate class for it, so `ModRing<std::uint32_t, 8>` and `ModRing<Hit, 1024>` share source code but nothing else. Member functions are only compiled for the combinations, and the functions, you actually use.

`static_assert(condition, "message")` is checked during compilation. A ring with fewer than two slots cannot work, so the mistake is rejected before the program exists rather than discovered during acquisition.

### Type traits: asking questions about a type

A *type trait* is a compile-time question about a type. The answer is a `bool` constant, available with a `_v` suffix:

```cpp
std::is_trivially_copyable_v<Hit>           // true: copying Hit is a plain memory copy
std::is_nothrow_copy_assignable_v<Hit>      // true: assigning a Hit cannot throw
std::is_nothrow_constructible_v<T, Args...> // can T be built from Args without throwing?
```

The library uses traits to state the limits of an implementation honestly. The seqlock of Chapter 7 copies payloads as raw words, so it requires a trivially copyable `T`. The MPMC queue of Chapter 9 cannot recover if constructing an element throws half-way through an operation, so it requires a `noexcept` constructor. Supporting every type would add states and recovery paths that make the algorithm much harder to prove correct. Restricting the type, and saying so in a `static_assert`, is often the better engineering choice.

C++20 *concepts* express the same constraints with nicer error messages (`template <std::integral U>`); the library mostly uses `static_assert` because the message can explain the reason.

### Lambdas are objects

A lambda is an unnamed class with a call operator, created on the spot. The square brackets say what it captures from the surrounding scope:

```cpp
int limit = 10;
auto by_value = [limit](int x) { return x < limit; };   // stores a copy of limit
auto by_ref   = [&limit](int x) { return x < limit; };  // stores a reference to limit
auto implicit = [&](int x) { return x < limit; };       // captures what it uses, by reference
```

`[x]` copies `x` into the lambda; `[&x]` stores a reference. `[&]` and `[=]` capture whatever the body uses, which is convenient in a short function and dangerous in a long one, because the lifetime dependencies become invisible. In threaded code, write captures explicitly: a reference capture is a borrow, and Chapter F2's lifetime rules apply to it.

```cpp
std::uint64_t result = 0;
std::thread worker([&result] { result = 42; });
worker.join();
std::printf("%llu\n", (unsigned long long)result);  // safe: see below
```

Two separate facts make this correct. `result` outlives the worker, because it stays in scope until after the join. And `join()` does more than wait: everything the worker did *happens before* `join()` returns, so the main thread is guaranteed to see the write (Chapter F7 defines "happens before"). Capturing by reference provides neither fact. Reading `result` before the join, while the worker may be writing it, is a data race, which Chapter F5 shows is undefined behaviour, not just a stale read.

### Templates and lambdas together

Generic code often takes a lambda as a *sink* or *callback*. The streaming coincidence sorter of Chapter 20 takes one:

```cpp
template <class Sink>
Status push(const Hit& h, Sink&& sink) {
    // ... for each new pair:
    sink(Coincidence{r, h});
}

sorter.push(hit, [&](const Coincidence& c) { out.push_back(c); });
```

Because `Sink` is a template parameter, every call site gets its own instantiation with the lambda's body visible to the compiler, which can inline it completely. A `std::function<void(const Coincidence&)>` parameter would also work, but it erases the type, usually costs an indirect call, and may allocate if the lambda captures a lot. On a per-event path, prefer the template.

### Summary

- A template is a family of types or functions; each set of arguments is compiled separately.
- `static_assert` and type traits reject unsupported types at compile time. Narrow contracts are often the safer design.
- A lambda is an object. Explicit captures make lifetime dependencies visible; a reference capture is a borrow.
- `join()` both waits and makes the thread's writes visible. Capturing by reference does neither.
- Pass callbacks on hot paths as template parameters, not `std::function`.

### Exercises

1. **Instantiation.** How many distinct classes does a program contain if it uses `ModRing<int, 8>`, `ModRing<int, 16>` and `ModRing<unsigned, 8>`? Why might a header-only library therefore increase compile time but not run time?

2. **Choose the trait.** For each of these, name the trait you would `static_assert` and say why: (a) a queue that copies elements with `memcpy`; (b) a ring whose `try_push` is `noexcept` and copy-assigns into an existing slot; (c) a pool that destroys objects without calling their destructor.

3. **Capture bug.** A loop starts eight threads with `for (int i = 0; i < 8; ++i) ts.emplace_back([&] { work(i); });`. What is wrong, and what is the one-character fix?

4. **Callback cost.** Write the same `for_each_pair(span, window, f)` twice, once with `template <class F>` and once with `std::function`. Compile both at `-O2` and compare the generated loop (Compiler Explorer is fine). What changed?
