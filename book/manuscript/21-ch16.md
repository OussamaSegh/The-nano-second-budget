## Testing and Verifying Concurrent Code {#ch16}

Every structure in this book was tested, and every test passed. That statement is much weaker than it sounds. This chapter begins with a ring buffer that contains a real memory-ordering bug and passes a stress test of twenty million messages, and then builds up the set of tools that would have caught it: sanitizers, stress tests designed to provoke failures, model checkers that explore every permitted execution, and the habits of reasoning and review that keep bugs out in the first place.

### A bug that tests cannot find

`examples/ch16_stress.cpp` contains two versions of the simplest SPSC ring, identical except for one memory order:

```cpp
template <bool Buggy>
class Ring {
public:
    bool try_push(const Payload& p) {
        const auto t = tail_.load(std::memory_order_relaxed);
        if (t - head_.load(std::memory_order_acquire) == kCap) return false;
        slots_[t % kCap] = p;   // plain write, ordered only by the tail store
        tail_.store(t + 1, Buggy ? std::memory_order_relaxed : std::memory_order_release);
        return true;
    }
    bool try_pop(Payload& p) {
        const auto h = head_.load(std::memory_order_relaxed);
        if (h == tail_.load(Buggy ? std::memory_order_relaxed : std::memory_order_acquire)) return false;
        p = slots_[h % kCap];   // plain read
        head_.store(h + 1, std::memory_order_release);
        return true;
    }
    // ... kCap = 8, slots, padded head_ and tail_
};
```

In the buggy version, the tail is published with a relaxed store and read with a relaxed load. Nothing orders the write of the slot before the publication of the index, so a consumer may see the new tail and then read a slot whose contents have not arrived. By the rules of Chapter 3, this is a data race on `slots_`, and the program's behaviour is undefined.

The stress test pushes twenty million `Payload`s, each with four fields set to the same sequence number, through a ring of only eight slots (to maximise wrap-around), and checks every one on the consumer side. On the reference machine:

```text
correct ring: 0 bad reads out of 20000000
buggy ring:   0 bad reads out of 20000000
```

Zero failures, and that result is expected. The x86 memory model (TSO) never makes two stores from one core visible out of order, and never reorders two loads, so the hardware happens to provide the release and acquire orderings the code forgot to ask for. Only the compiler could break the program, by moving the slot write after the tail store, and today GCC does not. Tomorrow's GCC, a different optimisation level, inlining into a different caller, or the first deployment on an ARM server, an Apple laptop or an embedded board, and the bug appears: rarely, under load, as corrupted messages.

**Tests on x86 are not evidence that memory orderings are correct.** Everything else in this chapter follows from that sentence.

### A hierarchy of evidence

There is no single tool that proves a concurrent program correct, so practitioners combine several, each covering what the others miss. From cheapest to most thorough:

1. **Single-threaded tests** find logic errors: off-by-one capacities, wrong wrap-around arithmetic, bad empty and full conditions. Most bugs in concurrent code are of this kind, and they should be found before anything harder is attempted.
2. **Sanitizers** (ThreadSanitizer, AddressSanitizer, UndefinedBehaviorSanitizer) instrument the program and check every access during a run. They find data races, use-after-free and undefined behaviour in the executions that happen.
3. **Stress tests** run the structure hard, with invariants checked on every operation, to provoke rare interleavings. They are most valuable on weakly ordered hardware and with perturbation.
4. **Model checkers** explore *all* executions of a small test that the C++ memory model allows, including ones no real machine has ever produced. They find ordering bugs with certainty, on small cases.
5. **Reasoning and review**: a written happens-before argument for every synchronising operation, and a reviewer who checks it.

The library in this book uses levels 1 to 3 in its test suite, levels 4 and 5 in the design of its core structures, and its CMake build makes the sanitizer runs a one-line change.

### ThreadSanitizer

**ThreadSanitizer** (TSan), available in GCC and Clang with `-fsanitize=thread`, is the most effective single tool for concurrent C++. The compiler instruments every memory access and every synchronisation operation; at run time, TSan tracks the happens-before relation between threads with vector clocks, and keeps a shadow record of recent accesses to every 8 bytes of memory. When two threads access the same location, at least one access is a write, at least one is non-atomic, and neither happens before the other, it reports a data race, with both stacks.

The project builds a TSan configuration with:

```text
cmake -S . -B build-tsan -DLLDS_SANITIZE=thread -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-tsan -j && ctest --test-dir build-tsan -LE exercise
```

Run against the buggy ring, it reports the bug at once, on the first wrap-around (trimmed):

```text
WARNING: ThreadSanitizer: data race (pid=7353)
  Read of size 8 at 0x7ffe303857c0 by thread T2:
    #0 Ring<true>::try_pop(Payload&) examples/ch16_stress.cpp:45
    #1 operator() examples/ch16_stress.cpp:65
  Previous write of size 8 at 0x7ffe303857c0 by main thread:
    #0 Ring<true>::try_push(Payload const&) examples/ch16_stress.cpp:38
    #1 stress<Ring<true> > examples/ch16_stress.cpp:71
SUMMARY: ThreadSanitizer: data race examples/ch16_stress.cpp:45 in Ring<true>::try_pop(Payload&)
```

Line 38 is the slot write, line 45 the slot read. TSan does not need the race to produce a wrong value; it needs only to observe that the two accesses are unordered, which they are on every run. The correct ring, with release and acquire, produces no report. In this project's CTest configuration, the smoke test for `ch16_stress` is marked `WILL_FAIL` under TSan precisely because of this deliberate report.

Some details matter in practice.

**TSan sees only what runs.** It checks the executions that happen, not all possible ones. A race on a path the test never exercises, such as the "queue full" branch, is invisible. Combine TSan with tests that drive every branch, including small capacities and many threads.

**TSan understands atomics, not fences.** TSan models the ordering provided by atomic operations with memory orders, but GCC's TSan does not model standalone `std::atomic_thread_fence`, and warns about it at compile time (`-Wtsan`). Code that synchronises through fences, such as the seqlock of Chapter 7 and the reclamation schemes of Chapter 12, may produce false reports, or, worse, may hide a real race because TSan cannot see the fence's effect. This project silences the warning with `-Wno-tsan` and compensates in two ways: the seqlock's payload is read and written through relaxed atomic words, so TSan never sees a plain-memory race to report; and the fence-based code is checked by reasoning and by stress tests on its invariants. If your design relies on fences, know that TSan's verdict on it is weaker.

**TSan reports races, not ordering bugs on atomics.** If every shared variable is atomic, there are no data races by definition, and TSan is silent, even if the memory orders are too weak for the algorithm's logic. The store-buffering bug in hazard pointers (Chapter 12) is of this kind: the slot and the source pointer are both atomic, and a weak order causes a use-after-free, not a race. TSan might catch the *consequence* (a race between the free and the reader's access), but only if it happens during the run. Ordering bugs among atomics are the domain of model checkers.

**The cost** is a slowdown of about 5 to 15 times and 5 to 10 times the memory. That is fine for tests and too much for benchmarks: never measure performance under a sanitizer.

### AddressSanitizer and UndefinedBehaviorSanitizer

**AddressSanitizer** (`-fsanitize=address`) detects use-after-free, buffer overflows and leaks, by surrounding allocations with poisoned **redzones** and keeping freed memory in a **quarantine** for a while before reusing it. It is the essential tool for reclamation code: a hazard-pointer or epoch bug almost always shows up as a read of memory that was freed a few microseconds earlier, and ASan reports exactly that, with the stacks of the allocation, the free and the bad access. Exercise 12.1's test is designed to be run under ASan for this reason.

Custom allocators hide bugs from ASan, because ASan only knows about `malloc` and `new`. A pool that recycles slots never "frees" anything ASan can see. Pools can tell ASan what they are doing with the manual poisoning interface, `ASAN_POISON_MEMORY_REGION` and `ASAN_UNPOISON_MEMORY_REGION` from `<sanitizer/asan_interface.h>`: poison a slot when it is returned, unpoison it when it is handed out.

**UndefinedBehaviorSanitizer** (`-fsanitize=undefined`) catches signed overflow, misaligned accesses, invalid shifts and similar errors at small cost; this project combines it with ASan in one build (`-DLLDS_SANITIZE=address,undefined`). Misaligned atomics deserve a special mention: an `std::atomic<uint64_t>` that straddles a cache line, which can happen with packed structs or careless `reinterpret_cast`s, is not atomic on x86 (and faults on many ARM cores), and UBSan's alignment check finds it.

TSan cannot be combined with ASan in the same build, so a typical CI matrix has three configurations: Release (for benchmarks and the normal tests), TSan, and ASan with UBSan.

### Designing stress tests

A stress test that merely runs a structure for a long time finds little. One designed to provoke failure finds a lot. The tests in this book's suite follow a few rules.

**Check invariants on every operation, inside the payload.** Each message in `ch16_stress` carries the same value in four fields. A torn or stale read produces mismatched fields, which is detectable without knowing anything about timing. Sequence numbers, checksums, and "the sum of the fields is constant" serve the same purpose for other structures.

**Make capacities tiny.** A ring of 8 slots wraps around every 8 messages, so the full and empty conditions, where most bugs live, are exercised millions of times per second. A ring of 65,536 slots might never fill during a test.

**Compare with a sequential model.** For structures with richer semantics, record the operations and their results and check them against a sequential implementation. The skip list's test in `tests/test_maps.cpp` gives each of four threads the keys congruent to its index modulo 4, so that the threads' keys interleave and they contend on shared predecessors, while each thread's results remain predictable. Every insert and erase result is checked against a per-thread `std::set`, and the final contents against the union of the four sets. The general version of this idea is **linearizability checking**: record the start time, end time and result of every operation in a concurrent history, and search for a sequential order consistent with both the results and the real-time order. Tools such as Porcupine (Go), Knossos (Clojure) and Lincheck (Kotlin) automate it; for C++, the history-and-checker approach is easy to write for a specific structure.

**Perturb the schedule.** Interleavings that matter are rare because threads run at similar speeds. Break that symmetry: run more threads than cores; insert random short delays or `std::this_thread::yield()` calls at chosen points under a test-only macro; run the test with a noisy neighbour (`stress-ng --cpu 0`) on the same cores; vary pinning with `taskset`. `rr record --chaos`, from the `rr` record-and-replay debugger, deliberately randomises scheduling and lets you replay any failure deterministically afterwards.

**Run on weakly ordered hardware.** ARM machines (AWS Graviton, Ampere, Apple Silicon, Raspberry Pi) reorder stores with other stores and loads with other loads. A missing release or acquire that x86 hides will produce wrong values there, often within seconds. If your code will ever run on ARM, your CI must include an ARM runner, and even if it will not, an ARM runner is the cheapest model checker you can buy.

**Run long, and run many times.** Some interleavings need billions of operations. A nightly job that runs each stress test for an hour is cheap insurance.

### Model checking

A **model checker** for concurrent code takes a small test program and explores every execution that the memory model permits: every interleaving, and every value each atomic load is allowed to return. If any execution violates an assertion, it reports it, usually with the full execution. This is the only practical way to *prove* that a given test cannot fail, and the only tool that finds ordering bugs among atomics reliably.

The best-known tools for C and C++ are:

- **CDSChecker** and its successor **C11Tester** (Demsky and colleagues), which model the C11/C++11 memory model and run unmodified C++ code linked against their own threading library.
- **GenMC** (Kokologiannakis and Vafeiadis), a stateless model checker for C programs under the C11 model and under hardware models such as IMM, which is much faster than earlier tools on realistic tests.
- **Relacy Race Detector** (Dmitry Vyukov), a header-only C++ library: the test is written with Relacy's `rl::atomic` and `rl::var` types, and Relacy explores schedules exhaustively or randomly. It has long been a favourite of lock-free library authors.
- **CppMem** and **herd7**, which enumerate the outcomes of litmus tests (a few lines per thread) under the C++ model and under hardware models. They are the tools for answering "is this outcome allowed?".

A model-checking test is small, typically two or three threads performing a few operations each, because the number of executions grows exponentially. That is less of a limitation than it sounds: almost all memory-ordering bugs appear with two threads and two or three operations. Here is the message-passing pattern of the ring, as a GenMC test in C:

```c
#include <assert.h>
#include <pthread.h>
#include <stdatomic.h>

int slot;          /* plain data */
atomic_int tail;

void* producer(void* arg) {
    slot = 42;
    atomic_store_explicit(&tail, 1, memory_order_relaxed);   /* bug: should be release */
    return NULL;
}

void* consumer(void* arg) {
    if (atomic_load_explicit(&tail, memory_order_relaxed) == 1)  /* should be acquire */
        assert(slot == 42);
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, producer, NULL);
    pthread_create(&b, NULL, consumer, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    return 0;
}
```

GenMC reports, in a fraction of a second, that the program has a data race on `slot` (and, with the race made atomic, that the assertion can fail), and prints the execution graph that shows how. With release and acquire, it reports that all executions are correct. The same test run a billion times on x86 would never fail.

A practical workflow is to extract the synchronisation skeleton of each new structure (the atomics and the accesses they protect, with the data reduced to a few integers) into a model-checking test, and to keep the test in the repository next to the structure. When someone later "optimises" a memory order, the test says whether the change is legal.

For the design of new algorithms, before any code is written, **TLA+** and its model checker TLC are widely used in industry to check protocols at the level of steps and states. TLA+ does not model the C++ memory model, but it finds algorithmic errors (lost wake-ups, ABA, forgotten states) that no amount of C++-level checking would reveal as clearly.

### Reasoning and review

Tools find bugs; reasoning prevents them. Every synchronising operation in a concurrent structure should come with an explanation, in a comment next to it, of what it synchronises with and why. The library in this book follows a few rules that make reviews effective:

- **Every release has a named acquire.** A comment on each release store says which acquire load it pairs with and what data the pairing publishes, and vice versa. A release with no acquire partner is either unnecessary or a bug.
- **Every `relaxed` is justified.** A relaxed operation needs a reason: "only this thread writes it", "a counter whose value orders nothing", "re-validated by the CAS below".
- **Every `seq_cst` names its store-buffering pattern.** Chapter 3's rule: `seq_cst` is needed when a store must be ordered before a later load of a different variable. The comment says which store and which load.
- **Every field has an owner.** State, in the class, which thread writes each field and which threads read it. Fields written by more than one thread are the dangerous ones, and there should be very few.
- **Every allocation has a reclamation story.** Who frees this node, and how do they know no one is reading it?
- **Linearization points are written down.** For each operation, the single atomic step at which it takes effect.

A reviewer can check these rules mechanically, without simulating interleavings in their head, and most memory-ordering errors in code review are caught as violations of one of them.

### Testing in regulated software

In a medical device, an avionics system or a vehicle, verification is not only good practice but a regulatory requirement. IEC 62304 for medical device software, for instance, requires documented verification of each software unit and of its integration, with evidence that the verification was done. Concurrency is one of the areas where the evidence is hardest to produce, because a passing test proves so little. A credible verification record for a concurrent component typically contains: the written ordering argument; model-checking tests of its synchronisation skeleton, with their results; TSan and ASan runs of its unit and stress tests in continuous integration; stress tests run on the *target* hardware, for the specified duration; and run-time checks in the product (sequence numbers on every message, watchdogs on every pipeline stage) that detect and report a failure if one ever occurs. Chapter 18's patient-monitor pipeline includes the last of these.

### Summary

- A real memory-ordering bug (a relaxed publication in an SPSC ring) passed 20 million stress-test messages on x86 with zero failures. Tests on x86 are not evidence of correct memory orders.
- Combine evidence: single-threaded tests for logic, sanitizers for races and memory errors, invariant-checking stress tests for rare interleavings, model checkers for ordering, and written reasoning for everything.
- ThreadSanitizer found the bug on the first run. It sees only executions that happen, does not model standalone fences in GCC, and cannot see ordering bugs among atomics.
- AddressSanitizer is essential for reclamation code; teach it about custom pools with manual poisoning. Run Release, TSan and ASan+UBSan builds in CI.
- Stress tests should check invariants in the payload, use tiny capacities, compare with sequential models, perturb the schedule, and run on ARM.
- Model checkers (GenMC, CDSChecker/C11Tester, Relacy) explore every allowed execution of a small test and are the only reliable way to check memory orders among atomics.
- Review against explicit rules: every release names its acquire, every relaxed is justified, every field has an owner, every allocation has a reclamation story.
