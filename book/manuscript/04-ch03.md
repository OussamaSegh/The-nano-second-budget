## The C++ Memory Model {#ch03}

Chapter 2 explained what the hardware does when several cores touch memory. This chapter explains what the C++ language *promises* about it. The two are not the same. The hardware may reorder memory operations in ways the coherence protocol does not prevent; the compiler may reorder, merge, or delete them; and the language standard defines which of those transformations are allowed and which programs are meaningful at all. Every concurrent data structure in this book is correct only because of specific guarantees in the memory model, and every one of them would be broken by a single wrong `memory_order` argument.

The goal of this chapter is not to cover the standard's text exhaustively. It is to give you a precise working model, the handful of rules you need to write and review lock-free code, and the experience of watching the "impossible" happen on real hardware.

### Why there is a memory model at all

Consider two threads and two shared variables, both initially zero:

```cpp
int x = 0, y = 0;

// Thread 1          // Thread 2
x = 1;               y = 1;
int r1 = y;          int r2 = x;
```

Can both `r1` and `r2` end up 0? If the threads interleave in any order, at least one store happens before the other thread's load, so at least one of `r1` and `r2` must be 1. Intuitively, `r1 == 0 && r2 == 0` is impossible.

On real hardware it happens all the time. Each core has a **store buffer**: when a core executes a store, it puts the value into a private queue and carries on, and the value reaches the cache (and becomes visible to other cores) a little later. Meanwhile, the core's next instruction, the load, reads the cache directly. So thread 1's load of `y` can complete before thread 1's store to `x` is visible, and the same for thread 2. Both loads see 0.

Store buffers exist because they make single-threaded code much faster: a core does not have to wait tens of cycles for every store to reach the cache. Compilers reorder for similar reasons. The result is that the intuitive model, where every thread's operations happen in program order and interleave with other threads' operations (**sequential consistency**), is not what you get by default.

A memory model is a contract that tells you which reorderings can be observed by other threads and how to forbid the ones you care about.

### Data races are undefined behaviour

The single most important rule of the C++ memory model is this:

> If two threads access the same memory location, at least one of the accesses is a write, at least one is not atomic, and neither happens before the other, the program has a **data race**, and its behaviour is undefined.

Undefined, not "you might read a stale value". The compiler is entitled to assume that data races do not happen, and it optimises accordingly. It may keep a variable in a register across a loop (so a flag set by another thread is never seen), merge two stores into one, invent a temporary store, or tear a 64-bit write into two halves. The famous example is a busy-wait loop:

```cpp
bool ready = false;  // not atomic

void wait() {
    while (!ready) {}  // compiler may hoist the load: loops forever
}
```

Because `ready` is a plain `bool` and the loop body does not write it, the compiler may load it once and spin on the register. That is a correct optimisation *of a race-free program*, and since a race-free program cannot have another thread writing `ready` concurrently, the optimisation is allowed.

The fix is never `volatile`. In C++, `volatile` means "this access has side effects outside the program" (memory-mapped I/O); it does not make accesses atomic and does not order them with respect to other threads. The fix is `std::atomic`.

### std::atomic in brief

`std::atomic<T>` provides operations on a single memory location that are **indivisible** (no thread can observe a half-completed operation) and **race-free** by definition (concurrent atomic accesses never constitute a data race). For integral and pointer types it provides:

- `load(order)` and `store(v, order)`;
- `exchange(v, order)`: store `v`, return the previous value;
- `compare_exchange_weak(expected, desired, success, failure)` and `compare_exchange_strong(...)`: if the current value equals `expected`, replace it with `desired` and return true; otherwise copy the current value into `expected` and return false;
- `fetch_add`, `fetch_sub`, `fetch_and`, `fetch_or`, `fetch_xor` for integers (and C++26 adds `fetch_max` and `fetch_min`);
- C++20 `wait(old)`, `notify_one()`, `notify_all()`: block until the value changes from `old`, implemented with a futex on Linux.

`std::atomic<T>` works for any trivially copyable `T`, but it is only lock-free when the hardware has instructions of the right width. On x86-64 and AArch64 that means up to 8 bytes always and 16 bytes sometimes. Check with `std::atomic<T>::is_always_lock_free`; the library asserts it wherever it matters.

C++20 also added `std::atomic_ref<T>`, which applies atomic operations to an ordinary object for the duration of the reference. It is useful when a variable is accessed atomically in one phase of a program and non-atomically in another (for example, initialised single-threaded and then shared).

Every operation takes an optional `std::memory_order` argument. That argument is what this chapter is really about.

### Happens-before

The memory model is defined in terms of a relation called **happens-before**. Informally, if A happens before B, then B sees the effects of A, and everything that A saw. Happens-before is built from two ingredients:

1. **Sequenced-before:** within one thread, an operation that comes earlier in program order is sequenced before one that comes later. (There are subtleties with unsequenced sub-expressions, which do not matter here.)
2. **Synchronizes-with:** certain pairs of atomic operations in different threads create an edge between threads. The basic case: a **release** store to an atomic variable synchronizes with an **acquire** load of the same variable that reads the value written by that store.

Happens-before is (roughly) the transitive closure of these: if A is sequenced before a release store S, S synchronizes with an acquire load L in another thread, and L is sequenced before B, then A happens before B.

This one pattern, the release-acquire pair, is the foundation of nearly every data structure in this book. It is how a producer hands data to a consumer:

```cpp
Payload data;                       // plain, non-atomic
std::atomic<bool> ready{false};

// Producer
data = compute();                                 // (1)
ready.store(true, std::memory_order_release);     // (2) release

// Consumer
while (!ready.load(std::memory_order_acquire)) {} // (3) acquire, reads true from (2)
use(data);                                        // (4)
```

(1) is sequenced before (2); (2) synchronizes with (3) because (3) reads the value (2) wrote; (3) is sequenced before (4). So (1) happens before (4): the consumer is guaranteed to see the complete payload. And because the accesses to `data` are ordered by happens-before, there is no data race, even though `data` is not atomic.

The release store says: "everything I did before this is visible to whoever acquires it". The acquire load says: "everything the releasing thread did before its release is visible to me after this". Neither says anything about operations *after* the release or *before* the acquire, and neither says anything to a thread that does not take part in the pair.

### The memory orders

C++ has six memory orders. In practice you need four.

**`memory_order_relaxed`** guarantees atomicity and nothing else. Relaxed operations on a single variable are still coherent: all threads agree on one *modification order* for that variable, and a thread never sees the variable go backwards in that order. But relaxed operations impose no ordering on *other* variables. Use relaxed for counters and statistics, for variables that only one thread writes and whose value is not used to decide whether to read something else, and for the "data" part of a release-acquire hand-off.

**`memory_order_release`** (stores and read-modify-writes) prevents any memory operation before it in program order from being reordered after it. Combined with an acquire on the other side, it publishes everything written before it.

**`memory_order_acquire`** (loads and read-modify-writes) prevents any memory operation after it in program order from being reordered before it. Combined with a release on the other side, it makes everything published visible.

**`memory_order_acq_rel`** (read-modify-writes only) is both: an RMW that both acquires what previous releasers published and releases what this thread did before. Use it for CAS operations in the middle of a chain of hand-offs, such as swinging the tail pointer of a linked queue.

**`memory_order_seq_cst`**, the default, is acquire-release plus one more guarantee: all `seq_cst` operations in the program appear in a single total order that every thread agrees on, consistent with each thread's program order. That extra guarantee is exactly what is needed to forbid the store-buffering outcome above.

**`memory_order_consume`** was meant to be a cheaper acquire that only orders operations data-dependent on the loaded value. No compiler implements it as specified; all of them treat it as acquire, and the standard has deprecated it in effect. Do not use it.

### Watching the impossible happen

The companion example `examples/ch03_litmus.cpp` runs the store-buffering test (and its sibling, the message-passing test) two million times each, with different memory orders. Two threads, pinned to different cores, are released at the same moment by a spinning start line; each executes its half of the test; the main thread records the outcome. The store-buffering half is:

![Store buffering. Each core's store waits in its private store buffer while the following load reads the other variable from memory, so both loads can return 0.](figures/store-buffer.svg)

```cpp
// thread 1                         // thread 2
x.store(1, Store);                  y.store(1, Store);
r1 = y.load(Load);                  r2 = x.load(Load);
// count the trials where r1 == 0 && r2 == 0
```

Results on the reference machine:

```text
store buffering, 2000000 trials (count of r1 == r2 == 0)
  relaxed          : 152094
  release/acquire  : 158013
  seq_cst          : 0   (must be 0)
message passing, 2000000 trials (count of flag seen but data stale)
  relaxed          : 0   (0 on x86, nonzero possible on ARM)
  release/acquire  : 0   (must be 0)
```

With relaxed or release/acquire orders, the "impossible" outcome appeared in about 7.5% of trials. Release/acquire does not help, because the pattern needs a store followed by a load of a *different* variable to stay in order, and release/acquire only constrain operations relative to the release store and the acquire load themselves, not a store relative to a later load. Only `seq_cst` forbids the outcome. On x86, the compiler implements a `seq_cst` store as an `xchg` instruction (or `mov` followed by `mfence`), which drains the store buffer before continuing.

The message-passing test shows the other side. With relaxed orders, the C++ model allows the consumer to see the flag but stale data, because nothing orders the two stores or the two loads. On x86 it never happens: x86's memory model (**TSO**, total store order) never reorders two stores with each other or two loads with each other. The only reordering x86 allows is a store followed by a later load. ARM and POWER are weaker and do reorder stores and loads freely, so the same binary built for ARM would show violations.

That asymmetry is dangerous. Code with missing acquire and release annotations often runs perfectly on x86, passes every test, and breaks the day it is compiled for an ARM server, or the day a new compiler version reorders the relaxed operations itself (which the C++ model permits on any architecture). Chapter 16 shows how ThreadSanitizer catches these bugs on x86 by checking the program against the C++ model rather than against the hardware.

### What it costs

On x86, the hardware already gives you acquire on every load and release on every store, so `load(acquire)`, `store(release)` and their relaxed versions all compile to a plain `mov`. The only extra cost is that the compiler may not reorder across them. A `seq_cst` store, by contrast, needs a full fence. The single-thread measurements from `ch06_atomics` on the reference machine show this:

```text
  load(relaxed)            0.38 ns
  load(seq_cst)            0.73 ns
  store(release)           0.36 ns
  store(seq_cst)           6.66 ns
  fetch_add(relaxed)       6.97 ns
  compare_exchange        11.81 ns
```

A `seq_cst` store costs about 18 times more than a release store. Every read-modify-write on x86 is a `lock`-prefixed instruction that is already a full barrier, so `fetch_add` costs about the same whatever order you pass it. (The sub-nanosecond loads are loop-amortised: the CPU overlaps independent loads, so the numbers show throughput, not latency.)

On ARMv8, acquire loads and release stores have dedicated instructions (`ldar`, `stlr`), which are cheap but not free; relaxed operations are plain loads and stores; and `seq_cst` loads also become `ldar`. ARMv8.1 added single-instruction atomic RMWs (`ldadd`, `cas`), which matter a great deal for contended counters. Appendix A has the full mapping for both architectures.

The practical consequence: on x86, choosing release/acquire instead of `seq_cst` saves you a fence on every store. On ARM it saves more. And on both, using relaxed where it is correct lets the compiler optimise around the operation.

### Fences

`std::atomic_thread_fence(order)` is a free-standing barrier that orders surrounding operations without being attached to a particular variable. A release fence followed by a relaxed store behaves like a release store, as far as synchronisation is concerned; a relaxed load followed by an acquire fence behaves like an acquire load. Fences are useful when one barrier must cover several atomic operations, or when the operation that must be ordered is a relaxed one you cannot change.

The sequence lock in Chapter 7 is the canonical example: the reader performs several relaxed loads of the data and then needs them all to be ordered before a final load of the sequence counter. No single acquire load can express "the loads before me must complete before me" (acquire orders operations *after* it), so the reader uses an acquire fence:

```cpp
const auto s1 = seq_.load(std::memory_order_acquire);
for (std::size_t i = 0; i < kWords; ++i)
    buf[i] = data_[i].load(std::memory_order_relaxed);
std::atomic_thread_fence(std::memory_order_acquire);  // keep data loads before s2
const auto s2 = seq_.load(std::memory_order_relaxed);
```

A `seq_cst` fence (`std::atomic_thread_fence(std::memory_order_seq_cst)`) is the strongest tool available: it participates in the single total order of `seq_cst` operations and prevents store-load reordering. Hazard pointers (Chapter 12) need exactly this, because they are a store-buffering pattern: a reader stores "I am using this pointer" and then loads the pointer again, while a reclaimer stores "this pointer is retired" and then loads the readers' slots.

### The rules you actually use

Here is the working model, distilled. Each rule is justified above; every data structure in this book follows them.

1. **Every shared variable that is written while another thread may access it must be atomic**, or protected by a lock, or ordered by happens-before through some other atomic. No exceptions.
2. **To hand data from one thread to another**, write the data (atomically or not), then store a flag or index with **release**; the other thread loads the flag or index with **acquire**, then reads the data.
3. **To hand a slot back** (the consumer has finished reading and the producer may overwrite it), the same rule in reverse: the consumer stores its progress with release, the producer loads it with acquire.
4. **A variable that only one thread writes** can be read by that thread with relaxed (or as a plain variable, if no other thread ever reads it).
5. **Counters and statistics** that do not guard other data use relaxed.
6. **CAS operations that both consume and publish** (for example, linking a node and swinging a pointer) use acq_rel on success; the failure order can usually be relaxed or acquire.
7. **If correctness depends on a store being visible before a later load of a different variable** (store-buffering patterns: Dekker's algorithm, hazard pointers, some wake-up protocols), you need `seq_cst` on both sides, or `seq_cst` fences.
8. **When in doubt, use `seq_cst`**, get it right, then weaken one operation at a time with a written justification for each and a test under ThreadSanitizer.

### Compiler barriers versus memory barriers

The `asm volatile("" ::: "memory")` construct you will see in the benchmark harness (`llds::clobber_memory()`) is a **compiler barrier**: it tells the compiler that memory may have changed, so it cannot cache values in registers across it or move memory operations past it. It emits no instruction and has no effect on the hardware. It is useful in benchmarks, to stop the optimiser from deleting the code being measured, and it is never a substitute for atomics in concurrent code.

### Summary

- Hardware (store buffers, out-of-order execution) and compilers both reorder memory operations; the memory model says which reorderings other threads may observe.
- A data race (concurrent non-atomic access with at least one write) is undefined behaviour. `volatile` does not help; `std::atomic` does.
- Release-acquire pairs create happens-before edges between threads. They are how data is published.
- Relaxed gives atomicity only. Acquire and release give one-directional ordering. `seq_cst` adds a single global order and is the only order that forbids store-buffering outcomes.
- On the reference machine, the store-buffering outcome appeared in 7.5% of trials without `seq_cst`, and never with it.
- x86 never reorders store-store or load-load, so many ordering bugs are invisible there and appear on ARM. Test against the model, not the machine.
- A `seq_cst` store costs about 18 times more than a release store on x86. Use the weakest order that is correct, and justify it.
