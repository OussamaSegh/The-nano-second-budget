## Safe Memory Reclamation {#ch12}

Every lock-free structure that allocates nodes eventually has to free them, and that is where most lock-free code written from scratch goes wrong. Chapter 6 met the problem in the Treiber stack, where a popped node might still be read by a thread that loaded the head a moment earlier, and Chapter 9 used hazard pointers in the Michael-Scott queue with a promise to explain them later. This chapter keeps that promise. It states the problem precisely, measures four ways of solving it, builds hazard pointers and epoch-based reclamation in detail, and shows where read-copy-update and the new C++26 facilities fit.

### The problem

Consider the simplest shared structure there is: one atomic pointer to an immutable object, read by many threads and occasionally replaced by one.

```cpp
std::atomic<Config*> current;

// reader, millions of times per second
const Config* c = current.load(std::memory_order_acquire);
use(c->limits);                       // (1)

// writer, a few times a minute
Config* old = current.exchange(new Config(next));
delete old;                           // (2)
```

The reader loads the pointer, and then, however briefly, uses it. If the writer's exchange and `delete` happen between the reader's load and its use at (1), the reader dereferences freed memory. The window is a few nanoseconds wide, the program usually works, and when it fails it reads garbage or crashes far from the bug. With a lock, the problem does not arise: the writer cannot replace the pointer while a reader holds the lock. Without one, *the writer has no way of knowing whether a reader is still using the old object*.

**Safe memory reclamation** (SMR) is the name for the schemes that give it a way. They all have the same two-sided shape:

- Readers do something cheap to announce what they might be using: a pointer (hazard pointers), a time period (epochs), or nothing at all but their own progress (quiescent-state RCU).
- Writers do not free a removed node; they **retire** it. The scheme frees a retired node once it can prove that no reader can still reach it.

A retired node has been unlinked from the structure, so no *new* reader can find it. The only question is whether some *old* reader still holds a pointer to it, and every scheme in this chapter is a different way of answering that question.

Two simpler answers are worth knowing before the clever ones.

**Never free.** If the set of nodes is bounded, allocate them all from a pool (Chapter 11) and recycle them, but never return the memory to the system. A late reader then reads a *valid* node, possibly a recycled one, and the algorithm must be designed to detect that (the version counters of Chapter 6's tagged pointers, or the sequence numbers of the Vyukov queue in Chapter 9). This is called **type-stable memory**, and it is how many production queues and pools work. It does not help when nodes contain owned resources (strings, vectors) or when readers follow pointers inside a recycled node.

**Reference counting.** Give every object a counter; readers increment it before use and decrement it after; the last one out frees. `std::shared_ptr` does this, and C++20's `std::atomic<std::shared_ptr<T>>` makes the pointer itself atomically replaceable. It is correct, general, and easy to use. Its cost is that every read is a *write* to the object's reference count, so every reader on every core writes the same cache line. That is precisely the pattern Chapter 2 measured as the most expensive thing a multicore machine does.

### Measurements

`examples/ch12_reclamation.cpp` measures the read side of four schemes. R reader threads repeatedly read two fields of a 64-byte `Config` through a shared pointer, while one writer replaces the object every 10 µs. Results on the reference machine:

```text
                       R=1                         R=3
mutex                  8.70 M reads/s  (115 ns)    2.37 M reads/s  (422 ns)
atomic<shared_ptr>     7.51 M reads/s  (133 ns)    1.04 M reads/s  (959 ns)
hazard pointers       27.02 M reads/s  ( 37 ns)   23.74 M reads/s  ( 42 ns)
epoch                 30.32 M reads/s  ( 33 ns)   26.11 M reads/s  ( 38 ns)
```

The figures are per reader, so a scheme that scales perfectly shows the same number in both columns.

The mutex is slow even with one reader, because the writer is also taking it a hundred thousand times a second and every acquisition moves the lock's cache line. With three readers, it is nearly four times slower per read.

`std::atomic<std::shared_ptr>` is worse than the mutex. The standard allows it to be implemented with an internal lock, and libstdc++ does exactly that: it uses a spin bit in the control-block pointer, so every `load()` takes a lock *and* increments the reference count, two contended writes per read. At three readers, a read costs almost a microsecond. It is a convenient tool for code that reads rarely; it is not a tool for a hot path.

Hazard pointers and epochs barely notice the extra readers: 37 to 42 ns and 33 to 38 ns respectively. Each reader writes only its own cache line, so readers do not interfere with each other at all. The remaining cost, about 70 cycles, is almost entirely one full memory fence per read, which we will meet in a moment and learn how to remove at the end of the chapter.

### Hazard pointers

Hazard pointers were published by Maged Michael in 2004 and are the most precise of the SMR schemes. Each thread owns a small number of **hazard slots**, single-writer multi-reader atomic pointers that live in a global array. To use a shared pointer safely, a reader writes it into one of its slots: "I am using this; do not free it". A thread that retires a node puts it on a private **retire list**. When the list gets long enough, the thread **scans**: it reads every hazard slot of every thread, and frees each retired node that does not appear in any slot.

The reader's side is a short loop (`include/llds/reclaim/hazard_pointers.hpp`):

```cpp
template <class T>
T* protect(const std::atomic<T*>& src) noexcept {
    T* p = src.load(std::memory_order_relaxed);
    for (;;) {
        slot_->store(p, std::memory_order_seq_cst);     // (a) announce
        T* again = src.load(std::memory_order_seq_cst);  // (b) validate
        if (again == p) return p;
        p = again;
    }
}
```

The loop is necessary because announcing is not enough on its own. Between loading `p` and storing it in the slot, the writer might have unlinked `p`, retired it, scanned, seen no hazard (the store had not happened yet), and freed it. So, after announcing, the reader checks that `src` still points to `p`. If it does, then `p` was still linked at a moment *after* the announcement became visible, so any scan that starts after the unlink will see the announcement. If it does not, the reader tries again with the new value.

The argument depends on a subtle ordering requirement. The reader does a store (to its slot) followed by a load (of `src`). The writer does a store (unlinking the node from `src`) followed by loads (of all the slots, during the scan). This is exactly the **store-buffering** litmus test of Chapter 3: unless each side keeps its store ahead of its load, each thread's store can sit in its store buffer while it performs its load, so the reader sees the old `src` *and* the writer sees an empty slot, and the node is freed while protected. Chapter 3's litmus test observed that outcome in about 7.5% of trials on the reference machine, with release/acquire as well as with relaxed orders.

![The hazard-pointer handshake. With seq_cst on both of the reader's operations and a seq_cst fence in the scan, either the scan sees the hazard or the reader's re-read sees the unlink.](figures/hazard-order.svg)

The fix is rule 7 of Chapter 3: `seq_cst` on both operations of each side, or a `seq_cst` fence between them. On the writer's side the scan begins with a `seq_cst` fence, which sits between the unlink and the slot loads. On the reader's side the announcement is a `seq_cst` store *and* the validating load is a `seq_cst` load. Both have to be `seq_cst`. A `seq_cst` store followed by an *acquire* load of a different variable is not ordered in C++, and on real hardware it is not ordered either. x86 happens to hide the mistake, because it compiles a `seq_cst` store to `xchg`, a full barrier, so a version with an acquire re-read passes every test on a PC. On ARMv8.3 and later, an acquire load can compile to `ldapr` (Appendix A), which may complete before the preceding `stlr` store is visible. On POWER, no barrier separates the store from the load at all. With both reader operations `seq_cst` (or with `std::atomic_thread_fence(std::memory_order_seq_cst)` between the store and a weaker re-read), the four operations take part in the single total order of `seq_cst` operations. The unlink comes before the writer's fence, and the announcement comes before the reader's load. Either the scan comes later in that order and sees the announcement, or the reader's re-read comes later and sees the unlink and retries. On ARM the cost of the `seq_cst` load over the acquire load is small: `ldar` instead of `ldapr`, once per protected pointer.

The writer's side:

```cpp
void retire(void* p, void (*deleter)(void*)) {
    auto& rec = my_record();
    rec.retired.push_back({p, deleter});
    if (rec.retired.size() >= kScanThreshold) scan(rec);
}

void scan(Record& rec) {
    std::atomic_thread_fence(std::memory_order_seq_cst);
    std::vector<void*> hazards;              // snapshot of all slots
    for (auto& r : records_)
        for (auto& s : r.slots)
            if (void* p = s.load(std::memory_order_acquire)) hazards.push_back(p);
    std::sort(hazards.begin(), hazards.end());
    std::vector<Retired> keep;
    for (auto& r : rec.retired) {
        if (std::binary_search(hazards.begin(), hazards.end(), r.ptr)) keep.push_back(r);
        else r.deleter(r.ptr);
    }
    rec.retired.swap(keep);
}
```

The scan threshold is what makes hazard pointers attractive for bounded-memory systems. With `H` hazard slots in the whole program, at most `H` retired nodes can be protected at any moment. A thread that scans once its list reaches `2H` frees at least `H` nodes per scan, so the scan's cost (proportional to `H`) is amortised over at least `H` retirements, and *the number of retired but unfreed nodes is bounded by a constant*, whatever the readers are doing. A reader that is preempted for a second while holding a hazard pointer keeps exactly one node alive.

That bound is the property that distinguishes hazard pointers from everything else in this chapter, and for a system that must run for months in a fixed memory budget it can be decisive.

The implementation details that make the code usable rather than just correct:

- **Guards.** `HazardDomain::Guard` is an RAII handle on one slot. The slot is cleared when the guard goes out of scope, so the protection lasts exactly as long as a C++ scope.
- **Thread exit.** A thread that exits with a non-empty retire list cannot simply free its nodes (some may still be protected) or drop them (that leaks). Our domain scans once more and hands the leftovers to a shared **orphan list**, which the next scanning thread adopts.
- **Slot count.** Traversing a linked list needs two slots, used hand-over-hand: protect the next node with one slot while still holding the current one with the other. The Michael-Scott queue needs two (head and its successor). Our domain gives each thread two; production libraries allow more.

The costs are equally clear. Every *pointer* a reader follows needs a protect, which means a full fence per hop. For a hash lookup that touches one node, that is fine; for a skip list search that visits thirty nodes, it is thirty fences, and hazard pointers become the wrong tool.

### Epoch-based reclamation

Epoch-based reclamation (EBR), described by Keir Fraser in 2004, protects *time periods* instead of pointers. There is a global epoch counter. A reader entering a **critical region** announces the current global epoch in its per-thread record; on leaving, it announces that it is inactive. Inside the region it may follow as many pointers as it likes, with no further synchronisation. Retired nodes are put on a list tagged with the epoch in which they were retired.

The global epoch advances from `e` to `e + 1` only when every *active* thread has announced `e`. So once the epoch has advanced twice past the epoch in which a node was retired, every thread has either been inactive or entered a new region since the retirement, and no region that might have seen the node is still open. The node can be freed.

![A node retired in epoch e is freed only once the global epoch reaches e + 2. By then, every reader region that could have loaded it has ended.](figures/epochs.svg)

Because only three epochs can be "live" at once (the current one and the two before it), each thread keeps three **limbo lists**, indexed by `epoch % 3`, and recycles them. The code (`include/llds/reclaim/epoch.hpp`) is short:

```cpp
class Guard {
public:
    Guard() : rec_(EpochDomain::global().my_record()) {
        if (rec_.nesting++ == 0) {
            auto e = EpochDomain::global().epoch_.load(std::memory_order_relaxed);
            rec_.local.store(e, std::memory_order_relaxed);
            std::atomic_thread_fence(std::memory_order_seq_cst);
        }
    }
    ~Guard() {
        if (--rec_.nesting == 0) rec_.local.store(kInactive, std::memory_order_release);
    }
    // ...
};

bool try_advance(std::uint64_t e) {
    std::atomic_thread_fence(std::memory_order_seq_cst);
    for (auto& r : records_) {
        if (!r.owned.load(std::memory_order_acquire)) continue;
        const auto l = r.local.load(std::memory_order_acquire);
        if (l != kInactive && l != e) return false;   // someone is still in an older epoch
    }
    return epoch_.compare_exchange_strong(e, e + 1, std::memory_order_acq_rel);
}
```

The fence in the guard plays the same role as the `seq_cst` store in `protect`: the announcement (a store) must be visible before the reader's loads of shared pointers, and the advancing thread's check of the announcements (loads) must not be reordered before its own unlink (a store). It is store buffering again, and the fix is again a full fence on each side.

Guards nest: only the outermost guard announces, so a function that takes a guard can call another that also takes one, at the cost of one counter increment. Retirement is amortised: every 64th `retire` call tries to advance the epoch and frees the oldest limbo list if it is safe.

Threads come and go, so records must be reused. `EpochDomain` has a fixed array of 128 records, and the limit applies to threads registered *at the same time*, not over the life of the process. When a thread exits, a `thread_local` handle runs one last collection. It then moves whatever is still in the thread's limbo lists to a shared **orphan list**, each node tagged with the current epoch, and releases the record for the next thread. Any thread's later collection frees orphans whose tag is at least two epochs old. An early version of the companion code kept the record owned forever. A process that started its 129th thread over its lifetime then found no free record: an `assert` in a debug build, and a null dereference in a release build, where `NDEBUG` removes the assertion. A long-running acquisition system that restarts worker threads (Part VI) would hit exactly that. Two lessons follow. A registry of per-thread records must handle thread exit as carefully as thread entry. And a check that protects memory safety must not be an `assert`, because release builds compile assertions out. Both domains now stop with a clear message in every build type, and the test suite runs 1,000 short-lived threads through each.

Compared with hazard pointers, EBR has three advantages. Reads are cheaper when they touch many nodes: one fence per region rather than one per pointer. The programming model is simpler: "everything you load inside a guard stays valid until the guard ends" is easier to get right than per-pointer protection. And traversals of any length, including range scans, need nothing extra; that is why Chapter 14's skip list uses epochs.

Its weakness is the mirror image of the hazard-pointer bound. **One stalled reader blocks all reclamation.** A thread that is preempted, or blocked on I/O, or stopped in a debugger, inside a guard keeps the epoch from advancing, and every node retired by every thread from then on stays in limbo. Memory grows without bound until the reader wakes. In a well-behaved low-latency system, where reader regions are short and threads are pinned and never block inside them, this is acceptable. In a system with long or unpredictable regions, it is not, and the usual mitigations (bounding limbo size and falling back to blocking, or combining epochs with hazard pointers as Hyaline and "hazard eras" do) add back the complexity that made EBR attractive.

| Property | Hazard pointers | Epochs |
|---|---|---|
| Reader cost | 1 fence per protected pointer | 1 fence per region |
| Long traversals | Hand-over-hand, fence per hop | Free |
| Unreclaimed memory | Bounded by a constant | Unbounded if a reader stalls |
| Stalled or crashed reader | Holds a few nodes | Blocks all reclamation |
| Programming model | Per pointer, must validate | Per scope |
| Typical use | Queues, stacks, maps with short lookups | Trees, skip lists, read-mostly snapshots |

### Read-copy-update

**Read-copy-update** (RCU) is a pattern and a family of reclamation schemes, made famous by the Linux kernel, where it protects routing tables, the module list, and thousands of other read-mostly structures. The pattern is the one this chapter started with:

1. Readers access the structure through a pointer, inside a read-side critical section, without locks.
2. A writer **copies** the part it wants to change, **updates** the copy, and publishes it with one atomic pointer store.
3. The writer waits for a **grace period**, a time after which every reader that might have seen the old version has finished, and then frees the old version.

Epoch-based reclamation is one way to implement step 3, and `RcuMap` in Chapter 13 does exactly that. The kernel's own implementation goes further. In a non-preemptible kernel, a read-side critical section cannot be interrupted by a context switch, so "every CPU has context-switched at least once" implies a grace period has passed, and `rcu_read_lock()` compiles to *nothing at all*. The reader's cost is zero.

User space cannot rely on that, but it can come close. The `liburcu` library offers several flavours, of which the fastest is **QSBR** (quiescent-state-based reclamation): each reader thread periodically calls `rcu_quiescent_state()` at a point where it holds no references (typically at the top of its event loop), and read-side sections are empty. Grace periods are detected by the writer observing that every reader has passed a quiescent state. For a pinned, event-loop-driven thread, the cost is one store per loop iteration, which is essentially free.

### Removing the fence

Both measured schemes spend most of their 35 to 40 ns on a full fence that exists only to order the reader's announcement against a writer that is almost never there. Since writers are rare, it would be better to make *them* pay.

Linux provides a way: the `membarrier()` system call, with `MEMBARRIER_CMD_PRIVATE_EXPEDITED`, makes the kernel issue a memory barrier on every CPU currently running a thread of the process. A reader can then announce with a plain store plus a *compiler* barrier (`std::atomic_signal_fence(std::memory_order_seq_cst)`), and the scanning or advancing thread calls `membarrier()` before it reads the announcements. The barrier on the reader's CPU, forced by the kernel, plays the role of the reader's fence. This is called an **asymmetric fence**. Folly's hazard pointers and `liburcu`'s `memb` flavour both use it, and it brings read-side cost down to a few nanoseconds. The writer pays a system call that interrupts every core the process is running on, so it is only a good trade when writes are rare.

### C++26: `std::hazard_pointer` and `std::rcu`

C++26 standardises both families, based on Folly's implementations (proposals P2530 and P2545). The hazard-pointer interface will look familiar:

```cpp
#include <hazard_pointer>

struct Node : std::hazard_pointer_obj_base<Node> { /* ... */ };
std::atomic<Node*> head;

// reader
std::hazard_pointer hp = std::make_hazard_pointer();
Node* n = hp.protect(head);          // the same announce-and-validate loop
use(n);                              // hp's destructor clears the slot

// writer
Node* old = head.exchange(fresh);
old->retire();                       // freed when no hazard pointer holds it
```

And the RCU interface:

```cpp
#include <rcu>

struct Config : std::rcu_obj_base<Config> { /* ... */ };
std::atomic<Config*> current;

// reader
{
    std::scoped_lock guard(std::rcu_default_domain());   // read-side section
    use(current.load(std::memory_order_acquire));
}

// writer
Config* old = current.exchange(fresh);
old->retire();                       // or std::rcu_retire(old); or std::rcu_synchronize(); delete old;
```

At the time of writing, standard library support for these headers is only beginning to appear, so check your implementation. Folly provides both today, and the `llds` versions in this book have deliberately similar shapes, so code written against them ports easily.

### Choosing

The decision rarely needs a table:

- If the object is small and trivially copyable, do not reclaim at all: copy it through a seqlock (Chapter 7).
- If nodes can be recycled within a fixed pool and the algorithm tolerates reading a recycled node, use type-stable memory.
- If readers touch one or two nodes per operation and memory must stay bounded, use hazard pointers.
- If readers traverse, or many pointers are read together, and reader regions are short, use epochs.
- If the structure is read millions of times per second and changed a few times a minute, copy the whole thing on write and reclaim the old one with whichever scheme you have (RCU). Chapter 13's `RcuMap` and Exercise 12.1 are both this pattern.
- If reads are rare, use `std::shared_ptr` and spend your effort elsewhere.

In the patient-monitor pipeline of Chapter 18, alarm limits are a configuration object of exactly the RCU kind: every channel reads them on every sample, and a clinician changes them a few times per shift. Readers must never block on the bedside UI thread that writes them, and a freed limits object read by an alarm thread would be a safety defect, not just a crash.

### Summary

- A lock-free reader holds pointers that a writer cannot see. Freeing a removed node immediately is a use-after-free that shows up rarely and far from its cause.
- Safe memory reclamation splits removal into unlinking (immediate) and freeing (deferred until no reader can hold the node). Readers announce what they use; writers retire instead of freeing.
- `std::atomic<std::shared_ptr>` turns every read into contended writes: 959 ns per read with three readers on the reference machine. A mutex was 422 ns.
- Hazard pointers (37 to 42 ns) protect individual pointers with an announce-and-validate loop. They need a full fence per pointer, and they bound unreclaimed memory by a constant.
- Epochs (33 to 38 ns) protect whole regions with one fence. They make traversals free, but one stalled reader stops all reclamation.
- Both fences guard against store buffering. Asymmetric fences (`membarrier`) move that cost to the rare writer.
- C++26 standardises both families as `std::hazard_pointer` and `std::rcu`.
