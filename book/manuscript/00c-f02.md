## Ownership, RAII, Moves and Exceptions {#f02}

Before data moves between threads, you need a clear answer to a simpler question: who is responsible for each resource, and when is it released? C++ answers it with ownership, expressed in types, and with RAII, which ties release to scope. This chapter covers both, then the move operations that transfer ownership, the place of exceptions, and the single most common lifetime bug in threaded code.

### Owners and borrowers

An *owner* is responsible for a resource's lifetime. A *borrower* may use the resource only while the owner guarantees it is alive. Resources are not only memory: an open file, a held lock, a running thread and a buffer lent to a device are all resources with owners.

`std::unique_ptr<T>` expresses single ownership. It cannot be copied, only moved, and moving it transfers ownership:

```cpp
auto buffer = std::make_unique<std::array<Hit, 64>>();
auto next_owner = std::move(buffer);   // buffer is now null; next_owner owns the array
```

`std::shared_ptr<T>` lets several handles share ownership; the object is destroyed when the last handle goes away. Two warnings come with it. Shared *ownership* is not shared *mutation*: two `shared_ptr`s to one object do not make unsynchronised writes to that object safe. And copying a `shared_ptr` updates an atomic reference count, which is cheap once per batch and expensive once per event in a hot loop (Chapter 12 measures it). Chapter 21 uses `shared_ptr` exactly where its cost is acceptable: for a calibration table that changes rarely and is picked up once per batch.

### Moves

`std::move(x)` does not move anything. It is a cast that says "I am done with `x`", which lets the compiler choose a *move* constructor or assignment, if the type has one, instead of a copy. A moved-from standard-library object is valid but in an unspecified state: you may assign to it or destroy it, but do not assume it is empty unless the type documents that (a moved-from `unique_ptr` is null; a moved-from `std::vector` is in practice empty, but the standard does not promise it).

### RAII: scope is a clean-up protocol

RAII (resource acquisition is initialisation) means acquiring a resource in an object's constructor and releasing it in its destructor. Then leaving the scope, by any path, releases the resource:

```cpp
{
    std::lock_guard lock(mutex);   // locks here
    update_shared_state();         // may throw
}                                  // unlocks here, also if an exception was thrown
```

The manual version, `mutex.lock(); update_shared_state(); mutex.unlock();`, leaves the mutex locked forever if `update_shared_state()` throws, and every other thread that needs it then waits forever. RAII makes the clean-up path part of the type structure, so no early `return` or exception can skip it.

### Exceptions, used deliberately

Exceptions are not slow when they are not thrown, and they are the right tool for failures that are rare and that the immediate caller cannot handle, such as an invalid configuration at start-up. They are the wrong tool for things that happen in normal operation, such as an empty queue on a poll. Distinguish four kinds of failure and give each its own mechanism:

| Situation | Example | Mechanism in this book |
|---|---|---|
| Invalid configuration | queue capacity 0, NaN calibration gain | throw at construction |
| Malformed external input | a record of the wrong length | return a status or empty optional |
| Temporary back-pressure | the ring is full | return `false`; the caller decides |
| Broken internal invariant | an index that cannot be out of range | a check that stops the program (a bug, not an input) |

`noexcept` on a function is a promise that no exception escapes it; if one tries, the program terminates. It is a contract, not a speed-up request. It matters in lock-free code for a reason Chapter 9 explains: once a thread has claimed a slot that other threads are waiting on, it must not fail before finishing, and `noexcept` is how the code states and checks that.

### The thread-lifetime trap

Here is the bug that this chapter exists to prevent:

```cpp
void start_logging() {
    std::vector<Hit> recent = load_recent();
    std::thread worker([&recent] { write_to_disk(recent); });  // borrows a local
    worker.detach();                                           // ... and outlives it
}   // recent is destroyed here, while worker may still be reading it
```

`[&recent]` captures a reference to a local variable. `detach()` lets the thread keep running after `start_logging` returns and `recent` is destroyed. The worker now reads freed memory. It will usually work in testing, because the thread usually finishes first, and fail in the field when the scheduler is busy.

Two rules prevent it. First, **do not detach threads**: keep every thread joinable and join it before destroying anything it uses. A detached thread has also lost any way to report errors or completion. Second, **destroy in the right order**. Class members are destroyed in reverse declaration order, so a class that owns both a worker thread and the buffers it uses must stop and join the worker before those buffers are destroyed. Declaring the thread last, so it is destroyed first, helps, but an explicit `stop()` that joins makes the order visible to the next reader. C++20's `std::jthread` joins in its destructor, which removes the "forgot to join" crash but not the ordering problem.

### Ownership at a hand-off

A worked example shows how far ownership reaches. An acquisition thread fills a reusable buffer, puts a `std::span<const Hit>` of it into a mutex-protected queue, and immediately starts filling the same buffer again. Is the queue's mutex enough?

No. The mutex protects the queue's own data, the span objects. It says nothing about the period during which the consumer reads the buffer the span points to, and the producer is already overwriting it. There are three correct designs, each with a different cost: transfer an owning buffer (allocation, or a pool); copy the data into the queue's own storage (copying); or lend the buffer and have the consumer explicitly give it back (a return protocol, as with the pools of Chapter 11). "The queue contains the pointer" is not an ownership argument. The question to ask is: *who may reuse this storage, and after which observable event?*

### Summary

- Ownership is expressed in types: `unique_ptr` for one owner, `shared_ptr` for shared ownership (not shared mutation).
- `std::move` is a cast. Moved-from objects are valid but unspecified.
- RAII ties release to scope, so exceptions and early returns cannot leak locks or memory.
- Match the failure mechanism to the failure: throw on bad configuration, return a status on bad input or back-pressure.
- Never detach. Join every thread before destroying what it uses, and mind member destruction order.
