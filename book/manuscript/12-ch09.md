## MPSC and MPMC Queues {#ch09}

The SPSC ring of Chapter 8 is fast because every variable has exactly one writer. The moment two producers share a queue, that property is gone: they must agree on who writes which slot, and agreement between threads means a read-modify-write on a shared cache line. This chapter is about paying that cost as few times as possible. We build two classic multi-producer multi-consumer (MPMC) queues, Dmitry Vyukov's bounded array queue and the Michael-Scott unbounded linked queue, compare them with a mutex-protected deque, and then add what every real queue needs and benchmarks usually forget: a way to wait.

### Before you reach for MPMC

The fastest MPMC queue is often no MPMC queue at all. If you have P producers and one consumer, P separate SPSC rings, which the consumer polls in turn, avoid all producer-producer contention. If you have one producer and C consumers that each handle a different subset of work (by key, by symbol, by patient), C SPSC rings with the producer routing each item give you ordering per key for free. Contention you design away is cheaper than contention you manage. Use a true MPMC queue when work items are interchangeable and any consumer may take any item, as in a thread pool.

### Vyukov's bounded MPMC queue

Dmitry Vyukov published this design on his site 1024cores.net around 2010. It is still the best general-purpose bounded MPMC queue, and its core idea is small enough to hold in your head: **give every slot its own sequence number**, and use it to tell producers and consumers whether the slot is ready for them.

The queue is an array of `capacity` cells (a power of two) and two shared counters, `enqueue_pos` and `dequeue_pos`. Each cell holds an element and an atomic sequence number `seq`. Initially cell *i* has `seq == i`.

For a position *pos* (a free-running counter, as in the SPSC ring) and its cell `cells[pos & mask]`:

- `seq == pos` means the cell is **free** for the producer that claims position *pos*.
- `seq == pos + 1` means the cell is **full**, holding the element for the consumer that claims position *pos*.
- After the consumer takes the element, it sets `seq = pos + capacity`, which means "free for the producer one lap later".

A producer reads `enqueue_pos`, looks at the corresponding cell's `seq`, and if it equals `pos`, tries to claim the position by CASing `enqueue_pos` from `pos` to `pos + 1`. If the CAS succeeds, the cell is the producer's alone: no other producer can claim the same position. It writes the element and then stores `seq = pos + 1` with release, publishing it. Consumers do the mirror image on `dequeue_pos`.

Here is the producer side from `include/llds/queue/mpmc_bounded.hpp`:

```cpp
template <class... Args>
bool try_emplace(Args&&... args) noexcept {
    static_assert(std::is_nothrow_constructible_v<T, Args...>);
    Cell* cell;
    auto pos = enqueue_pos_.load(std::memory_order_relaxed);
    for (;;) {
        cell = &cells_[pos & mask_];
        const auto seq = cell->seq.load(std::memory_order_acquire);
        const auto diff = static_cast<std::intptr_t>(seq) - static_cast<std::intptr_t>(pos);
        if (diff == 0) {
            if (enqueue_pos_.compare_exchange_weak(pos, pos + 1, std::memory_order_relaxed))
                break;  // slot claimed
        } else if (diff < 0) {
            return false;  // slot still holds an element from one lap ago: full
        } else {
            pos = enqueue_pos_.load(std::memory_order_relaxed);  // someone beat us
        }
    }
    new (&cell->storage) T(std::forward<Args>(args)...);
    cell->seq.store(pos + 1, std::memory_order_release);
    return true;
}
```

and the consumer side:

```cpp
bool try_pop(T& out) {
    Cell* cell;
    auto pos = dequeue_pos_.load(std::memory_order_relaxed);
    for (;;) {
        cell = &cells_[pos & mask_];
        const auto seq = cell->seq.load(std::memory_order_acquire);
        const auto diff =
            static_cast<std::intptr_t>(seq) - static_cast<std::intptr_t>(pos + 1);
        if (diff == 0) {
            if (dequeue_pos_.compare_exchange_weak(pos, pos + 1, std::memory_order_relaxed))
                break;
        } else if (diff < 0) {
            return false;  // empty
        } else {
            pos = dequeue_pos_.load(std::memory_order_relaxed);
        }
    }
    T* p = std::launder(reinterpret_cast<T*>(&cell->storage));
    out = std::move(*p);
    p->~T();
    cell->seq.store(pos + mask_ + 1, std::memory_order_release);  // free for next lap
    return true;
}
```

The three-way comparison is the heart of it. For a producer at position *pos*:

- `diff == 0`: the cell is free for this lap. Try to claim it.
- `diff < 0`: the cell's sequence is *behind* (it is `pos - capacity + 1`): it still holds an element from the previous lap that no consumer has taken yet. The queue is full.
- `diff > 0`: another producer already claimed *pos* and has published (or is publishing) it; our view of `enqueue_pos` is stale. Reload and retry.

Why are the CASes on `enqueue_pos` and `dequeue_pos` relaxed? Because they only decide *ownership* of a position; they do not publish data. Data is published by the release store to the cell's `seq` and consumed by the acquire load of it. Ownership and publication are separated, and each uses exactly the ordering it needs.

#### Properties

- **One CAS per operation**, on a counter shared only by threads of the same role (producers contend with producers, consumers with consumers). Producers and consumers never write the same counter.
- **No allocation.** The array is allocated once.
- **FIFO per producer.** Items from one producer come out in the order that producer pushed them. Across producers, order is by successful CAS on `enqueue_pos`.
- **Cells are cache-line aligned** in the library (`struct alignas(kCacheLine) Cell`), so neighbouring cells used by different threads at the same moment do not falsely share. This costs memory for small elements; for 8-byte elements an unpadded variant uses an eighth of the space at some cost in contention.

#### The catch: it is not quite lock-free

Suppose a producer claims position *pos* (its CAS succeeds) and is then preempted before it stores `seq = pos + 1`. A consumer at position *pos* now sees `diff < 0` (empty) and returns false, *even if positions pos+1, pos+2, ... have been filled by other producers*. The queue is stuck at *pos* until the preempted producer runs again. Consumers are not blocked forever (they return false rather than spin), but no consumer can make progress past that slot.

Formally, then, Vyukov's queue is not lock-free: one delayed thread can stop all consumers from making progress. In practice the window is a few instructions wide, and the trade is a good one: the alternatives that are strictly lock-free (Michael-Scott, below) pay with an allocation and several more atomics per operation, and the alternatives that are wait-free are slower still. But it is worth knowing, because a system that runs producers at a lower priority than consumers, or on oversubscribed cores, can see long stalls from it.

The same window has a second, less obvious consequence: **exceptions**. Once a producer has claimed a position, nobody else can release it. If the element's constructor threw between the claim and the `seq` store, the slot would stay "claimed but never published" forever, and the queue would be stuck at that position for good, not just for a preemption. The consumer side has the mirror problem if moving the element out throws. The library therefore requires both operations to be `noexcept` and checks this with `static_assert`s; store elements that might throw on construction as a pointer or handle that cannot. A version that tolerated throwing constructors would need a way to publish a "poisoned" slot that consumers skip, which costs a branch on every pop. It is a good example of a general rule in lock-free code: every point after which other threads depend on you to finish is a point at which you must not fail.

### The Michael-Scott queue

Maged Michael and Michael Scott's 1996 queue is the textbook lock-free unbounded queue, and the basis of `java.util.concurrent.ConcurrentLinkedQueue`. It is a singly linked list with a **dummy node** at the head: `head_` always points to a node whose value has already been consumed (or that never had one), and the first real element is in `head_->next`.

Enqueue appends a new node after the last node and then swings `tail_` to it. Dequeue swings `head_` forward to `head_->next` and returns the value stored in that node, which becomes the new dummy.

![The Michael-Scott queue between the two steps of an enqueue. Node C is linked, but tail still points to B, and any thread that notices swings tail forward before it continues.](figures/msqueue.svg)

```cpp
template <class U>
void push(U&& v) {
    Node* node = new Node(std::forward<U>(v));
    HazardDomain::Guard hp;
    for (;;) {
        Node* tail = hp.protect(tail_);
        Node* next = tail->next.load(std::memory_order_acquire);
        if (tail != tail_.load(std::memory_order_acquire)) continue;  // tail moved
        if (next) {
            // Tail is lagging: help the other enqueuer and retry.
            tail_.compare_exchange_weak(tail, next, std::memory_order_release,
                                        std::memory_order_relaxed);
            continue;
        }
        Node* expected = nullptr;
        if (tail->next.compare_exchange_weak(expected, node, std::memory_order_release,
                                             std::memory_order_relaxed)) {
            // Linked. Swinging tail_ may fail if someone helped; that is fine.
            tail_.compare_exchange_strong(tail, node, std::memory_order_release,
                                          std::memory_order_relaxed);
            return;
        }
    }
}
```

Enqueue is a two-step operation: link the node (CAS on `tail->next`), then advance the tail (CAS on `tail_`). Between the two steps, the queue is in an intermediate state where `tail_` points to the second-to-last node. Any other thread that sees this state, recognisable by `tail->next != nullptr`, *helps* by advancing `tail_` itself before trying its own operation. This **helping** is what makes the algorithm lock-free: a thread preempted between the two steps cannot block anyone, because anyone can finish its work for it.

```cpp
std::optional<T> try_pop() {
    HazardDomain::Guard hp_head;
    HazardDomain::Guard hp_next;
    for (;;) {
        Node* head = hp_head.protect(head_);
        Node* tail = tail_.load(std::memory_order_acquire);
        Node* next = hp_next.protect(head->next);
        if (head != head_.load(std::memory_order_acquire)) continue;
        if (!next) return std::nullopt;  // empty
        if (head == tail) {
            // Tail lagging behind a completed enqueue; help it along.
            tail_.compare_exchange_weak(tail, next, std::memory_order_release,
                                        std::memory_order_relaxed);
            continue;
        }
        if (head_.compare_exchange_weak(head, next, std::memory_order_acq_rel,
                                        std::memory_order_relaxed)) {
            std::optional<T> out(std::move(next->value));
            next->value.reset();
            hp_next.reset();
            hp_head.reset();
            HazardDomain::global().retire(head);
            return out;
        }
    }
}
```

Dequeue reads `head`, `tail` and `head->next`, re-checks that `head` has not moved (so the three values are a consistent snapshot), and then either reports empty, helps a lagging tail, or swings `head_` to `next`. The winner of that CAS takes the value out of `next`, which becomes the new dummy, and retires the old dummy.

#### Reclamation

The old head node cannot simply be deleted: another thread may have read `head` a moment ago and be about to read `head->next`. This is the same use-after-free problem as in Treiber's stack (Chapter 6), and the same ABA problem lurks if nodes are recycled. The library solves it with **hazard pointers**, covered properly in Chapter 12. For now, read `hp.protect(src)` as "load `src` and announce to the world that I am using the result, so nobody may free it", and `retire(node)` as "free this node once nobody has announced it". Every pointer the algorithm dereferences after loading it from a shared location is protected first.

#### Costs

Every push allocates a node and every pop frees one (eventually). Every operation does two to four atomic RMWs and two hazard-pointer publications, which on x86 are `seq_cst` stores (Chapter 12 explains why). Head and tail are on separate cache lines, so producers and consumers do not contend with each other when the queue is non-empty, which is the algorithm's main advantage over a single-lock queue.

The lessons:

**Vyukov's queue has three times the capacity of the others** in every configuration: 5.7 to 6.5 million items a second, against 1 to 3 million. It does one CAS per operation and never allocates.

**Everything is far slower than SPSC.** Compare 6.5 million items a second with the SPSC ring's 139 million in Chapter 8. The single extra CAS per operation, and the contention on the shared position counters, cost a factor of twenty. This is the strongest argument for the advice at the start of the chapter: use SPSC rings wherever the topology allows.

**Paced latency is where the designs separate.** With one producer and one consumer, Vyukov's queue hands off an item in 207 ns at the median. The Michael-Scott queue takes twice as long (an allocation, more atomics and hazard pointers); the mutex queue five times as long.

**Overload is a cliff.** With three producers each sending 500,000 items a second (1.5 million in total) to one consumer, the mutex queue's capacity of 0.93 million is exceeded, its queue fills, and latency jumps to milliseconds: the median item waits almost 5 ms. The Michael-Scott queue, with enough average capacity, still has a millisecond p99 because the single consumer occasionally falls behind and the unbounded queue lets the backlog grow. This is the most common failure mode of real systems: not a slow queue, but a queue run close to or beyond its capacity.

**The tails are the machine.** The p99.9 figures of tens of microseconds to a millisecond, even in the comfortable configurations, are the virtual machine's interference with four busy-spinning threads on four vCPUs (and, in Vyukov's case, the occasional stalled producer described above, which a preempted thread makes visible). On isolated cores they shrink dramatically.

### Waiting well

Every queue in this book so far is non-blocking: `try_push` and `try_pop` return immediately. A real consumer with nothing to do must wait somehow, and *how* it waits has a bigger effect on latency than which queue it uses. The options form a spectrum:

| Strategy | Wake-up latency | CPU cost while idle |
|---|---|---|
| Busy-spin (`while (!try_pop()) {}`) | tens of ns | one full core |
| Spin with `pause` | tens of ns | one core, less power, kinder to the SMT sibling |
| Spin, then `yield()` | ~1 µs if the core is free, scheduler-dependent otherwise | high |
| Spin, then sleep on a futex (`atomic::wait`) | 5–50 µs | none |
| Sleep on a condition variable | 5–50 µs, plus mutex overhead | none |
| Sleep for a fixed time (`sleep_for`) | the sleep time, at least | none |

Latency-critical consumers on dedicated cores busy-spin. Everything else should spin briefly (the producer is often about to deliver) and then sleep. C++20's `std::atomic<T>::wait` and `notify_one`/`notify_all` give you a futex directly: `wait(old)` blocks until the atomic's value is no longer `old`, without a mutex or a condition variable.

The difficulty is the **lost wake-up**: the consumer checks the queue (empty), the producer pushes and notifies (nobody is waiting yet), and then the consumer goes to sleep, waiting for a notification that has already been sent. The standard defence is a counter, often called an *epoch* or *event count*, that producers increment after every push. The consumer reads the counter *before* its final check of the queue and sleeps only until the counter changes from that value. If a push happened in between, the counter has already changed and `wait` returns immediately.

Exercise 9.1 asks you to build a blocking queue on top of Vyukov's queue this way, with one more refinement: producers only call `notify` (a system call) when a consumer might be waiting, so the uncontended path never enters the kernel. The test checks not just correctness but that a waiting consumer really sleeps, by measuring its CPU time.

### Choosing a queue

| Need | Choice |
|---|---|
| One producer, one consumer | SPSC ring (Chapter 8) |
| Several producers, one consumer, ordering per producer | one SPSC ring per producer |
| Interchangeable work, bounded memory | Vyukov's bounded MPMC queue |
| Must never refuse an item, memory is not a concern | Michael-Scott (with a node pool, Chapter 11) |
| Producers can be preempted and consumers must not stall | Michael-Scott (lock-free), or per-producer SPSC rings |
| Every consumer must see every item | the Disruptor (Chapter 10) |
| Throughput matters, latency does not | batch everything; a mutex around a vector of batches is often fine |

### Summary

- Avoid MPMC where the topology allows: per-producer or per-consumer SPSC rings remove producer-producer contention entirely.
- Vyukov's queue gives each cell a sequence number; one relaxed CAS claims a position and one release store publishes it. No allocation. A producer preempted between the two can stall consumers at that slot.
- The Michael-Scott queue is a linked list with a dummy node; enqueue is a two-step operation that other threads help complete, which makes it lock-free. It allocates per item and needs safe memory reclamation.
- Measured: Vyukov 6 to 6.5 million items/s, Michael-Scott 1.5 to 3.3 million, mutex 1 to 2 million, against 139 million for SPSC. Paced hand-off latency: Vyukov 207 ns, Michael-Scott 427 ns, mutex 1 µs.
- Running a queue near capacity is a cliff: latency jumps to milliseconds.
- How a consumer waits matters as much as which queue it uses. Spin then sleep on a futex, and guard against lost wake-ups with an epoch counter.
