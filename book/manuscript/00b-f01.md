## Modern C++ Without Mystery {#f01}

This chapter covers the everyday C++ that the rest of the book takes for granted: how objects are initialised and how long they live, which standard containers to reach for, how to express "maybe no value" and "a view of someone else's data", and how a program is built from headers and source files. None of it is about concurrency yet. All of it matters for concurrency, because many concurrency bugs turn out to be ordinary lifetime bugs that scheduling makes hard to reproduce.

### Values, types and lifetimes

A variable names an object. The object's type decides which operations are allowed on it, and its lifetime decides when those operations mean anything. A pointer can still hold an address after the object at that address has died; that does not make the object alive again.

Prefer objects that are initialised where they are declared:

```cpp
struct Hit {
    std::uint64_t tick{};      // the {} makes each member start at zero
    std::uint16_t module{};
    std::uint16_t energy{};
};

Hit h{100, 3, 511};            // members in declaration order
Hit zero{};                    // all members zero
int count{};                   // zero
int garbage;                   // inside a function: indeterminate, reading it is undefined
const auto m = h.module;       // type deduced (std::uint16_t), and fixed at compile time
```

`auto` does not make a variable dynamically typed. It asks the compiler to write the type for you, from the initialiser, and the type is then as fixed as if you had written it. `const` says the variable will not be reassigned, which makes code easier to reason about and is free.

`std::uint64_t` and its relatives are integer types with an exact width. The book uses them whenever a value's width matters, for example in a data format or a counter that must not overflow, because the width of `long` differs between platforms.

**Passing arguments.** A function taking `Hit h` receives a copy. One taking `const Hit& h` borrows the caller's object and promises not to change it. One taking `Hit& h` borrows it and may change it. A reference never extends the life of the object it refers to: if a thread keeps a reference to a local variable after the function that owns the variable has returned, the reference dangles. Chapter F2 returns to this, because it is the most common way to crash a multithreaded program.

### Containers before pointers

`std::vector<T>` owns a contiguous sequence of `T`. *Contiguous* means the elements sit next to each other in memory, which is what makes scanning a vector fast (Chapter 2 explains why in detail).

```cpp
std::vector<Hit> hits;
hits.reserve(1000);              // room for 1000; size() is still 0
hits.push_back(Hit{100, 3, 511});
for (const auto& hit : hits) {   // borrow each element: no copy per iteration
    // ...
}
```

Two numbers describe a vector. `size()` counts the elements that exist; `capacity()` counts the slots reserved for them. `reserve(1000)` changes the capacity, not the size, so `hits[0]` after only a `reserve` is undefined behaviour: there is no element there. Use `push_back` to create elements one at a time, or `resize(n)` to create `n` of them at once.

When a vector grows past its capacity, it allocates new storage, moves the elements there, and frees the old storage. Every pointer, reference and iterator into the old storage is now invalid. Reserving a known upper bound avoids that, which is one reason low-latency code reserves at start-up. It does not make concurrent `push_back` calls safe: two threads changing one vector still need synchronisation.

`std::array<T, N>` owns exactly `N` elements, and `N` is part of its type. Choose an array when the size is fixed at compile time and a vector when it is not.

`std::span<const T>` is a *view*: a pointer and a length that refer to someone else's contiguous elements. It neither allocates nor owns. It is the right parameter type for a function that reads a sequence, because it accepts a vector, an array or part of either. It is the wrong thing to keep after the function returns, and returning a span of a local vector returns a dangling view.

### Saying "no value" and naming states

`std::optional<T>` holds either one `T` or nothing. A parser that may reject its input can return `std::optional<Hit>`:

```cpp
if (auto h = decode(bytes)) {   // true only if a Hit was produced
    use(*h);
}
```

An empty optional is not the same as a zero-valued `Hit`. A hit on module 0 with energy 0 may be perfectly valid; "the input was malformed" is a different fact, and the type should keep them apart. When the caller needs to know *why* something failed, return an `enum class` status instead, as the decoder in Chapter 19 does.

`enum class State { idle, running, draining, fault };` gives states names that do not silently convert to integers. It does not enforce which transitions are legal; that is still the design's job.

### The build model in one page

A `.cpp` file plus every header it includes becomes one *translation unit*. The compiler turns each translation unit into an object file; the linker combines the object files and libraries into a program, resolving calls from one file to functions defined in another.

Templates (Chapter F3) are normally defined entirely in headers, because the compiler needs the full definition wherever a template is used with a new type. An ordinary function defined in a header must be marked `inline`, or every translation unit that includes the header defines it again and the linker reports duplicate definitions. In this context `inline` is a linkage rule, not a request to inline the call. `#pragma once` stops a header being included twice into the *same* translation unit; it does nothing about duplicates *across* translation units.

The companion library `llds` is header-only, so there is nothing to link except the threads library. Build it as the preface describes, with CMake; the Foundations exercises are part of the same project:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build -R ex_f       # your Foundations exercises (fail until solved)
ctest --test-dir build -R sol_f      # the reference solutions (pass)
```

Turn on warnings and keep them at zero: the project compiles with `-Wall -Wextra -Wpedantic`, and many of the bugs in this part are things a warning would have pointed at.

### Summary

- Initialise every object where you declare it. `auto` deduces a type; it does not make it dynamic.
- `size()` counts elements, `capacity()` counts room. Growing a vector invalidates pointers into it.
- `std::span` borrows, it never owns. Do not keep one past the owner's lifetime.
- `std::optional` and `enum class` statuses keep "no value" and "failure" apart from valid zeros.
- Templates live in headers; non-template functions in headers need `inline`.
