## Atomics as a Design Tool {#ch06}

Chapter 3 treated atomics as a way to make individual accesses safe. This chapter treats them as building material. With a single primitive, compare-and-swap, you can build any concurrent object without locks; the question is how to do it so that it is correct, fast and safe from a family of bugs that do not exist in locked code. We start with the cost of atomic operations under contention, define the progress guarantees precisely, build the most famous lock-free structure of all, Treiber's stack, and then break it with the ABA problem and fix it with tagged pointers.

### The cost of an atomic operation

`examples/ch06_atomics.cpp` first measures single-threaded costs on the reference machine (loop-amortised, so these are per-operation throughput):

```text
single thread, per operation:
  plain increment          0.18 ns
  load(relaxed)            0.38 ns
  load(seq_cst)            0.73 ns
  store(release)           0.36 ns
  store(seq_cst)           6.66 ns
  fetch_add(relaxed)       6.97 ns
  compare_exchange        11.81 ns
```

On x86, every atomic read-modify-write (`fetch_add`, `exchange`, `compare_exchange`) is a `lock`-prefixed instruction. It must own the cache line exclusively for the duration of the operation and it acts as a full memory barrier, draining the store buffer. That costs about 7 ns (15 cycles) even with no contention at all, roughly 20 times a plain store. A CAS loop costs more again, because it is a load followed by a `lock cmpxchg`.

Then it measures contended costs: T threads increment one counter, either with `fetch_add` or with a CAS loop:

```text
contended counter, ns per increment (wall time / total ops):
  T=1 fetch_add    9.63 ns
  T=1 CAS loop    11.74 ns
  T=2 fetch_add   22.73 ns
  T=2 CAS loop    40.39 ns
  T=4 fetch_add   28.81 ns
  T=4 CAS loop    51.30 ns
```

![What atomics cost. Left: one thread, no contention; every operation that needs a full barrier costs about 7 ns or more. Right: one counter shared by T threads.](figures/chart-atomics.svg)

The wall time per increment grows with the number of threads, which means adding threads makes the *total* throughput worse, not better: four threads doing increments get 35 million done per second, one thread alone gets 104 million. Every increment must take the line from whichever core had it last. And CAS loops degrade faster than `fetch_add`, because a CAS can *fail*: between your load and your CAS, another thread may have changed the value, and you must retry, wasting both the work and a cache-line transfer. `fetch_add` cannot fail; the hardware performs the whole read-modify-write while holding the line.

Two design rules follow:

1. **Use the specific RMW when one exists.** If you need an atomic add, use `fetch_add`, not a CAS loop that adds. ARMv8.1's `ldadd` and x86's `lock xadd` are implemented in the cache controller and never retry.
2. **A contended atomic is a serialisation point.** No atomic primitive scales when every thread writes the same line. Scalable designs avoid shared writes (one writer per line), not just locks. The sharded counter in Exercise 13.1 is the standard fix for a contended counter.

### Compare-and-swap

`compare_exchange_strong(expected, desired)` atomically does:

```text
if (*this == expected) { *this = desired; return true; }
else                   { expected = *this; return false; }
```

Note that on failure it writes the current value into `expected`. That makes the standard CAS loop compact:

```cpp
T cur = a.load(std::memory_order_relaxed);
while (!a.compare_exchange_weak(cur, f(cur), std::memory_order_acq_rel,
                                std::memory_order_relaxed)) {
    // cur now holds the latest value; recompute and retry
}
```

`compare_exchange_weak` is allowed to fail *spuriously*, even when the value matches. On x86 it never does. On ARM and other load-linked/store-conditional (LL/SC) architectures, the "weak" form maps to a single LL/SC pair, which can fail if anything disturbs the reservation (an interrupt, another access to the same line), while the "strong" form must wrap it in a loop. Use `weak` inside a loop that retries anyway; use `strong` when a single attempt is all you want.

A CAS can implement any atomic read-modify-write you need. Exercise 6.1 asks you to build `fetch_max`, which C++26 adds to the standard but which no current mainstream x86 instruction provides:

```cpp
template <class T>
T fetch_max(std::atomic<T>& a, T v, std::memory_order order = std::memory_order_seq_cst) {
    T cur = a.load(std::memory_order_relaxed);
    while (cur < v && !a.compare_exchange_weak(cur, v, order, std::memory_order_relaxed)) {
    }
    return cur;
}
```

Notice the early exit: if `cur` is already at least `v`, we do not write at all. A CAS that writes the same value back still takes the line in exclusive state and invalidates every other core's copy. Avoiding unnecessary writes is one of the most effective optimisations in concurrent code.

### Progress guarantees

Chapter 1 introduced the progress classes informally. Here they are precisely. Consider a concurrent object and the threads that call its operations.

- **Blocking.** Some thread can be prevented from completing an operation indefinitely by another thread that is delayed (for example, preempted while holding a lock). Any algorithm that uses a lock is blocking.
- **Obstruction-free.** Any thread that runs *in isolation* (all other threads paused) completes its operation in a bounded number of steps. Contention can cause livelock, where threads keep undoing each other's work.
- **Lock-free.** In any execution, *some* thread completes an operation in a bounded number of system-wide steps. Individual threads can starve (keep failing their CAS while others succeed), but the system as a whole always makes progress, and a delayed thread cannot block others.
- **Wait-free.** *Every* thread completes its operation in a bounded number of its own steps, regardless of the others. No starvation, no matter what the scheduler does.

A typical CAS loop is lock-free but not wait-free: if a thread's CAS fails, it is because another thread's succeeded, so the system made progress, but the unlucky thread may fail forever in theory. `fetch_add` on a counter is wait-free on hardware that implements it natively. A seqlock writer (Chapter 7) is wait-free, but a seqlock reader is **blocking**: readers never delay one another, yet a writer that is preempted in the middle of a write leaves the counter odd, and every reader then retries until that writer runs again. (A fast writer that never pauses can also starve a reader, but that is a rate problem; the stalled writer is the progress problem.)

These guarantees concern **robustness to delay**, not speed. A wait-free algorithm is often slower on average than a lock-free one, and a lock-free one is often slower than a good lock. What lock-freedom buys you is that a thread preempted, faulting on a page, or running on a slow core in the middle of an operation cannot hold everyone else hostage. That is exactly the property a latency-sensitive system needs on its critical path.

### Treiber's stack

The simplest lock-free data structure, published by R. Kent Treiber at IBM in 1986, is a stack implemented as a singly linked list whose head pointer is updated with CAS:

```cpp
struct Node {
    T value;
    Node* next;
};
std::atomic<Node*> head{nullptr};

void push(Node* n) {
    n->next = head.load(std::memory_order_relaxed);
    while (!head.compare_exchange_weak(n->next, n, std::memory_order_release,
                                       std::memory_order_relaxed)) {
    }
}

Node* pop() {
    Node* top = head.load(std::memory_order_acquire);
    while (top && !head.compare_exchange_weak(top, top->next, std::memory_order_acquire,
                                              std::memory_order_acquire)) {
    }
    return top;
}
```

`push` points the new node at the current head and swings the head to the new node, retrying if the head changed in between. The release order publishes the node's contents to whoever pops it. `pop` reads the head, reads its `next`, and swings the head to `next`, retrying if the head changed.

It looks obviously correct. It has two serious problems.

**Problem 1: memory reclamation.** In `pop`, between loading `top` and reading `top->next`, another thread may pop `top` and *delete* it. Our read of `top->next` is then a use-after-free. This is the central problem of lock-free programming with dynamic memory, and it gets all of Chapter 12. For now we sidestep it: nodes are never freed while the stack exists.

**Problem 2: ABA.** Even if nodes are never freed, the stack can be corrupted, because a CAS only checks that the head has the *same value*, not that it has not *changed*.

### The ABA problem

Start with the stack A → B → C. Then:

1. Thread 1 begins `pop`. It reads `top = A` and `top->next = B`. Before it can execute its CAS, it is preempted.
2. Thread 2 pops A. The stack is B → C.
3. Thread 2 pops B. The stack is C. Node B is now "free" (perhaps returned to a pool).
4. Thread 2 pushes A back. The stack is A → C.
5. Thread 1 resumes. Its CAS compares the head with A, finds A, and succeeds, setting the head to B.

![The ABA problem. Thread 1's compare-and-swap sees top == A again and succeeds, although the stack changed underneath it and node B has been freed.](figures/aba.svg)

The head now points at B, a node that is not in the stack and that thread 2 may be using for something else entirely. C is lost. The structure is corrupt, and nothing crashed.

The name comes from the sequence of values the head took on: A, then something else, then A again. The CAS saw A both times and could not tell the difference.

`examples/ch06_atomics.cpp` replays this sequence deterministically (the "preemption" is simulated by interleaving the two threads' steps in one thread, so the output is the same every time):

```text
ABA demonstration with a naive stack (A -> B -> C):
  naive CAS succeeded: yes; head is now node 2
  but node 2 was popped by thread B: the stack is corrupted.
  tagged CAS succeeded: no (tag was 3, expected 0)
```

ABA is not an exotic corner case. It occurs whenever nodes are reused, and nodes are *always* reused in a low-latency system, because the whole point of a pool (Chapter 11) is to recycle memory without calling the allocator. Any lock-free structure that compares pointers with CAS and recycles its nodes is vulnerable unless it is designed against it.

### Defeating ABA with tagged pointers

The classic fix is to make the value compared by the CAS change on every modification, even if the pointer comes back. Pair the pointer with a **version tag** and increment the tag on every successful update. Then in step 5 above, thread 1 compares (A, tag 0) with the current (A, tag 3), and the CAS fails as it should.

The pair must be updated atomically, so it must fit in a single CAS. Two options:

- **Double-width CAS.** x86-64 has `cmpxchg16b`, which compares and swaps 16 bytes, so you can pair a full 64-bit pointer with a 64-bit counter. AArch64 has `casp` (ARMv8.1) and `ldxp`/`stxp`. Compilers use them for `std::atomic` of a 16-byte struct only with the right flags (`-mcx16` on GCC and Clang for x86), and GCC routes 16-byte atomics through `libatomic`, which may not report them as lock-free. Check `is_always_lock_free`.
- **Pointer packing.** On x86-64 and AArch64 Linux, user-space addresses fit in the low 48 bits of a pointer. The top 16 bits are available for a tag, and the whole thing fits in a single 64-bit word. A 16-bit tag wraps after 65,536 updates, so in principle a thread preempted for exactly a multiple of 65,536 updates could still suffer ABA. In practice that is extremely unlikely, but it is a probabilistic defence, not an absolute one. (Also, Linux on hardware with 5-level paging can hand out 57-bit addresses if a program asks for them; the library assumes it does not.)

The companion library uses pointer packing, in `include/llds/stack/treiber_stack.hpp`:

```cpp
class TaggedPtr {
public:
    static constexpr std::uint64_t kPtrMask = (std::uint64_t{1} << 48) - 1;

    TaggedPtr() = default;
    TaggedPtr(void* p, std::uint16_t tag) noexcept
        : bits_((reinterpret_cast<std::uint64_t>(p) & kPtrMask) |
                (static_cast<std::uint64_t>(tag) << 48)) {}

    template <class T>
    T* ptr() const noexcept { return reinterpret_cast<T*>(bits_ & kPtrMask); }
    std::uint16_t tag() const noexcept { return static_cast<std::uint16_t>(bits_ >> 48); }
    bool operator==(const TaggedPtr&) const = default;

private:
    std::uint64_t bits_ = 0;
};
```

and the stack itself is intrusive: anything that derives from `TaggedStackHook` can be pushed.

```cpp
struct TaggedStackHook {
    std::atomic<TaggedStackHook*> next{nullptr};
};

class TaggedStack {
public:
    void push(TaggedStackHook* n) noexcept {
        TaggedPtr old = head_.load(std::memory_order_relaxed);
        for (;;) {
            n->next.store(old.ptr<TaggedStackHook>(), std::memory_order_relaxed);
            TaggedPtr desired(n, static_cast<std::uint16_t>(old.tag() + 1));
            if (head_.compare_exchange_weak(old, desired, std::memory_order_release,
                                            std::memory_order_relaxed))
                return;
        }
    }

    TaggedStackHook* pop() noexcept {
        TaggedPtr old = head_.load(std::memory_order_acquire);
        for (;;) {
            auto* top = old.ptr<TaggedStackHook>();
            if (!top) return nullptr;
            auto* next = top->next.load(std::memory_order_relaxed);
            TaggedPtr desired(next, static_cast<std::uint16_t>(old.tag() + 1));
            if (head_.compare_exchange_weak(old, desired, std::memory_order_acquire,
                                            std::memory_order_acquire))
                return top;
        }
    }

private:
    alignas(kCacheLine) std::atomic<TaggedPtr> head_{};
};

static_assert(std::atomic<TaggedPtr>::is_always_lock_free);
```

A few details deserve comment.

- The `next` field is itself atomic. In `pop`, a thread may read `top->next` while another thread, having popped `top` and pushed it again, is writing `top->next`. The value read may be stale, but the tag guarantees the CAS will then fail. Making `next` atomic keeps that racing read well-defined; with a plain pointer it would be a data race and undefined behaviour, even though the stale value is never used.
- Both `push` and `pop` increment the tag. Strictly, only one of them needs to (incrementing on pop is enough to defeat the scenario above), but incrementing on both makes the argument simpler and costs nothing.
- The reclamation problem is still there. `pop` dereferences `top` after another thread may have popped it. That is safe *only* because nodes are never returned to the operating system while the stack is alive. That restriction is perfectly acceptable for the stack's main job, which is to be the free list inside a pool.

The test in `tests/test_memory.cpp` hammers the stack with four threads popping and re-pushing nodes 50,000 times each and then checks that every node is still present exactly once. Remove the tags (always pass 0) and, under enough contention, the test eventually fails.

### When not to use a lock-free stack

A lock-free stack is a fine free list and a poor general-purpose container. Every operation contends on one cache line, the head, so it scales no better than a spinlock-protected stack; under heavy contention it scales worse, because failed CAS attempts waste transfers. Its value is its *progress guarantee*: a thread preempted in the middle of `push` or `pop` does not prevent any other thread from using the stack. Where that matters, use it. Where it does not, a spinlock around a vector is simpler and often faster.

The same is true of lock-free structures in general. The guiding question is never "is it lock-free?" but "what happens to everyone else when one thread stalls here?".

### A catalogue of atomic idioms

Some patterns appear so often in this book that they deserve names.

**Publish-subscribe flag.** One writer fills in data, then stores a flag with release; readers load the flag with acquire, then read the data. The mailbox in Exercise 3.1 and every queue in Part III are elaborations of this.

**Single-writer counter.** A counter written by one thread and read by others needs no RMW: `c.store(c.load(relaxed) + 1, release)` (or relaxed, if it publishes nothing). Exercise 2.1 uses this.

**Claim by CAS.** Several threads compete to claim a slot or a task by CASing a field from "free" to "mine"; exactly one succeeds. Vyukov's queue (Chapter 9) claims positions this way; the lock-free hash map (Chapter 13) claims cells this way.

**Claim by fetch_add.** If every claimant should get a distinct ticket and nobody needs to fail, `fetch_add` is cheaper than CAS and never retries. The ticket lock uses it; so do some MPMC queue designs.

**Bounded increment.** Increment only if the result stays within a limit (a counting semaphore without blocking, an admission limit, a token bucket). This needs a CAS loop with a check inside it; a load followed by `fetch_add` is a check-then-act race. Exercise 6.2 asks you to build it.

**Monotonic max/min.** `fetch_max` and `fetch_min` keep a running extreme, such as the highest sequence number seen or the latest timestamp.

**Help-along.** In multi-step lock-free operations, a thread that finds another thread's operation half-done completes the missing step itself rather than waiting. The Michael-Scott queue's lagging tail pointer (Chapter 9) is the canonical example.

### Summary

- An atomic RMW on x86 is a locked instruction: a full barrier and about 7 ns uncontended. Contended, it costs a cache-line transfer, and adding threads reduces total throughput.
- Prefer `fetch_add` and friends to CAS loops when they fit; avoid writes that do not change the value.
- Blocking, obstruction-free, lock-free, wait-free: guarantees about robustness to delay, not about speed.
- Treiber's stack is the simplest lock-free structure. It has a reclamation problem (solved in Chapter 12) and an ABA problem.
- ABA happens whenever nodes are reused and a CAS compares pointers. Tagged pointers (or double-width CAS) defeat it.
